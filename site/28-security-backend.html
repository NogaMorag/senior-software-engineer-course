פרק 28: אבטחה לשירותי backend

רוב הפריצות לשירותי API אינן קריפטוגרפיה מתוחכמת. הן handler שמחזיר אובייקט של לקוח אחר, טוקן שנבדק רק חלקית, שרת שמבקש כתובת שהמשתמש בחר ומגיע לרשת הפנימית, וסוד שנכתב ללוג. הפרק עובר על הרשימה של OWASP לממשקי API, ובונה את ההגנות כקוד Go עם בדיקות: אימות טוקנים, הרשאה לכל אובייקט, הגנה מ־SSRF, מפתחות API מגובבים ולוגים שלא מדליפים. ובסוף, מודל איומים שמחבר את כולם.

מה נלמד בפרק

  • את רשימת OWASP API Security Top 10 מ־2023, וכל פריט ממופה לקוד Go מוחשי.
  • איך OIDC עובד למשתמשים (authorization code עם PKCE) ולשירותים (client credentials).
  • לאמת JWT נכון: רשימת אלגוריתמים סגורה, מנפיק, קהל יעד, זמנים עם מרווח, ומפתח לפי מזהה מתוך JWKS.
  • למצוא ולתקן BOLA: handler שמחזיר אובייקט של דיירת אחרת, הבדיקה שתופסת אותו, והתיקון.
  • להגן מ־SSRF בשתי שכבות: בדיקת המחרוזת, ובדיקה של הכתובת שאליה מתחברים בפועל, אחרי ה־DNS.
  • לשמור מפתחות API כגיבוב, לנהל סודות, ולהשמיט סודות מלוגים של slog.
  • להפיק SBOM, לסרוק תלויות, ולבנות מודל איומים בשיטת STRIDE.

28.1 OWASP API Security Top 10

הארגון OWASP מפרסם רשימה של עשר הבעיות הנפוצות והמסוכנות בממשקי API. המהדורה הנוכחית, נכון לאוקטובר 2026, היא של 2023. אין טעם לשנן אותה; יש טעם לדעת לזהות כל פריט בקוד. הטבלה ממפה כל פריט לצורה שלו ב־Go, ולמקום בספר שמטפל בו:

מזהה שם איך זה נראה בקוד Go איפה בספר
API1 Broken Object Level Authorization חיפוש לפי r.PathValue("id") בלי הדיירת מהטוקן סעיף 28.4
API2 Broken Authentication טוקן שנבדקת רק החתימה שלו, או אלגוריתם שלא נעול סעיפים 28.2 ו־28.3
API3 Broken Object Property Level Authorization struct שלם שמפוענח מהבקשה או מוחזר בתשובה, כולל שדות פנימיים סעיף 28.4
API4 Unrestricted Resource Consumption limit בלי תקרה, גוף בלי MaxBytesReader, בלי הגבלת קצב פרקים 6 ו־16

שימי לב שהפריט הראשון אינו באג קריפטוגרפי. BOLA בראש הרשימה כי הוא פשוט, נפוץ, ובלתי נראה לכלים: ה־handler עובד בדיוק כמו שנכתב, והתוקפת היא משתמשת מחוברת וחוקית שפשוט מחליפה מזהה בכתובת.

28.2 אימות ו־OIDC

אימות (authentication) עונה על „מי את?”. הרשאה (authorization) עונה על „מה מותר לך?”. רוב השירותים לא מאמתים סיסמאות בעצמם: הם סומכים על ספק זהות (identity provider) חיצוני, ומקבלים ממנו טוקן חתום. הפרוטוקול המקובל הוא OIDC (OpenID Connect), שכבת זהות מעל OAuth 2.0. הטוקן הוא בדרך כלל JWT (JSON Web Token): אובייקט חתום בשלושה חלקים, מופרדים בנקודות.

28.2.1 משתמשים: authorization code עם PKCE

כשמשתמשת נכנסת לאפליקציה, האפליקציה מפנה אותה לספק, הספק מאמת אותה, ומחזיר לאפליקציה קוד חד־פעמי. האפליקציה מחליפה את הקוד בטוקנים. PKCE (Proof Key for Code Exchange) מוסיף סוד חד־פעמי שנוצר בדפדפן, כך שמי שיירט את הקוד בדרך לא יוכל להחליף אותו:

sequenceDiagram
  participant U as User browser
  participant A as App
  participant I as Identity provider
  participant S as API
  A->>A: verifier = random; challenge = SHA256(verifier)
  A->>I: redirect /authorize?code_challenge=challenge&state=s
  U->>I: login (password, MFA)
  I->>A: redirect back with code and state
  A->>I: POST /token code + verifier
  I->>I: SHA256(verifier) == challenge ?
  I->>A: access token (JWT), id token
  A->>S: GET /v1/projects, Authorization Bearer token
  S->>S: verify signature, iss, aud, exp, kid
פריט תפקיד
state ערך אקראי שהאפליקציה בודקת כשהיא חוזרת; מונע זיוף של התחלת ההתחברות
code_verifier סוד אקראי שנשאר אצל האפליקציה; נשלח רק בהחלפת הקוד
code_challenge הגיבוב של ה־verifier; נשלח בהתחלה, גלוי לכולם
ה־id token אומר לאפליקציה מי המשתמשת; לא נשלח ל־API
ה־access token מה שה־API מקבל ובודק, עם קהל יעד (aud) של ה־API

28.2.2 שירותים: client credentials

שירות שקורא לשירות אחר אין לו משתמשת ואין לו דפדפן. הוא מזדהה מול הספק עם מזהה וסוד משלו (או עם מפתח פרטי, שעדיף), ומקבל access token ישירות:

sequenceDiagram
  participant B as Billing service
  participant I as Identity provider
  participant S as Projects API
  B->>I: POST /token grant_type=client_credentials, client auth, audience
  I->>B: access token (JWT, short-lived)
  B->>S: GET /v1/projects, Authorization Bearer token
  S->>S: same checks as for a user token

שני כללים לשני המקרים. ה־API לא מבחין בין המקורות: הוא בודק את אותו טוקן באותה דרך. והטוקן קצר חיים: דקות, לא ימים, כי JWT שנבדק מקומית אי אפשר לבטל לפני שפג תוקפו.

איך ה־API יודע מה המפתחות של הספק? הספק מפרסם מסמך גילוי (discovery) בכתובת קבועה מתחת ל־issuer, ובו כתובת של JWKS (JSON Web Key Set: רשימת המפתחות הציבוריים שלו, כל אחד עם מזהה kid). הספרייה go-oidc (בגרסה המוצמדת בנספח ג) עושה את הגילוי, מורידה את המפתחות ומרעננת אותם כשהספק מחליף מפתח. בתרגיל ה־JWKS הוא קובץ מקומי, כדי שהבדיקות ירוצו בלי רשת; את ההחלפה ל־go-oidc בייצור תמצאי ברשימת ההמשך של מודל האיומים.

28.3 JWT: מה בודקים

טוקן JWT בנוי משלושה חלקים, מופרדים בנקודות, וכל חלק מקודד ב־base64url:

  • הכותרת (header): באיזה אלגוריתם נחתם הטוקן (alg) ובאיזה מפתח (kid).
  • המטען (payload): הטענות (claims).
  • החתימה (signature): מכסה את שני החלקים הקודמים.

בדיקה נכונה עונה על שש שאלות, ולכל אחת יש התקפה מוכרת כשהיא חסרה:

בדיקה השאלה מה קורה בלעדיה
רשימת אלגוריתמים האם alg הוא אחד מאלה שאני מצפה להם? alg: none מתקבל; או HS256 עם המפתח הציבורי כסוד
kid איזה מפתח מה־JWKS? האם הוא מתאים לאלגוריתם? מפתח לא נכון, או בלבול בין סוגי מפתחות
חתימה האם הטוקן נחתם במפתח הזה ולא שונה? כל אחד כותב לעצמו tenant אחר
iss האם הספק הוא הספק שלי? טוקן מספק אחר שגם הוא נחתם כראוי
aud האם הטוקן הונפק בשבילי? טוקן לשירות אחר נשלח אליי ומתקבל
exp, nbf, iat האם הוא בתוקף עכשיו, עם מרווח קטן לסטיית שעונים? טוקן גנוב עובד לנצח

ההתקפה בשורה הראשונה ראויה להסבר. בבלבול אלגוריתמים (algorithm confusion), השרת מחזיק מפתח RSA ציבורי ומצפה ל־RS256. התוקפת חותמת טוקן ב־HS256, אלגוריתם סימטרי, ומשתמשת במפתח הציבורי כסוד. ספרייה שבוחרת את האלגוריתם לפי ה־header תאמת את החתימה בהצלחה. ההגנה: השרת קובע את רשימת האלגוריתמים, לא הטוקן.

28.3.1 הקוד

כל הבדיקות האלה הן אפשרויות של ה־parser של הספרייה, והפונקציה NewVerifier בונה אותו פעם אחת (הקובץ internal/jwtauth/verifier.go):

    parser := jwt.NewParser(
        jwt.WithValidMethods(cfg.Methods),
        jwt.WithIssuer(cfg.Issuer),
        jwt.WithAudience(cfg.Audience),
        jwt.WithLeeway(cfg.Leeway),
        jwt.WithExpirationRequired(),
        jwt.WithIssuedAt(),
        jwt.WithTimeFunc(cfg.Now),
    )
אפשרות מה היא אוכפת
WithValidMethods רשימת האלגוריתמים; כל alg אחר נדחה לפני שבודקים חתימה
WithIssuer, WithAudience התאמה מדויקת של iss; aud חייב להופיע ולהכיל את השירות
WithLeeway מרווח לסטיית שעונים על exp, nbf ו־iat; בתרגיל 30 שניות
WithExpirationRequired טוקן בלי exp נדחה, במקום להיחשב „בתוקף לנצח”
WithIssuedAt טוקן שהונפק בעתיד נדחה
WithTimeFunc השעון; הבדיקות מקפיאות אותו

לפני כן, NewVerifier מסרבת לתצורה מסוכנת: בלי מנפיק, בלי קהל יעד, או עם none או אלגוריתם סימטרי ברשימה. ברירת מחדל של „הכול מותר” היא באג, ולכן אין ברירת מחדל.

את המפתח בוחרת פונקציה שה־parser קורא לה אחרי שבדק את האלגוריתם. היא מוצאת את ה־kid ב־JWKS, ומוודאת שסוג המפתח מתאים למשפחת האלגוריתם (אותו קובץ):

func (v *Verifier) keyFor(t *jwt.Token) (any, error) {
    kid, _ := t.Header["kid"].(string)
    if kid == "" {
        return nil, ErrNoKID
    }
    key, ok := v.cfg.Keys[kid]
    if !ok {
        return nil, fmt.Errorf("%w %q", ErrUnknownKID, kid)
    }
    switch t.Method.(type) {
    case *jwt.SigningMethodRSA, *jwt.SigningMethodRSAPSS:
        if _, ok := key.(*rsa.PublicKey); !ok {
            return nil, ErrKeyType
        }
    case *jwt.SigningMethodECDSA:
        if _, ok := key.(*ecdsa.PublicKey); !ok {
            return nil, ErrKeyType
        }
    default:
        return nil, ErrKeyType
    }
    return key, nil
}

ופרט אחד בטענות עצמן. הטיפוס Claims מוסיף לטענות הרשומות את tenant. המתודה Validate שלו דוחה טוקן בלי דיירת או בלי נושא (sub), וה־parser קורא לה אחרי הבדיקות הרגילות. כך טוקן בלי דיירת נדחה כמו טוקן שפג תוקפו.

איך Rust עושה את זה: ב־crate jsonwebtoken, המבנה Validation מחזיק את רשימת האלגוריתמים, את המנפיק, את הקהל ואת המרווח, ופונקציית הפענוח דוחה טוקן שלא מתאים. העיקרון זהה: האלגוריתם מגיע מהתצורה של השרת, לא מה־header.

28.3.2 הבדיקות

כל שורה בבדיקה הטבלאית יוצרת טוקן שתקין חוץ מדבר אחד, ומוודאת שהוא נדחה בשגיאה הנכונה. המפתחות נוצרים פעם אחת לכל הרצה, וה־JWKS נבנה מהם, כך שאין מפתח פרטי במאגר (הקובץ internal/jwtauth/verifier_test.go):

        {"alg none", func(t *testing.T) string {
            return sign(t, jwt.SigningMethodNone, "rsa-1", goodClaims(), jwt.UnsafeAllowNoneSignatureType)
        }, jwt.ErrTokenSignatureInvalid},
        {"alg confusion: HS256 keyed with the public key", func(t *testing.T) string {
            return sign(t, jwt.SigningMethodHS256, "rsa-1", goodClaims(), pubDER)
        }, jwt.ErrTokenSignatureInvalid},

בטבלה 19 שורות, בחמש קבוצות:

קבוצה השורות
תקינים טוקן RS256, טוקן ES256
אלגוריתם none; בלבול אלגוריתמים; RS512, שאינו ברשימה
מנפיק וקהל issuer שגוי; audience של שירות אחר; בלי audience
זמנים פג תוקף מעבר למרווח; פג תוקף בתוך המרווח (מתקבל); בלי exp; nbf בעתיד; iat בעתיד
מפתח ותוכן בלי kid; kid לא מוכר; מפתח EC על טוקן RSA; payload ששונה; בלי דיירת; מחרוזת שאינה JWT

השורה „פג תוקף בתוך המרווח” חשובה כמו האחרות: היא מוכיחה שהמרווח עובד, ולא רק שהכול נדחה.

ניסוי מהתרגיל מראה למה יש שתי שכבות. כשמוחקים את WithValidMethods, השורות של none ושל בלבול האלגוריתמים עדיין נדחות, כי keyFor מסרבת למפתח RSA על טוקן שאינו RSA. אבל טוקן RS512 מתקבל: הוא חתום במפתח הנכון, באלגוריתם שאף אחד לא התכוון לאשר. כל שכבה תופסת מה שהשנייה מפספסת.

ה־middleware מחזיר 401 עם הכותרת WWW-Authenticate לפי RFC 6750. הסיבה המדויקת נכתבת ללוג, והלקוחה מקבלת רק invalid_token, כי „פג תוקף” מול „חתימה שגויה” הוא מידע שימושי לתוקפת. והטוקן עצמו לא נכתב לשום מקום.

28.4 הרשאות: BOLA

BOLA (Broken Object Level Authorization) הוא מצב שבו משתמשת מחוברת וחוקית מבקשת אובייקט לפי מזהה, והשירות מחזיר אותו בלי לבדוק שהוא שלה. בקוד ההתחלה של התרגיל, המאגר מחפש לפי מזהה בלבד, וה־handler משתמש בזה (הקובץ starter/internal/projects/handler.go):

    p, err := h.Store.ByID(r.Context(), r.PathValue("id"))

ה־handler כן בודק שיש משתמשת מחוברת. הוא פשוט לא שואל של מי האובייקט. זו בדיוק הסיבה שאף כלי לא תופס את זה: הקוד נכון מבחינת טיפוסים, שגיאות ומקביליות, והוא עושה מה שנכתב.

הבדיקה שתופסת את זה מתחזה לדיירת אחת ומבקשת אובייקט של דיירת אחרת. היא גם בודקת שהתשובה לא מגלה אם המזהה קיים (הקובץ internal/projects/handler_test.go):

func TestTenantCannotReadAnotherTenantsProject(t *testing.T) {
    h := newServer()
    rec := as(t, h, "globex", "/v1/projects/prj_a1")
    if rec.Code != http.StatusNotFound {
        t.Fatalf("globex reading acme's project: status %d, body %q; want 404", rec.Code, rec.Body.String())
    }
    if strings.Contains(rec.Body.String(), "Acme") {
        t.Fatalf("response leaks the other tenant's data: %q", rec.Body.String())
    }
    // "Not yours" must look exactly like "does not exist", or ids can be enumerated.
    missing := as(t, h, "globex", "/v1/projects/prj_zz")
    if missing.Code != rec.Code || missing.Body.String() != rec.Body.String() {
        t.Fatalf("cross-tenant answer %d %q differs from missing-id answer %d %q",
            rec.Code, rec.Body.String(), missing.Code, missing.Body.String())
    }
}

על קוד ההתחלה הבדיקה נכשלת עם 200 ועם השם של הפרויקט של הדיירת האחרת. התיקון הוא להכניס את הדיירת למפתח החיפוש, כך שאי אפשר לשכוח אותה. החתימה של הממשק משתנה, והקומפיילר מוצא כל מקום שקורא לה (הקובץ internal/projects/store.go בפתרון):

func (s *MemoryStore) Get(_ context.Context, tenantID, id string) (Project, error) {
    s.mu.RLock()
    defer s.mu.RUnlock()
    p, ok := s.byID[id]
    if !ok || p.TenantID != tenantID {
        return Project{}, ErrNotFound

ב־PostgreSQL (פרק 10) זה אותו רעיון בשאילתה: WHERE tenant_id = $1 AND id = $2, ולא שליפה לפי מזהה ובדיקה ב־Go אחריה. וה־handler לוקח את הדיירת רק מהטוקן המאומת, לעולם לא מכותרת, מפרמטר או מגוף הבקשה.

ארבע החלטות שהתיקון מגלם:

  • 404 ולא 403. תשובה 403 מאשרת שהמזהה קיים, וזה מספיק כדי למפות מזהים של לקוחות אחרים.
  • הדיירת בחתימה של המאגר. בדיקה שה־handler עושה אחרי השליפה תישכח ב־handler הבא.
  • מזהים אקראיים לא מספיקים. הם מקשים לנחש, אבל מזהה דולף בלוג, בקישור או בצילום מסך.
  • בדיקת BOLA לכל נתיב חדש. זו השורה האחרונה ברשימת ההמשך של מודל האיומים.

שני האחים של BOLA ברשימה של OWASP הם אותה שאלה ברמה אחרת. ברמת השדה (API3): השדה הפנימי TenantID מסומן כך שלא ייצא בתשובה, ומפענחים קלט לטיפוס בקשה נפרד ולא ל־struct השמור. וברמת הפונקציה (API5): נתיב ניהול בודק תפקיד, לא רק שהמשתמשת מחוברת.

28.5 SSRF

SSRF (Server Side Request Forgery) קורה כשהשירות שולח בקשה לכתובת שהמשתמשת בחרה. ב־Hookline, למשל, דיירת רושמת כתובת שאליה יישלחו webhooks. אם הכתובת היא http://169.254.169.254/latest/meta-data/, השרת מבקש את שירות המטא־דאטה של הענן ועלול להחזיר מפתחות גישה זמניים. אם היא http://10.0.0.5:9200/, השרת פונה לבסיס נתונים פנימי שאף פעם לא נחשף לאינטרנט.

28.5.1 למה בדיקת המחרוזת לא מספיקה

הניסיון הראשון הוא לבדוק את הכתובת לפני הבקשה. הוא נשבר בשלוש דרכים:

עקיפה למה בדיקת מחרוזת מפספסת
שם שמצביע לכתובת פנימית internal.attacker.example עובר כל בדיקה של מחרוזת, ונפתר ל־10.0.0.5
DNS rebinding השם נפתר לכתובת ציבורית בבדיקה, ולכתובת פנימית שנייה אחר כך, בחיבור
כתיב חלופי 0x7f000001 אינו כתובת IP בעיני url.Parse, אבל resolver של המערכת עשוי לפרש אותו כ־127.0.0.1
הפניה הכתובת הראשונה תקינה, והשרת שלה מחזיר 302 לכתובת פנימית

המסקנה: בודקים את הכתובת שאליה מתחברים בפועל, אחרי ה־DNS, בכל חיבור. ב־Go יש לזה נקודה מדויקת: הפונקציה Control של ה־dialer נקראת אחרי שהכתובת נפתרה ולפני החיבור עצמו, עם הכתובת של אותו ניסיון חיבור.

28.5.2 שתי שכבות

השכבה הראשונה, CheckURL, דוחה מה שאפשר לדחות מהמחרוזת: סכמה (ברירת המחדל: https בלבד), פרטי התחברות בכתובת, בלי host, וכתובת IP מפורשת שנמצאת בטווח חסום. היא נותנת הודעת שגיאה ברורה מוקדם, ברישום הכתובת. השכבה השנייה היא זו שמחזיקה (הקובץ internal/ssrf/ssrf.go):

func (p Policy) Control(network, address string, _ syscall.RawConn) error {
    if network != "tcp4" && network != "tcp6" {
        return fmt.Errorf("%w: network %q", ErrBlocked, network)
    }
    ap, err := netip.ParseAddrPort(address)
    if err != nil {
        return fmt.Errorf("%w: %v", ErrBlocked, err)
    }
    return p.CheckAddr(ap.Addr())
}

הפונקציה CheckAddr מבטלת קודם את המיפוי של IPv4 בתוך IPv6, כי הכתובת ::ffff:127.0.0.1 היא בעצם 127.0.0.1. אחר כך היא בודקת מול רשימה מפורשת של טווחים:

func (p Policy) Client(timeout time.Duration) *http.Client {
    dialer := &net.Dialer{Timeout: 5 * time.Second, Control: p.Control}
    transport := &http.Transport{
        Proxy:                 nil, // a proxy would make the dialer check the proxy, not the target
        DialContext:           dialer.DialContext,
        ForceAttemptHTTP2:     true,
        MaxIdleConns:          100,
        IdleConnTimeout:       90 * time.Second,
        TLSHandshakeTimeout:   5 * time.Second,
        ResponseHeaderTimeout: 10 * time.Second,
    }
    return &http.Client{
        Timeout:   timeout,
        Transport: transport,
        CheckRedirect: func(req *http.Request, via []*http.Request) error {
            if len(via) >= maxRedirects {
                return fmt.Errorf("%w: more than %d redirects", ErrBlocked, maxRedirects)
            }
            _, err := p.CheckURL(req.URL.String())
            return err
        },
    }
}

28.6 ניהול סודות

סוד (secret) הוא כל ערך שמי שמחזיק בו יכול לפעול בשמך: סיסמה למסד נתונים, מפתח API, סוד חתימה, מפתח פרטי. שלוש שאלות על כל סוד: איפה הוא נשמר, איך הוא מגיע לתהליך, ואיך מחליפים אותו.

28.6.1 איך הסוד מגיע לתהליך

דרך יתרון חיסרון
משתנה סביבה פשוט, כל כלי תומך נראה ב־/proc/<pid>/environ, עובר לתהליכי בן, נשפך בדוחות קריסה; החלפה דורשת הפעלה מחדש
קובץ שמותקן לקונטיינר הרשאות קובץ; Kubernetes מעדכן את הקובץ כשה־Secret משתנה צריך לקרוא מחדש כדי ליהנות מההחלפה
מנהל סודות (Vault, AWS Secrets Manager וכדומה) בקרת גישה, יומן ביקורת, סודות זמניים עוד מערכת שצריכה להיות זמינה, ועוד הרשאה לנהל

ב־Kubernetes, האובייקט Secret מקודד ב־base64, לא מוצפן. כל מי שיכול לקרוא אותו ב־API קורא את הערך. שלושה דברים מגנים עליו:

  • הרשאות גישה ב־RBAC, לפי מינימום הרשאות (least privilege).
  • הצפנה במנוחה של מאגר הנתונים של ה־cluster, שהמנהלת שלו מפעילה.
  • לא לשמור אותו גלוי במאגר Git.

פרק 20 מראה איך מחברים Secret ל־pod.

החלפה (rotation) היא הבדיקה האמיתית. סוד שאי אפשר להחליף בלי השבתה לא יוחלף, גם אחרי שדלף. הדפוס: שני ערכים תקפים בזמן החפיפה (הישן והחדש), הפצה של החדש, ורק אחר כך ביטול הישן. JWKS עושה בדיוק את זה עם מפתחות חתימה: כמה kid בבת אחת.

28.6.2 מפתחות API מגובבים

מפתח API הוא סוד ארוך טווח שהשירות שלך מנפיק. כלל הברזל: שומרים רק גיבוב (hash). אם בסיס הנתונים דולף, התוקפת מקבלת גיבובים, לא מפתחות. במפתח של התרגיל שלושה חלקים, hl_<id>_<secret>:

חלק תפקיד
הקידומת hl אומרת מה המחרוזת: אדם מזהה אותה, וסורקי סודות ב־Git מוצאים אותה
המזהה 6 בתים אקראיים בהקסדצימלי; ציבורי, ומשמש לחיפוש השורה
הסוד 32 בתים מ־crypto/rand, ב־base64url

הנה ההנפקה והאימות (הקובץ internal/apikey/apikey.go):

func Generate(prefix, owner string) (plaintext string, stored Stored, err error) {
    if !prefixRE.MatchString(prefix) {
        return "", Stored{}, errors.New("apikey: prefix must be 2 to 8 lowercase letters")
    }
    buf := make([]byte, idBytes+secretBytes)
    if _, err := rand.Read(buf); err != nil { // never fails on supported platforms; checked anyway
        return "", Stored{}, err
    }
    id := hex.EncodeToString(buf[:idBytes])
    secret := base64.RawURLEncoding.EncodeToString(buf[idBytes:])
    plaintext = prefix + "_" + id + "_" + secret
    return plaintext, Stored{ID: id, Hash: sha256.Sum256([]byte(plaintext)), Owner: owner}, nil
}

func (s Stored) Matches(key string) bool {
    sum := sha256.Sum256([]byte(key))
    return subtle.ConstantTimeCompare(sum[:], s.Hash[:]) == 1
}

למה SHA-256 ולא bcrypt? גיבוב איטי כמו bcrypt או argon2 נועד לסיסמאות: ערכים שאנשים בוחרים, עם מעט אנטרופיה, שאפשר לנחש במיליארדי ניסיונות. למפתח שלנו 256 ביטים אקראיים, ואין מה לנחש: גם בגיבוב מהיר, חיפוש ממצה לא יסתיים לעולם. גיבוב איטי היה רק עולה זמן CPU בכל בקשה, והופך כל בקשה עם מפתח שגוי לדרך זולה להעמיס על השירות. ולמה השוואה בזמן קבוע? כדי שזמן התשובה לא יגלה כמה בתים ראשונים של הגיבוב התאימו. כאן החשיפה קטנה, כי התוקפת לא שולטת בגיבוב, אבל ההשוואה הזאת לא עולה כלום ומונעת ויכוח.

המפתח מוצג למשתמשת פעם אחת, ביצירה. אם איבדה אותו, מנפיקים חדש ומבטלים את הישן; אין „שחזור”.

28.6.3 לעולם לא ללוג

לוגים מועתקים, נשמרים חודשים, ונקראים על ידי יותר אנשים מאשר בסיס הנתונים. החבילה redact של התרגיל נותנת שלושה כלים, מהחזק לחלש:

  • הטיפוס Secret: מחרוזת שכל צורת הדפסה שלה היא [REDACTED], בכל דרך שבה Go מדפיסה ערך.
  • הפונקציה ReplaceAttr: מחליפה ערכים לפי שם המפתח, ולפי צורת הערך.
  • הפונקציה Header: כותבת כותרות HTTP כקבוצה, כי ReplaceAttr לא נכנסת לתוך maps.

הפונקציה ReplaceAttr מתחברת לאפשרויות של ה־handler של slog, שקורא לה לכל מאפיין, גם בתוך קבוצות (הקובץ internal/redact/redact.go):

func ReplaceAttr(_ []string, a slog.Attr) slog.Attr {
    if a.Value.Kind() == slog.KindGroup {
        return a // slog calls ReplaceAttr again for each member
    }
    if sensitive(a.Key) {
        return slog.String(a.Key, Redacted)
    }
    if a.Value.Kind() == slog.KindString && secretShapes.MatchString(a.Value.String()) {
        return slog.String(a.Key, secretShapes.ReplaceAllString(a.Value.String(), Redacted))
    }
    return a
}

הבדיקה כותבת ללוג סיסמה, טוקן, מפתח API, סוד חתימה ועוגייה בכל הצורות שיש להן (לפי שם, בתוך קבוצה, דרך With, בתוך משפט חופשי, ככותרת), ומוודאת שאף אחד מהם לא מופיע בפלט. והיא בודקת גם את הכיוון ההפוך: שהכתובת ושאר הערכים הרגילים נשארו, כי מסנן שמוחק יותר מדי מכבים מהר מאוד. כך נראית שורה אחת:

{"time":"...","level":"INFO","msg":"calling endpoint","url":"https://hooks.example.com","Authorization":"[REDACTED]","note":"retrying with [REDACTED]","signing_secret":"[REDACTED]"}

בדיקה שלישית מתעדת את המגבלה: כותרות HTTP גולמיות שנכתבות ללוג כערך אחד כן מדליפות, כי הן map. היא עוברת כל עוד הדליפה קיימת, וכך אם slog ישתנה, הבדיקה תגיד לעדכן את התיעוד. מסנן כזה הוא רשת ביטחון, לא תחליף לא לכתוב סודות מלכתחילה.

28.8 מודל איומים

מודל איומים (threat model) הוא מסמך קצר שעונה על ארבע שאלות: מה אנחנו בונים, מה יכול להשתבש, מה אנחנו עושים לגבי זה, והאם עשינו עבודה טובה. הוא נכתב לפני הקוד, ומתעדכן כשמשהו משתנה: קורא חדש, מאגר חדש, תלות חיצונית.

השיטה STRIDE עוברת על כל רכיב בתרשים זרימת הנתונים, ובעיקר על כל חציה של גבול אמון (trust boundary), ושואלת שש שאלות:

אות איום השאלה ההגנה הטיפוסית
S התחזות (Spoofing) האם מישהו יכול להעמיד פנים שהוא מישהו אחר? אימות: JWT, מפתחות, mTLS
T שינוי (Tampering) האם מישהו יכול לשנות נתונים או קוד בדרך? חתימות, TLS, הרשאות כתיבה
R הכחשה (Repudiation) האם מישהו יכול להכחיש פעולה כי אין הוכחה? לוגים של פעולות, עם מזהה ובלי סודות
I חשיפת מידע (Information disclosure) האם מישהו יכול לקרוא מה שלא שלו? הרשאה לכל אובייקט, הסתרת שדות, לוגים נקיים
D מניעת שירות (Denial of service) האם מישהו יכול להשבית? זמנים קצובים, גבולות גודל, הגבלת קצב
E העלאת הרשאות (Elevation of privilege) האם מישהו יכול לעשות מה שהתפקיד שלו לא מתיר? הרשאה לכל פונקציה, מינימום הרשאות, SSRF

התבנית של התרגיל (בתיקייה data) מבקשת שישה דברים: תיאור קצר, תרשים זרימה עם גבולות אמון, נכסים, טבלת איומים, החלטות, והמשך. בטבלת האיומים לכל שורה יש עמודה שרוב המודלים שוכחים: הבדיקה או הראיה. איום שמסומן „מטופל” בלי בדיקה הוא תקווה. הנה שתי שורות מהמודל המלא של הפתרון (הקובץ solution/docs/threat-model.md):

| T4 | Project store | I | Tenant B requests tenant A's project id (BOLA) | Tenant from the verified token is part of every store lookup; same 404 for missing and foreign | `TestTenantCannotReadAnotherTenantsProject`, `TestListIsScopedToTenant` | Low for these routes; every new route needs the same test | service team |
| T6 | Outbound calls | E | A tenant registers `http://169.254.169.254/...` or a name resolving to 10.x and makes us fetch it (SSRF) | `ssrf.Policy`: URL check, dialer `Control` on the resolved address, redirects re-checked, no proxy | `TestClientChecksResolvedAddress`, `TestRedirectsAreRechecked` | Low; IPv6 ranges list must be kept current | service team |

שלושה הרגלים שהופכים את המודל לשימושי:

  • סיכון שנשאר נכתב. „טוקן גנוב תקף עד שפג תוקפו” הוא סיכון שמקבלים בכוונה, עם סיבה ועם מה שישנה את ההחלטה.
  • לכל שורה בעלים. איום בלי בעלים לא יטופל.
  • המודל קצר. עמוד או שניים שנקראים עדיפים על עשרים שאף אחד לא פותח.

בראיון, מודל איומים הוא דרך מצוינת לענות על „איך היית מאבטחת את המערכת הזאת?”: תרשים, גבולות אמון, ואז STRIDE על כל חציה. Hookline, באבן הדרך M9, כותב את המודל שלו באותה תבנית.

סיכום

  • רשימת OWASP API Top 10 מ־2023 מתחילה ב־BOLA: משתמשת חוקית, מזהה של מישהו אחר, ובלי כלי שיתפוס את זה.
  • OIDC: authorization code עם PKCE למשתמשים, client credentials לשירותים; ה־API בודק את שני הטוקנים באותה דרך.
  • JWT: האלגוריתם מהתצורה, מפתח מה־JWKS עם סוג מתאים, מנפיק וקהל יעד מדויקים, תפוגה חובה, מרווח קטן.
  • BOLA מתוקן בהכנסת הדיירת למפתח החיפוש ובחתימה של המאגר, עם 404 זהה ובדיקה לכל נתיב.
  • SSRF: בדיקת המחרוזת נותנת הודעה, ה־Control של ה־dialer נותן ביטחון; בלי proxy, והפניות נבדקות מחדש.
  • סודות: Secret של Kubernetes הוא base64, החלפה היא הבדיקה האמיתית, ומפתחות API נשמרים כ־SHA-256.
  • לוגים: טיפוס שלא מודפס, מסנן מאפיינים ופונקציה לכותרות, ובדיקה שמוודאת שהסודות לא בפלט והשאר כן.
  • SBOM מ־Syft, וסריקה עם Grype או Trivy לצד govulncheck.
  • מודל איומים בשיטת STRIDE, ולכל שורה בו בדיקה ובעלים.

טעויות נפוצות

  • לבחור את האלגוריתם לפי ה־header. טוקן עם alg: none, או HS256 עם המפתח הציבורי, מתקבל. הרשימה באה מהתצורה.
  • לבדוק רק את החתימה. טוקן חתום כראוי שהונפק לשירות אחר (aud) או על ידי ספק אחר (iss) מתקבל.
  • exp לא חובה. טוקן בלי exp נחשב בתוקף לנצח. WithExpirationRequired.
  • לשלוף לפי מזהה ולבדוק בעלות אחר כך ב־Go. הבדיקה נשכחת ב־handler הבא. הדיירת בשאילתה ובחתימה.
  • להחזיר 403 על אובייקט של דיירת אחרת. זה מאשר שהמזהה קיים. 404, זהה לחלוטין לחסר.
  • לבדוק SSRF רק במחרוזת. שם שנפתר ל־10.x, הפניה או DNS rebinding עוקפים אותה. Control על ה־dialer.
  • לשכוח את ה־proxy. עם הגדרת ה־proxy מהסביבה, ה־dialer בודק את ה־proxy ולא את היעד. בלקוח המוגן, Proxy: nil.
  • bcrypt למפתחות API אקראיים. עלות CPU בכל בקשה בלי שום תועלת. SHA-256 על 256 ביטים אקראיים.
  • לחשוב ש־Secret של Kubernetes מוצפן. הוא base64. RBAC והצפנה במנוחה.

שאלות ראיון

  1. למה חייבים לנעול את האלגוריתם באימות JWT? כי ה־header של הטוקן נשלט בידי מי ששלח אותו. ספרייה שבוחרת לפי alg תקבל none בלי חתימה, או HS256 שבו המפתח הציבורי של השרת משמש כסוד משותף, ואת המפתח הציבורי כולם מכירים. לכן השרת מחזיק רשימה סגורה, ובודק גם שסוג המפתח של ה־kid מתאים לאלגוריתם. העלות היא תצורה מפורשת, ושינוי שלה כשהספק עובר אלגוריתם.

המשך: ואיך מתמודדים עם החלפת מפתחות אצל הספק? ה־JWKS מכיל כמה מפתחות עם kid שונים; מורידים אותו מחדש מדי פעם, ובמיוחד כשמגיע kid לא מוכר, עם הגבלה על התדירות כדי שטוקנים מזויפים לא יגרמו להצפה.

  1. מה זה BOLA, ולמה הוא בראש הרשימה של OWASP? משתמשת מחוברת וחוקית מבקשת אובייקט לפי מזהה, והשירות מחזיר אותו בלי לבדוק שהוא שלה. הוא נפוץ כי כל נתיב עם מזהה הוא הזדמנות לשכוח, והוא בלתי נראה לכלים כי הקוד עושה בדיוק מה שנכתב. התיקון המבני הוא להכניס את הדיירת מהטוקן לחתימה של המאגר ולשאילתה, ולהחזיר 404 זהה לאובייקט חסר; ובדיקה של „דיירת אחרת” לכל נתיב.

  2. למה בדיקה של מחרוזת הכתובת לא מספיקה נגד SSRF? כי מה שנבדק אינו מה שמתחברים אליו. שם יכול להיפתר לכתובת פנימית, להיפתר לכתובת אחרת בין הבדיקה לחיבור, להיכתב בצורה שה־resolver מפרש אחרת, או להחזיר הפניה. ב־Go בודקים ב־Control של net.Dialer, שמקבל את הכתובת אחרי ה־DNS, לפני connect, בכל ניסיון. ובנוסף: בלי proxy, הפניות נבדקות מחדש, וזמנים קצובים. בדיקת המחרוזת נשארת בשביל הודעת שגיאה טובה ברישום.

  3. למה מגבבים מפתחות API, ולמה לא עם bcrypt? כדי שדליפה של בסיס הנתונים לא תיתן מפתחות שעובדים. bcrypt ודומיו איטיים בכוונה כדי להגן על סיסמאות שאנשים בוחרים, שאפשר לנחש. למפתח אקראי של 256 ביטים אין מה לנחש, ולכן SHA-256 מספיק, וגיבוב איטי רק היה מוסיף עלות CPU לכל בקשה ופותח פתח להעמסה. ההחלטה משתנה אם המפתחות נבחרים בידי אנשים.

  4. איך היית בונה מודל איומים לשירות חדש? תרשים זרימת נתונים עם השחקנים, השירותים, המאגרים והמערכות החיצוניות, ועליו גבולות האמון. אחר כך STRIDE על כל חציה, ולכל איום: ההגנה, הבדיקה שמוכיחה אותה, הסיכון שנשאר, ובעלים. הוא נכתב לפני הקוד ומתעדכן בכל שינוי מהותי. החולשה של השיטה היא שהיא תלויה בתרשים: מה שלא צויר לא ייבדק, ולכן מתחילים מהתרשים ומבקשים ממישהו אחר לסקור אותו.
