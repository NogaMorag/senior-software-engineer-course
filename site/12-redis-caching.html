פרק 12: Redis ומטמון

מטמון נראה כמו האופטימיזציה הקלה ביותר בעולם: שומרים תשובה בזיכרון ומחזירים אותה בפעם הבאה. בפועל הוא מוסיף מקור אמת שני שמתיישן, תלות שיכולה ליפול, ותקלות שמופיעות רק תחת עומס. בראיון לתפקיד backend בכיר לא ישאלו אותך איך כותבים GET; ישאלו מה קורה כשהמפתח החם פג באמצע שעת שיא, ולמה מוחקים אחרי הכתיבה ולא לפניה. בפרק הזה תבני מטמון מעל מאגר המוצרים, תראי התפרצות מטמון במספרים שלך, ותתקני אותה.

מה נלמד בפרק

  • להריץ Redis בקונטיינר, ולהכיר את מבני הנתונים שבאמת משמשים ב־backend.
  • את דפוס cache-aside: מסלול הקריאה, מסלול הכתיבה, ולמה מוחקים אחרי ה־commit.
  • זמן חיים (TTL) עם פיזור אקראי, מדיניות פינוי, והמרוץ שה־TTL חוסם.
  • התפרצות מטמון: למדוד אותה, ולתקן אותה עם singleflight.
  • מונים אטומיים עם INCR, וסקריפט Lua ראשון כהקדמה לפרק 16.
  • מתי מטמון מזיק, ואיך מודדים יחס פגיעות במקום לנחש.

ידע מקדים

  • פרק 2, סעיף 2.4 (Docker Desktop): שני קונטיינרים ירוצו מקובץ compose אחד.
  • פרק 4, סעיף 4.5 (עטיפת שגיאות) וסעיף 4.7 (generics): העוזר הגנרי של הפרק בנוי על שניהם.
  • פרק 5, סעיפים 5.4 ו־5.5 (context ו־WaitGroup), וסעיף 5.8 (-race): הבדיקות מריצות עשרות goroutines.
  • פרק 10, סעיף 10.7 (pgx ו־pgxpool): התרגיל כולל מאגר מוצרים קטן משלו, שמשקף את טבלת products ואת ה־repository מפרק 10. הוא עצמאי, ולא מייבא דבר מהתרגיל של פרק 10.
  • לא צריך redis-cli מותקן: הוא רץ בתוך הקונטיינר.

12.1 Redis בקונטיינר ומבני הנתונים

Redis הוא שרת מבני נתונים בזיכרון: מפתח הוא מחרוזת, והערך הוא מחרוזת, hash, רשימה, קבוצה או קבוצה ממוינת. כל פקודה רצה עד סופה לפני שהבאה מתחילה, ולכן כל פקודה בודדת היא אטומית. זו התכונה החשובה ביותר שלו בפרק הזה, יותר מהמהירות.

בסקר המודעות של הספר Redis הופיע במפורש בחמש מתוך 30 מודעות בלבד. מנגד, אתרי הכנה לראיונות מציינים „מטמון LRU עם TTL” ו„מגביל קצב” כשאלות קוד נפוצות בסבבי backend, אם כי בביטחון נמוך עד בינוני. המקור: סעיפים 1.4 ו־3.2 בקובץ 00-stage1/01-market-research.md.

12.1.1 הקונטיינרים

התרגיל מביא קובץ compose עם PostgreSQL ו־Redis. זה החלק של Redis, מהקובץ data/compose.yaml:

  cache:
    image: redis:8.10.2
    # A cache, not a database: a memory limit, an eviction policy, and no persistence.
    command: ["redis-server", "--maxmemory", "64mb", "--maxmemory-policy", "allkeys-lru", "--save", "", "--appendonly", "no"]
    ports:
      - "127.0.0.1:6312:6379"

שלוש ההחלטות שבשורת הפקודה הן החלטות של מטמון, לא של מסד נתונים: תקרת זיכרון, מדיניות שאומרת מה לזרוק כשמגיעים אליה, ובלי כתיבה לדיסק. סעיף 12.3 חוזר אליהן. הגרסה מקובעת בקובץ, נכון לאוקטובר 2026 (ראי נספח ג). מפעילים מתוך תיקיית הפרק, ופותחים את הלקוח של Redis בתוך הקונטיינר:

cd ~/senior-course/ch12
docker compose -p ch12 -f data/compose.yaml up -d --wait
docker compose -p ch12 -f data/compose.yaml exec cache redis-cli

12.1.2 מחרוזות, TTL ו־INCR

מחרוזת היא מבנה הנתונים של המטמון: ערך אחד, בדרך כלל JSON, עם זמן חיים (TTL). הקלידי בתוך redis-cli:

127.0.0.1:6379> SET product:42 hello EX 60
OK
127.0.0.1:6379> GET product:42
"hello"
127.0.0.1:6379> TTL product:42
(integer) 60
127.0.0.1:6379> GET product:43
(nil)
127.0.0.1:6379> INCR views:42
(integer) 1
127.0.0.1:6379> INCR views:42
(integer) 2

האפשרות EX 60 קובעת זמן חיים בשניות, ו־PX במילישניות. מפתח שאין לו ערך מחזיר (nil), ומ־Go זו תהיה שגיאה מיוחדת. הפקודה INCR יוצרת מונה מאפס אם אינו קיים ומגדילה אותו באחד, בפקודה אחת.

12.1.3 SET NX PX: מפתח שרק אחד מקבל

האפשרות NX פירושה „כתבי רק אם המפתח לא קיים”. יחד עם PX זו נעילה פשוטה עם תפוגה:

127.0.0.1:6379> SET lock:product:42 worker-a NX PX 5000
OK
127.0.0.1:6379> SET lock:product:42 worker-b NX PX 5000
(nil)
127.0.0.1:6379> PTTL lock:product:42
(integer) 4714

הראשונה קיבלה את המפתח, והשנייה קיבלה (nil) כי הוא כבר קיים. אם מחזיקת המפתח קורסת, התפוגה משחררת אותו אחרי חמש שניות. נשתמש בזה בסעיף 12.4, ופרק 18 ידון במה שנעילה כזו לא מבטיחה.

12.1.4 hash וקבוצה ממוינת

שני מבנים נוספים שתפגשי בכל שירות:

127.0.0.1:6379> HSET product:42:h name Lamp price_cents 1554
(integer) 2
127.0.0.1:6379> HGET product:42:h price_cents
"1554"
127.0.0.1:6379> ZINCRBY top:views 3 product:42
"3"
127.0.0.1:6379> ZINCRBY top:views 5 product:7
"5"
127.0.0.1:6379> ZINCRBY top:views 1 product:42
"4"
127.0.0.1:6379> ZREVRANGE top:views 0 -1 WITHSCORES
1) "product:7"
2) "5"
3) "product:42"
4) "4"
מבנה פקודות שימוש טיפוסי ב־backend
מחרוזת SET, GET, INCR ערך שמור ב־JSON, מונה, נעילה
hash HSET, HGET, HINCRBY אובייקט שמעדכנים שדה אחד שלו, מונים לפי שדה
קבוצה ממוינת ZADD, ZINCRBY, ZREVRANGE דירוג, „עשרת הנצפים”, חלון זמן לפי ציון
רשימה LPUSH, RPOP תור פשוט; בפרק 13 תראי למה Kafka מתאים יותר

המטמון של הפרק שומר את המוצר כמחרוזת JSON אחת. hash מתאים כשמעדכנים שדה בודד, אבל בשביל מטמון שנמחק בכל כתיבה, מחרוזת אחת פשוטה יותר. יוצאים מהלקוח עם exit.

12.1.5 go-redis

הספרייה שמדברת עם Redis מ־Go היא go-redis, והגרסה שלה מקובעת בקובץ המודול של התרגיל. הלקוח מחזיק pool של חיבורים, בדיוק כמו pgxpool מפרק 10, ולכן יוצרים אחד לתהליך ומשתפים אותו. ההחלטה המעניינת היא מפתח חסר: go-redis מחזירה אותו כשגיאה בשם redis.Nil. בקובץ internal/cache/redis.go היא הופכת לשגיאה שלנו:

func (s *RedisStore) Get(ctx context.Context, key string) ([]byte, error) {
    b, err := s.rdb.Get(ctx, key).Bytes()
    if errors.Is(err, redis.Nil) {
        return nil, ErrMiss
    }
    return b, err
}

איך Rust עושה את זה: שם היית מבקשת מהספרייה ערך אופציונלי, Option<Vec<u8>>, ומפתח חסר היה פשוט None: ערך, לא שגיאה. ב־Go „לא נמצא” הוא ערך שגיאה מוסכם שבודקים עם errors.Is. ההבדל חשוב: פספוס הוא מצב רגיל של מטמון, ושגיאה אמיתית (Redis לא עונה) מחייבת התנהגות אחרת לגמרי.

12.2 cache-aside

12.2.1 מסלול הקריאה

בדפוס cache-aside האפליקציה, לא המטמון, אחראית על הכול. בקריאה: לחפש במטמון; בפגיעה (hit) להחזיר; בפספוס (miss) לקרוא מהמסד, לשמור במטמון עם TTL, ולהחזיר. המטמון לא יודע שהמסד קיים. זה הדפוס הנפוץ ביותר, כי הוא עובד מול כל מסד ולא דורש מהמטמון שום היגיון.

זה מסלול הקריאה מהקובץ productcache.go, הגרסה שתכתבי ביד ביום הראשון:

func (c *ProductCache) Get(ctx context.Context, id int64) (Product, error) {
    key := ProductKey(c.prefix, id)
    raw, err := c.rdb.Get(ctx, key).Bytes()
    switch {
    case err == nil:
        var p Product
        if json.Unmarshal(raw, &p) == nil {
            return p, nil // hit
        }
        // An entry we cannot decode is treated as a miss and overwritten below.
    case errors.Is(err, redis.Nil):
        // miss
    default:
        // Redis is down or slow: serve from the database and do not try to fill.
        return c.store.GetProduct(ctx, id)
    }

    p, err := c.store.GetProduct(ctx, id)
    if err != nil {
        return Product{}, err // not-found is not cached: see section 12.6
    }
    if raw, err := json.Marshal(p); err == nil {
        // A failed fill is not a failed read: the next reader simply misses again.
        _ = c.rdb.Set(ctx, key, raw, cache.Jittered(c.ttl, c.jitter)).Err()
    }
    return p, nil
}

שלוש החלטות בקוד הזה, וכל אחת שווה שאלה בראיון:

  • Redis שלא עונה אינו סיבה להיכשל. הקריאה עוברת ישר למסד. המטמון הוא אופטימיזציה, והשירות צריך לעבוד בלעדיו, גם אם לאט יותר.
  • כתיבה שנכשלה למטמון אינה קריאה שנכשלה. המשתמשת קיבלה את המוצר; הקוראת הבאה פשוט תפספס שוב.
  • ערך שאי אפשר לפענח הוא פספוס. זה קורה אחרי פריסה ששינתה את מבנה ה־struct. הערך הישן נדרס, ולא מפיל את הבקשה.

12.2.2 מסלול הכתיבה: למחוק, לא לעדכן

בכתיבה יש שתי אפשרויות: לעדכן את הערך במטמון, או למחוק אותו ולתת לקריאה הבאה למלא. cache-aside מוחק, משלוש סיבות:

  • שני כותבים במקביל. כותבת א' מעדכנת את המסד למחיר 10, כותבת ב' למחיר 20. אם כל אחת גם כותבת למטמון, הסדר ביניהן במטמון יכול להתהפך, ואז המסד אומר 20 והמטמון אומר 10 עד סוף ה־TTL. מחיקה היא פעולה שאין לה סדר: שתי מחיקות משאירות את אותו מצב.
  • הצורה השמורה מחושבת. ערך במטמון הוא לעתים קרובות צירוף של כמה טבלאות. מי שכותבת שורה אחת לא תמיד יודעת לבנות אותו.
  • עצלות. מוצר שמתעדכן מאה פעמים ונקרא פעם אחת לא צריך מאה כתיבות למטמון.

זה מסלול הכתיבה מאותו קובץ:

func (c *ProductCache) UpdatePrice(ctx context.Context, id, priceCents int64) error {
    if err := c.store.UpdatePrice(ctx, id, priceCents); err != nil {
        return err
    }
    // After the commit, never before: a delete inside the transaction lets a reader
    // refill the old row before the commit makes the new one visible.
    if err := c.rdb.Del(ctx, ProductKey(c.prefix, id)).Err(); err != nil {
        return fmt.Errorf("price of %d updated, but invalidation failed (the TTL will expire it): %w", id, err)
    }
    return nil
}

12.2.3 למה אחרי ה־commit

הפונקציה UpdatePrice של המאגר עוטפת את העדכון בטרנזקציה, וכשהיא מחזירה nil השינוי כבר מחויב. נניח שהיינו מוחקים מהמטמון לפני כן, בתוך הטרנזקציה. בין המחיקה ל־commit השורה החדשה עדיין לא נראית לאף אחד (פרק 11 מסביר למה). קוראת שמגיעה בדיוק אז מפספסת, קוראת מהמסד את המחיר הישן, וממלאת בו את המטמון. ה־commit מגיע, ואיש כבר לא מוחק: הערך הישן יחיה עד סוף ה־TTL.

אחרי ה־commit, כל קוראת שמפספסת רואה את השורה החדשה. נשאר מקרה אחד, עדין יותר, וסעיף 12.3.2 עוסק בו. ומה אם המחיקה עצמה נכשלת? השינוי במסד כבר קרה, ולכן הפונקציה מחזירה שגיאה שאומרת בדיוק את זה, וה־TTL הוא רשת הביטחון.

12.2.4 דפוסים אחרים, בקצרה

דפוס מי ממלא את המטמון מה מקבלים מה משלמים
cache-aside האפליקציה, בפספוס פשוט, עובד מול כל מסד פספוס ראשון איטי, חלון של ערך ישן
read-through ספריית המטמון, בפספוס קוד קורא נקי המטמון צריך לדעת לטעון
write-through הכותבת, למטמון ולמסד יחד קריאה טרייה מיד כל כתיבה איטית יותר, ערכים שאיש לא קורא
write-behind המטמון, למסד באיחור כתיבות מהירות מאוד אובדן נתונים אם המטמון נופל לפני הכתיבה

העוזר שתבני ביום השני הוא בעצם read-through קטן: הקוראת מוסרת לו פונקציית טעינה, והוא מחליט מתי לקרוא לה.

12.3 TTL, פינוי ואי־תוקף

12.3.1 TTL הוא רשת הביטחון

אי־תוקף (invalidation) מפורש מטפל במקרה הרגיל. ה־TTL מטפל בכל השאר: מחיקה שנכשלה, כותבת שעוקפת את הקוד שלך (מיגרציה, תיקון ידני ב־psql), ומרוץ שעוד רגע תראי. בלי TTL, כל אחד מאלה משאיר ערך שגוי לתמיד. ה־TTL הוא גם החוזה מול המוצר: „מחיר יכול להיות ישן עד דקה” הוא משפט שמישהי צריכה לאשר.

12.3.2 המרוץ בין קריאה ישנה לאי־תוקף

גם כשמוחקים אחרי ה־commit יש חלון אחד. קוראת מפספסת ומתחילה לקרוא מהמסד. באמצע, כותבת מחייבת מחיר חדש ומוחקת את המפתח, שעוד לא קיים. ואז הקוראת, עם השורה הישנה בידיה, ממלאת את המטמון:

sequenceDiagram
    participant R as Reader
    participant C as Redis
    participant DB as PostgreSQL
    participant W as Writer
    R->>C: GET (miss)
    R->>DB: SELECT (old price)
    W->>DB: UPDATE, COMMIT (new price)
    W->>C: DEL (nothing to delete)
    R->>C: SET old price, TTL
    Note over C: stale until the TTL expires

הבדיקה TestStaleFillIsBoundedByTTL בקובץ internal/cache/cache_test.go משחזרת את הרצף צעד אחר צעד, עם ערוצים במקום תזמון מזל. זה הלב שלה:

    <-read
    source.Store("new")                            // 2a. the writer commits
    if err := c.Invalidate(ctx, key); err != nil { // 2b. and invalidates: nothing to delete yet
        t.Fatal(err)
    }
    close(release)
    if v := <-done; v != "old" {
        t.Fatalf("slow reader returned %q, want old", v)
    }

    fresh := func(context.Context) (string, error) { return source.Load().(string), nil }
    if v, _ := c.Get(ctx, key, fresh); v != "old" {
        t.Fatalf("right after the race Get = %q, want the stale old", v)
    }
    time.Sleep(ttl + 100*time.Millisecond)
    if v, _ := c.Get(ctx, key, fresh); v != "new" {
        t.Errorf("after the TTL Get = %q, want new", v)
    }

החלון צר: הקוראת צריכה להתחיל לפני הכתיבה ולסיים אחריה, ובמערכת אמיתית זה נדיר. אבל „נדיר” במיליון בקשות ביום הוא „כמה פעמים ביום”. אין כאן תיקון פשוט; יש גבול: ה־TTL קובע כמה זמן הערך השגוי יכול לחיות. לכן ה־TTL נבחר לפי כמה התיישנות מותרת, לא לפי כמה זיכרון יש. מי שצריכה יותר מזה משתמשת בגרסה בתוך הערך, או לא שמה מטמון (סעיף 12.6).

שימי לב: מחיקה כפולה (delayed double delete) היא תיקון שתמצאי ברשת: למחוק שוב כמה מאות מילישניות אחרי הכתיבה. היא מצמצמת את החלון, לא סוגרת אותו, ומוסיפה עבודת רקע. ה־TTL עדיין נדרש.

12.3.3 פיזור אקראי ב־TTL

אם אלף מפתחות נטענו יחד, למשל אחרי פריסה שהתחילה עם מטמון ריק, ולכולם TTL של דקה בדיוק, הם יפוגו יחד בעוד דקה. כל הפספוסים יגיעו למסד באותה שנייה. התיקון הוא פיזור אקראי (jitter) קטן לכל TTL. מהקובץ internal/cache/ttl.go:

func Jittered(base, jitter time.Duration) time.Duration {
    if jitter <= 0 {
        return base
    }
    return base + rand.N(jitter)
}

הפונקציה rand.N מהחבילה math/rand/v2 גנרית, ולכן היא מקבלת time.Duration ישירות. בתרגיל ה־TTL הוא דקה עם עד עשר שניות פיזור, והבדיקה TestTTLIsSetWithJitter קוראת את הזמן שנשאר עם PTTL ומוודאת שהוא בטווח.

12.3.4 פינוי: מה קורה כשהזיכרון נגמר

הפקודה maxmemory קובעת תקרה, ו־maxmemory-policy קובעת מה לזרוק כשמגיעים אליה. לפי התיעוד של Redis בעמוד „Key eviction”, נכון לאוקטובר 2026, אלה המדיניות:

מדיניות מה נזרק
noeviction שום דבר: פקודות שמוסיפות נתונים נכשלות בשגיאה, קריאות ממשיכות
allkeys-lru המפתח שלא נגעו בו הכי הרבה זמן, מכל המפתחות
allkeys-lfu המפתח שנקרא הכי מעט, לפי מונה תדירות שדועך עם הזמן
allkeys-lrm המפתח שלא נכתב הכי הרבה זמן (חדש ב־Redis 8.6)
allkeys-random מפתח אקראי
volatile-lru, volatile-lfu, volatile-lrm, volatile-random כמו הקודמות, רק מבין המפתחות שיש להם TTL
volatile-ttl המפתח עם ה־TTL הקצר ביותר שנשאר

ברירת המחדל היא noeviction, ובדקתי אותה על ה־image המקובע. זו ברירת מחדל נכונה למסד נתונים ושגויה למטמון: כשהזיכרון מתמלא, כל SET נכשל. לכן קובץ ה־compose קובע allkeys-lru, שהתיעוד ממליץ עליה כברירת מחדל כשחלק קטן מהמפתחות נקרא הרבה יותר מהשאר. מדיניות volatile מתנהגת כמו noeviction כשלאף מפתח אין TTL, מלכודת קלאסית.

שני פרטים מהתיעוד ששווה לזכור. ה־LRU של Redis מקורב: הוא דוגם כמה מפתחות אקראיים (maxmemory-samples, ברירת מחדל 5) וזורק את הישן מביניהם. ובשירות שמשמש גם כמטמון וגם כמאגר של מפתחות שאסור לאבד, התיעוד ממליץ על שני שרתים נפרדים ולא על מדיניות volatile.

12.3.5 יחס פגיעות

מטמון בלי מדידה הוא ניחוש. Redis סופר פגיעות ופספוסים בכל השרת:

docker compose -p ch12 -f data/compose.yaml exec cache redis-cli INFO stats | grep -E 'keyspace_(hits|misses)|evicted_keys'

יחס הפגיעות הוא פגיעות חלקי סך הבדיקות. אבל המספר הזה כולל את כל המפתחות של כל השירותים, ולכן העוזר של התרגיל סופר גם בעצמו, לכל סוג ערך. מהקובץ internal/cache/cache.go:

func (s Stats) HitRatio() float64 {
    if total := s.Hits + s.Misses; total > 0 {
        return float64(s.Hits) / float64(total)
    }
    return 0
}

בפרק 24 המונים האלה יהפכו למדדים ב־Prometheus. כשהיחס נמוך, בדקי קודם את evicted_keys: הרבה פינויים אומרים שהמטמון קטן מדי או שהמדיניות לא מתאימה; מעט פינויים והרבה פספוסים אומרים שה־TTL קצר מדי או שהגישה פשוט לא חוזרת על עצמה.

12.4 התפרצות מטמון ו־singleflight

12.4.1 מה זה

התפרצות מטמון (cache stampede) קורית כשמפתח חם חסר, כי פג או כי השירות רק עלה, והרבה בקשות מגיעות אליו בבת אחת. כולן מפספסות, וכולן שולחות את אותה שאילתה למסד. השאילתה האיטית ביותר שלך רצה פתאום חמישים פעם במקביל, בדיוק ברגע שהמסד הכי עמוס. מכאן גם השם השני, „thundering herd”.

12.4.2 למדוד

התוכנית cmd/stampede בתרגיל משחררת N קוראות יחד על מפתח קר, פעם דרך הגרסה הידנית ופעם דרך העוזר. המאגר סופר כל קריאה שלו, ובכל קריאה הוא מוסיף pg_sleep שמדמה שאילתה של 200 מילישניות. מריצים:

export DATABASE_URL=postgres://course:change-me@localhost:5412/catalog
export REDIS_ADDR=localhost:6312
go run ./cmd/stampede

הפלט במכונה שעליה נכתב התרגיל היה כזה. מספר הקריאות לא אמור להשתנות אצלך, והזמנים כן:

cold key, 50 concurrent readers, 200ms per query
without singleflight:   50 database calls, 1.041s
with singleflight:       1 database calls, 204ms
helper stats: hits 50, misses 50, loads 1, hit ratio 0.50

חמישים קוראות, חמישים שאילתות. ושימי לב לזמן: ה־pool מוגבל לעשרה חיבורים (כמו בפרק 10), ולכן חמישים השאילתות רצו בחמישה גלים, והאחרונה חיכתה שנייה שלמה. התפרצות לא רק מעמיסה על המסד, היא גם מאריכה את זמן התגובה בזנב (p99) של כל מי שבתור. תריצי ותרשמי את המספרים שלך בפתק.

12.4.3 singleflight

החבילה golang.org/x/sync/singleflight עושה דבר אחד: לכל מפתח, רק קריאה אחת לפונקציה רצה בכל רגע. מי שמגיעה בזמן שהקריאה רצה מחכה ומקבלת את אותה תוצאה. זה מסלול הקריאה של העוזר, מהקובץ internal/cache/cache.go:

func (c *Cache[T]) Get(ctx context.Context, key string, load func(context.Context) (T, error)) (T, error) {
    raw, err := c.store.Get(ctx, key)
    if err == nil {
        var v T
        if json.Unmarshal(raw, &v) == nil {
            c.hits.Add(1)
            return v, nil
        }
    } else if !errors.Is(err, ErrMiss) {
        c.errored.Add(1)
    }
    c.misses.Add(1)

    // Do runs the function once per key at a time; callers that arrive while it runs
    // wait and receive the same result. The context is the first caller's.
    v, err, _ := c.group.Do(key, func() (any, error) {
        c.loads.Add(1)
        v, err := load(ctx)
        if err != nil {
            return v, err
        }
        if raw, err := json.Marshal(v); err == nil {
            // Fill before returning, so a reader that misses after this flight ends
            // finds the value instead of starting a new flight.
            _ = c.store.Set(ctx, key, raw, Jittered(c.opts.TTL, c.opts.Jitter))
        }
        return v, nil
    })
    if err != nil {
        var zero T
        return zero, err
    }
    return v.(T), nil
}

הסדר בתוך הפונקציה שמועברת ל־Do חשוב: המילוי למטמון קורה לפני שהטיסה (flight) נגמרת. אם היה קורה אחריה, קוראת שמפספסת ברגע שבין הסוף למילוי הייתה פותחת טיסה שנייה. ה־API של singleflight קודם ל־generics, ולכן התוצאה חוזרת כ־any ומומרת חזרה עם v.(T). הגרסה מקובעת בקובץ go.mod של התרגיל.

איך Rust עושה את זה: אין בספרייה הסטנדרטית מקבילה מוכנה. היית בונה את זה בעצמך: מילון ממפתח ל־future משותף, מאחורי נעילה. הספרייה futures נותנת לשם כך את Shared. ב־Go זה שלושים שורות בספרייה של צוות Go, וכל מי שקוראת את הקוד שלך מכירה אותן.

12.4.4 מה singleflight לא פותר

  • תהליכים אחרים. הקבוצה חיה בזיכרון של תהליך אחד. עשרה replicas של השירות יריצו עשר שאילתות, אחת לכל replica. זה כבר עשר במקום חמש מאות, ולעתים קרובות זה מספיק.
  • ה־context של הראשונה. כל הממתינות תלויות ב־context של מי שפתחה את הטיסה. אם הוא בוטל, כולן מקבלות את השגיאה, גם אם להן היה זמן. אפשר לטעון עם context.WithoutCancel וזמן קצוב משלך; זו פשרה, והעוזר משאיר אותה פשוטה.
  • שגיאות משותפות. כשהטעינה נכשלת, כל הממתינות נכשלות יחד. העוזר לא שומר שגיאה במטמון, ולכן הקוראת הבאה מנסה שוב.
  • מפתח שאינו חם. אם כל בקשה מבקשת מפתח אחר, אין מה לאחד.

12.4.5 בין תהליכים: מפתח נעילה ורענון מוקדם

כשגם שאילתה אחת לכל replica היא יותר מדי, יש שתי דרכים מוכרות, ושתיהן נשארות בפרק כפרוזה:

  • מפתח נעילה. בפספוס, הקוראת מנסה SET lock:<key> <id> NX PX <ms> מסעיף 12.1.3. מי שקיבלה את המפתח טוענת וממלאת; האחרות מחכות קצת וקוראות שוב מהמטמון, או מחזירות ערך ישן אם שמרו אחד. המחיר: המתנה, ותפוגה שצריכה להיות ארוכה מהטעינה, אחרת שתיים טוענות בכל זאת.
  • רענון מוקדם. במקום לחכות שהמפתח יפוג, קוראת שרואה שנשאר לו מעט זמן מרעננת אותו ברקע בהסתברות שגדלה ככל שהתפוגה קרובה. המפתח החם כמעט אף פעם לא חסר, ואין רגע שבו כולן מפספסות. הגרסה המוכרת של הרעיון נקראת XFetch, והיא מקושרת בהעשרה.

12.5 מונים ופעולות אטומיות

12.5.1 INCR מול „קרא ואז כתוב”

מונה צפיות נראה כמו GET, הוספת אחד, ו־SET. בשתי קוראות במקביל שתיהן קוראות 41 ושתיהן כותבות 42: עדכון אחד אבד. זה אותו מרוץ מפרק 5, רק בין תהליכים, ולכן -race לא יראה אותו. הפקודה INCR עושה את שלושת הצעדים בתוך השרת, בפקודה אחת, ושום פקודה אחרת לא נכנסת באמצע. מהקובץ counters.go:

func IncrViews(ctx context.Context, rdb redis.Cmdable, prefix string, id int64) (int64, error) {
    return rdb.Incr(ctx, fmt.Sprintf("%sviews:%d", prefix, id)).Result()
}

הבדיקה TestIncrViewsIsAtomic מריצה מאתיים goroutines ומצפה למונה 200 בדיוק.

12.5.2 כמה פקודות כפעולה אחת: Lua

מגביל קצב בחלון קבוע צריך שני צעדים: להגדיל מונה, ובפעם הראשונה בחלון לקבוע לו תפוגה. בשתי פקודות נפרדות, תהליך שקורס ביניהן משאיר מונה בלי TTL, והלקוח נחסם לתמיד. סקריפט Lua רץ בתוך Redis כפקודה אחת, ולכן אי אפשר להפריד בין הצעדים. מאותו קובץ:

var fixedWindow = redis.NewScript(`
local n = redis.call('INCR', KEYS[1])
if n == 1 then
  redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
return n
`)

// Allow is a fixed-window rate limiter, a preview of chapter 16: at most limit
// calls per window for key, counted in Redis so that every replica shares it.
func Allow(ctx context.Context, rdb redis.Scripter, key string, limit int64, window time.Duration) (bool, error) {
    n, err := fixedWindow.Run(ctx, rdb, []string{key}, window.Milliseconds()).Int64()
    if err != nil {
        return false, fmt.Errorf("rate limit %s: %w", key, err)
    }
    return n <= limit, nil
}

המפתחות עוברים ב־KEYS והערכים ב־ARGV, ולא נבנים לתוך מחרוזת הסקריפט: כך הסקריפט קבוע, ו־Redis שומר אותו לפי הגיבוב שלו. לפי התיעוד של go-redis, Run שולחת קודם EVALSHA עם הגיבוב, ורק אם השרת לא מכיר אותו שולחת את הסקריפט המלא. שימי לב גם לממשקים הקטנים בחתימות: redis.Cmdable ו־redis.Scripter במקום הלקוח עצמו.

סקריפט חוסם את כל השרת בזמן שהוא רץ, ולכן הוא צריך להיות קצר: כמה פקודות, בלי לולאות על אוספים גדולים. פרק 16 בונה על זה מגביל קצב אמיתי. חסרון אחד של חלון קבוע כבר רואים מכאן: לקוח יכול לשלוח את כל המכסה בסוף חלון אחד ושוב בתחילת הבא, כלומר פי שניים בזמן קצר.

12.6 מתי לא לשים מטמון

מטמון הוא מקור אמת שני, ולכן כל מטמון צריך להצדיק את עצמו במספרים. המקרים שבהם הוא מזיק:

  • הרבה כתיבות, מעט קריאות. כל כתיבה מוחקת, ואף ערך לא חי מספיק זמן כדי שיקראו אותו. משלמים על מסלול נוסף ולא מקבלים פגיעות.
  • עקביות חזקה. יתרה בחשבון, מלאי לפני תשלום, הרשאות שבוטלו: ערך ישן הוא באג, לא פשרה. כאן קוראים מהמסד, ומשפרים את השאילתה (פרק 10) במקום להסתיר אותה.
  • יחס פגיעות נמוך. כשהגישה מפוזרת על מיליוני מפתחות שכל אחד נקרא פעם אחת, כל בקשה משלמת על פספוס ועל מילוי, ומקבלת זמן תגובה גרוע מבלי מטמון. מודדים את היחס עם Stats ועם INFO stats לפני שמחליטים.
  • המקור כבר זול. שאילתה של מילישנייה לפי מפתח ראשי לא צריכה מטמון ברשת שעולה בערך אותו דבר.
  • המטמון מסתיר עומס שהמסד לא יעמוד בו. אם Redis נופל, כל התנועה עוברת למסד. העוזר של התרגיל עושה בדיוק את זה (הבדיקה TestStoreDownFallsBackToSource), וזו הבחירה הנכונה רק אם המסד מסוגל לשאת את זה. אחרת צריך גם הגבלה של מקביליות מול המסד, נושא של פרק 16.

ועוד החלטה אחת שהקוד של הפרק מקבל במכוון: „לא נמצא” לא נשמר. זה פשוט ונכון, אבל תוקפת שמבקשת מיליון מזהים שלא קיימים עוקפת את המטמון לגמרי. ההגנה היא מטמון שלילי (negative caching): לשמור „אין כזה” עם TTL קצר מאוד. זו העשרה, לא ברירת מחדל, כי היא מוסיפה עוד חלון של ערך ישן למוצר שנוצר הרגע.

הפרויקט המסכם, Hookline, ישתמש בעוזר הזה כמו שהוא בשלב M3: מטמון ל„אילו מנויים מעוניינים באירוע הזה”, שאלה שכל אירוע שואל ושמשתנה רק כשמנוי נוצר או נמחק. ראי פרק 38.

סיכום

  • Redis מריץ כל פקודה עד סופה, ולכן כל פקודה בודדת אטומית; סקריפט Lua הופך כמה פקודות לאחת.
  • במטמון cache-aside האפליקציה קוראת מהמטמון, ובפספוס טוענת מהמסד וממלאת עם TTL.
  • בכתיבה מוחקים ולא מעדכנים, ומוחקים אחרי ה־commit. מחיקה לפניו ממלאת את המטמון בערך הישן.
  • גם אחרי ה־commit נשאר מרוץ בין קריאה איטית למחיקה; ה־TTL הוא מה שחוסם אותו.
  • פיזור אקראי ב־TTL מונע תפוגה המונית, ומדיניות פינוי מתאימה מונעת כשלי כתיבה כשהזיכרון מלא.
  • התפרצות מטמון נמדדת במספר הקריאות למסד; singleflight מאחד אותן לאחת בכל תהליך.
  • מטמון צריך להצדיק את עצמו ביחס פגיעות מדוד, ושירות צריך לעבוד גם כש־Redis לא עונה.

טעויות נפוצות

  • למחוק מהמטמון לפני ה־commit, או בתוך הטרנזקציה. קוראת ממלאת בינתיים את הערך הישן. מחקי אחרי שהטרנזקציה החזירה הצלחה.
  • לעדכן את המטמון בכתיבה במקום למחוק. שני כותבים יכולים להשאיר את הישן אחרון. מחקי.
  • מפתח בלי TTL. כל באג באי־תוקף הופך לערך שגוי לתמיד. לכל מפתח מטמון יש TTL.
  • להשאיר את ברירת המחדל noeviction בשרת מטמון. כשהזיכרון מתמלא כל SET נכשל. קבעי allkeys-lru או מדיניות אחרת במודע.
  • להחזיר שגיאה כש־Redis לא עונה. המטמון הפך לנקודת כשל. קראי מהמסד.
  • לשמור שגיאה במטמון. תקלה רגעית במסד הופכת לתשובה שגויה לכל משך ה־TTL.
  • להניח ש־singleflight מגן על כל הצי. הוא מאחד בתוך תהליך אחד בלבד.

שאלות ראיון

  1. מה ההבדל בין cache-aside ל־write-through, ומתי תבחרי בכל אחד? ב־cache-aside האפליקציה טוענת בפספוס ומוחקת בכתיבה, ולכן המטמון מכיל רק מה שנקרא, והוא עובד מול כל מסד. המחיר הוא פספוס ראשון איטי וחלון קצר של ערך ישן. ב־write-through כל כתיבה מעדכנת גם את המטמון, כך שקריאה אחרי כתיבה טרייה מיד, אבל כל כתיבה איטית יותר, והמטמון מתמלא בערכים שאולי איש לא יקרא. ברוב שירותי הקריאה cache-aside הוא ברירת המחדל; write-through מתאים כשקריאה מיד אחרי כתיבה נפוצה וחייבת להיות טרייה.

  2. למה מוחקים מהמטמון אחרי הכתיבה ולא לפניה, ומה עדיין יכול להשתבש? מחיקה לפני ה־commit משאירה חלון שבו קוראת מפספסת, קוראת את השורה הישנה (החדשה עוד לא נראית) וממלאת אותה. אחרי ה־commit כל פספוס רואה את החדשה. עדיין יכולה קוראת שהתחילה לפני הכתיבה לסיים אחרי המחיקה ולמלא ערך ישן. אין לזה תיקון זול, ולכן ה־TTL הוא החסם, ונבחר לפי כמה התיישנות המוצר מוכן לקבל.

המשך: ואם המחיקה עצמה נכשלת? השינוי במסד כבר קרה, אז מחזירים שגיאה שאומרת זאת ומסתמכים על ה־TTL. מי שצריכה ערבות חזקה יותר כותבת את האי־תוקף כאירוע ב־outbox (פרק 13) ומוחקת ממנו.

  1. מה זו התפרצות מטמון, ואיך מטפלים בה? מפתח חם חסר, והרבה בקשות מפספסות יחד ושולחות את אותה שאילתה. בתוך תהליך, singleflight מאחד אותן לקריאה אחת, ובתרגיל חמישים קריאות ירדו לאחת. בין תהליכים: מפתח נעילה עם SET NX PX, שבו רק אחת טוענת והאחרות מחכות או מקבלות ערך ישן, או רענון מוקדם הסתברותי שמונע מהמפתח להיעלם בכלל. וגם פיזור אקראי ב־TTL, כדי שהרבה מפתחות לא יפוגו יחד.

המשך: מה החיסרון של singleflight? כולן תלויות ב־context ובשגיאה של הראשונה: אם היא בוטלה, כולן נכשלות. אפשר לטעון עם context מנותק וזמן קצוב משלו, במחיר טעינה שממשיכה גם כשאף אחת כבר לא מחכה.

  1. איך תחליטי אם בכלל לשים מטמון? קודם מודדים: כמה עולה השאילתה, כמה פעמים אותו מפתח נקרא בתוך חלון ה־TTL, וכמה התיישנות מותרת. מטמון משתלם כשהקריאות חוזרות, המקור יקר, והתיישנות קצרה מקובלת. הוא מזיק כשהכתיבות רבות, כשהעקביות חייבת להיות חזקה, וכשיחס הפגיעות נמוך. אחרי שמוסיפים אותו, ממשיכים למדוד את יחס הפגיעות ואת הפינויים, ומוכנים להוריד אותו.

  2. למה INCR ולא קריאה ואחריה כתיבה, ומתי צריך סקריפט Lua? קריאה וכתיבה נפרדות הן שתי פקודות, וקוראת אחרת יכולה להיכנס ביניהן, כך שעדכונים אובדים. INCR עושה את הכול בפקודה אחת בשרת. כשצריך כמה פקודות כפעולה אחת, למשל הגדלה ותפוגה במגביל קצב, סקריפט Lua רץ כפקודה אחת. המחיר: הוא חוסם את כל השרת בזמן הריצה, ולכן הוא חייב להיות קצר.

קריטריון סיום:

  • בדיקה מראה פספוס ואחריו פגיעה, וכתיבה שמוחקת את הערך השמור.
  • הבדיקה של המרוץ מראה ערך ישן אחרי המרוץ וערך חדש אחרי ה־TTL.
  • הפלט של cmd/stampede מהריצה שלך רשום בפתק, בלי singleflight ועם.

העשרה אופציונלית

  • בתיעוד של Redis, העמוד „Key eviction” מפרט את כל מדיניות הפינוי. הוא מסביר גם איך כל אלגוריתם מקורב, ואילו פרמטרים אפשר לכוונן.
  • הרענון המוקדם ההסתברותי מסעיף 12.4.5 מתואר במאמר „Optimal Probabilistic Cache Stampede Prevention”, שפורסם בכתב העת PVLDB, כרך 8. נסי לממש אותו מעל העוזר: לשמור לצד הערך את זמן הטעינה.
  • הוסיפי מטמון שלילי לעוזר: ערך „לא נמצא” עם TTL של כמה שניות, ובדיקה שמראה שבקשה שנייה למזהה חסר לא מגיעה למסד.
  • הריצי את ההדגמה עם הדגל -n 500, ואחר כך עם -latency 1s. ראי מה קורה לזמן של הגרסה הידנית כשכל החיבורים תפוסים.
