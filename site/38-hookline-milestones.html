פרק 38: אבני הדרך

הפרק הזה הוא מדריך הבנייה של Hookline: עשר אבני דרך, כל אחת בסוף החלק בספר שמלמד את מה שהיא צריכה. כל סעיף הוא תדריך עבודה באותו מבנה: המטרה, המושגים והיכן נלמדו, הצעדים, הקבצים, הבדיקות שצריכות להוריק בפקודות מדויקות, הפלט הצפוי, מתי נגמר, הטעויות הנפוצות, והרחבה. את הפרק לא קוראים ברצף: חוזרים לסעיף של אבן הדרך ביום שלה.

מה נלמד בפרק

  • להפוך את השרת מפרק 6 לשלד של API אמיתי: אימות, משאבים, עימוד ופרטי בעיה, מאחורי ממשקים.
  • להחליף מאגר בזיכרון במאגר PostgreSQL בלי לשנות שורה ב־handlers, ולהוכיח את זה בבדיקות התאמה.
  • לקלוט אירועים באופן אידמפוטנטי, כשאילוץ ייחודיות במסד מכריע בין בקשות מקבילות.
  • לחבר לפרויקט את מה שנלמד בכל חלק: מטמון, outbox ו־Redpanda, תור עבודות, חוסן, קונטיינרים, תצפיתיות ואבטחה.
  • לעבוד מול בדיקות שכבר כתובות, ולדעת מתי אבן דרך באמת נגמרה.

38.1.1 המטרה

‏API שעובד ונבדק, שתואם לחוזה שלו: דיירות שנוצרות בכלי המפעילה ומקבלות מפתח פעם אחת, אימות ב־Bearer, ‏endpoints עם סוד חתימה, מנויים, וקליטת אירועים עם מפתח אידמפוטנטיות. הכול מעל מאגר בזיכרון שיושב מאחורי ממשקים, כך שבאבן הדרך הבאה מחליפים אותו ב־PostgreSQL ולא נוגעים ב־handler אחד.

עכשיו קראי את internal/store/store.go. ארבעת הממשקים הם הגבול: ה־handlers מכירים רק אותם, ושום handler לא יודע אם מאחוריהם יש מפה או מסד. התיעוד של כל מתודה הוא חוזה. במיוחד המתודה של הקליטה:

// Events are ingested once per (tenant, idempotency key).
type Events interface {
    // IngestEvent stores e unless the tenant already used e.IdempotencyKey. Then, with the same
    // BodyHash, it returns the stored event and replayed=true; with another BodyHash it returns
    // domain.ErrIdempotencyMismatch. The decision is atomic: concurrent calls with one key store
    // exactly one event and all return it. The PostgreSQL store also writes the outbox row (M4) in the
    // same transaction.
    IngestEvent(ctx context.Context, e domain.Event) (stored domain.Event, replayed bool, err error)
    GetEvent(ctx context.Context, tenantID, id string) (domain.Event, error)
}

  • השם של הסכמה לא תלוי רישיות. כך מגדיר את זה תקן ה־HTTP. לכן bearer חייב לעבוד כמו Bearer.

  • ‏401 תמיד עם WWW-Authenticate. התקן דורש אותה, והבדיקה בודקת אותה.

בצעד 4 שימי לב לשני דברים. הסוד מוחזר רק בתשובת היצירה. בטיפוס domain.Endpoint השדה Secret מסומן כך שלא יקודד, ותשובת היצירה עוטפת את הטיפוס בטיפוס שמוסיף אותו. ומזהה בנתיב נבדק ב־domain.IsID לפני כל קריאה למאגר: מזהה לא תקין הוא 404, ובאבן הדרך השנייה הוא לא יגיע לעמודת uuid ויהפוך ל־500.

בצעד 6, המאגר בזיכרון צריך להחליט באופן אטומי אם המפתח חדש. מנעול אחד סביב הבדיקה וההכנסה עושה את מה שאילוץ הייחודיות יעשה במסד. זה הקוד מהקובץ internal/store/memory/memory.go:

func (s *Store) IngestEvent(_ context.Context, e domain.Event) (domain.Event, bool, error) {
    s.mu.Lock()
    defer s.mu.Unlock()
    k := idemKey{e.TenantID, e.IdempotencyKey}
    if id, ok := s.byIdemKey[k]; ok {
        stored := s.events[id]
        if stored.BodyHash != e.BodyHash {
            return domain.Event{}, false, domain.ErrIdempotencyMismatch
        }
        return stored, true, nil
    }
    e.Payload = slices.Clone(e.Payload) // the caller's buffer is not ours to keep
    s.events[e.ID] = e
    s.byIdemKey[k] = e.ID
    return e, false, nil
}

ה־handler מחשב את הגיבוב על הבתים הגולמיים של הגוף, לפני הפענוח. כך „אותו גוף” פירושו אותם בתים בדיוק, כמו בפרק 9. שימי לב גם שבניגוד ל־middleware של פרק 9, כאן אין מצב „בתהליך” ואין 409: התשובה נגזרת כולה מהאירוע השמור, והאירוע נוצר באופן אטומי. בקשה מקבילה עם אותו מפתח מחכה ומקבלת את אותו אירוע.

לסיום, הריצי את השרת על המאגר בזיכרון ושלחי אליו בקשות אמיתיות:

השרת מדפיס פעם אחת מפתח של דיירת פיתוח, בשורה כזאת. המזהה והמפתח אצלך יהיו אחרים:

בחלון שני:

curl -s localhost:8080/v1/endpoints -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' -d '{"url":"http://localhost:9000/hooks"}'

הריצי את בקשת האירוע פעמיים, ואז פעם שלישית עם "amount":9900. הראשונה מחזירה 202, השנייה 202 עם Idempotent-Replayed: true ואותו מזהה, והשלישית 422.

38.1.5 הבדיקות שצריכות להוריק

DATABASE_URL= go test -race -skip 'Invalidat|Deliver|Replay|ActiveSubscriptions|RateLimit|OverItsLimit|LimiterFailure|Shed|Trace|PrivateAddress' ./internal/api/ ./internal/store/... ./internal/admin/

ההשמה הריקה של DATABASE_URL מבטיחה שבדיקות ה־API רצות על המאגר בזיכרון, גם אם הגדרת את המשתנה בחלון אחר. הדגל -skip מדלג על הבדיקות של אבני דרך מאוחרות שכבר נמצאות באותן חבילות: המטמון של אבן הדרך השלישית (Invalidat, ‏ActiveSubscriptions), המסירות של החמישית (Deliver, ‏Replay), ההגנות של השישית (RateLimit, ‏Shed ועוד שתיים), והמעקב של השמינית (Trace). כל אבן דרך מורידה ממנו את מה שהיא מממשת.

    err := pgx.BeginTxFunc(ctx, s.pool, pgx.TxOptions{IsoLevel: pgx.ReadCommitted}, func(tx pgx.Tx) error {
        row := tx.QueryRow(ctx, `
            INSERT INTO events (id, tenant_id, type, payload, idempotency_key, body_hash, created_at, trace_context)
            VALUES ($1, $2, $3, $4, $5, $6, $7, NULLIF($8, ''))
            ON CONFLICT (tenant_id, idempotency_key) DO NOTHING
            RETURNING `+eventColumns,
            e.ID, e.TenantID, e.Type, []byte(e.Payload), e.IdempotencyKey, e.BodyHash[:], e.CreatedAt, e.TraceContext)
        got, err := scanEvent(row)
        if err == nil {
            stored = got
            _, err = tx.Exec(ctx, `INSERT INTO outbox (event_id, created_at) VALUES ($1, $2)`, got.ID, got.CreatedAt)
            return err
        }
        if !errors.Is(err, pgx.ErrNoRows) {
            return err
        }
        stored, err = scanEvent(tx.QueryRow(ctx, `
            SELECT `+eventColumns+` FROM events WHERE tenant_id = $1 AND idempotency_key = $2`,
            e.TenantID, e.IdempotencyKey))
        if err != nil {
            return err
        }
        if stored.BodyHash != e.BodyHash {
            return domain.ErrIdempotencyMismatch
        }
        replayed = true
        return nil
    })

העמודה trace_context בקוד הזה נוספת רק באבן הדרך השמינית (סעיף 38.8). באבן הדרך השנייה ההכנסה כוללת שבע עמודות.

כך זה עובד כששתי בקשות עם אותו מפתח מגיעות יחד:

רגע בקשה א' בקשה ב'
1 ‏INSERT מצליח ומחזיק את ערך המפתח באינדקס הייחודי ‏INSERT נתקל באותו ערך ומחכה לסוף הטרנזקציה של א'
2 ‏INSERT לשורת ה־outbox, ואז COMMIT עדיין מחכה
3 מחזירה את האירוע ‏ON CONFLICT DO NOTHING: אין שורה מוחזרת
4 ‏SELECT חדש, בתמונת מצב חדשה, רואה את השורה של א'; הגיבובים זהים, ולכן החזרה חוזרת

ב־Read committed כל פקודה מקבלת תמונת מצב משלה (פרק 11, סעיף 11.2), ולכן הקריאה של ב' רואה את מה ש־א' אישרה. אם א' הייתה מבטלת, ה־INSERT של ב' היה ממשיך ומצליח. אין כאן ניסיון חוזר ואין Serializable: האילוץ מספיק.

הגוף של האירוע נשמר כ־jsonb, והמסד מחזיר אותו בצורה מנורמלת: רווח אחרי נקודתיים, וסדר מפתחות משלו. בגלל זה הבדיקות משוות JSON לפי ערך ולא לפי בתים. שתי התשובות של בקשות מקבילות עדיין זהות, כי שתיהן נקראות מאותה שורה.

func (c *Cache) Endpoints(ctx context.Context, tenantID, eventType string) ([]string, error) {
    subs, err := c.c.Get(ctx, Key(tenantID), func(ctx context.Context) ([]domain.Subscription, error) {
        return c.loader.ActiveSubscriptions(ctx, tenantID)
    })
    if err != nil {
        return nil, err
    }
    var ids []string
    for _, s := range subs {
        if s.EventType == eventType || s.EventType == domain.AllTypes {
            ids = append(ids, s.EndpointID)
        }
    }
    slices.Sort(ids)
    return slices.Compact(ids), nil
}

שלושה דברים בקוד הזה:

  • רק endpoints פעילים. ‏ActiveSubscriptions מצטרפת לטבלת ה־endpoints ומשאירה רק את אלה שלא הושבתו, ולכן השבתה היא גם שינוי שמוחק את הרשומה.

להשלים את ההבטחה המרכזית של Hookline: כל שורת מסירה נשלחת למקבל כבקשת POST חתומה, עם ארבע הכותרות. כשל זמני מנוסה שוב עם המתנה גדלה. כשל סופי, או סוף הניסיונות, הופכים את המסירה למתה. מסירה מתה אפשר להריץ שוב דרך ה־API, וכל ניסיון גלוי בהיסטוריה. בסוף, בדיקה מקצה לקצה עוברת מול ה־sink: כל אירוע מגיע לכל מקבל מתאים.

יום 43: חתימה, שליחה ותור. התחילי מהחתימה, כי יש לה מפרט מדויק בקובץ: הבדיקה TestSignMatchesSharedVectors קוראת את אותם וקטורים שה־sink ב־Python בודק. זו הפונקציה מהקובץ internal/delivery/signer.go:

func Sign(secret string, ts int64, body []byte) string {
    mac := hmac.New(sha256.New, []byte(secret))
    t := strconv.FormatInt(ts, 10)
    mac.Write([]byte(t))
    mac.Write([]byte{'.'})
    mac.Write(body)
    return "t=" + t + ",v1=" + hex.EncodeToString(mac.Sum(nil))
}

עכשיו השליחה והסיווג. ‏Classify היא המדיניות של דרישה F6 בשש שורות:

func Classify(status int) (retryable bool, err error) {
    switch {
    case status >= 200 && status < 300:
        return false, nil
    case status == http.StatusRequestTimeout || status == http.StatusTooManyRequests || status >= 500:
        return true, fmt.Errorf("receiver answered %d", status)
    default:
        return false, fmt.Errorf("receiver answered %d; not retried", status)
    }
}

  • שגיאת רשת וזמן קצוב הם זמניים. המקבל עלול לחזור.

יום 44: הפעלה חוזרת, ה־pool והבדיקה מקצה לקצה. ההפעלה החוזרת נראית פשוטה: להחזיר מסירה מתה ל־pending. הפרט שמסבך אותה הוא המספור. בטבלה attempts יש מפתח ייחודי על הזוג מסירה ומספר. אם מאפסים את attempts לאפס, הניסיון הבא נרשם עם מספר 1 ומתנגש בניסיון 1 הישן. אם לא מאפסים, המסירה כבר הגיעה למקסימום ומתה אחרי כישלון אחד.

  • היומן נשאר רציף. המספר בטבלת הניסיונות ממשיך לעלות, וכך גם הכותרת Hookline-Attempt. המקבל רואה שזה ניסיון חוזר.
  • התנאי status = 'dead' בתוך הפקודה. שתי לחיצות במקביל מזיזות את המסירה פעם אחת. השנייה מקבלת 409, והבדיקה TestConcurrentReplaysMoveTheDeliveryOnce שולחת שמונה כאלה במקביל.

38.5.8 טעויות נפוצות

  • לחתום על גוף אחד ולשלוח אחר. אם הגוף נבנה פעמיים, או עובר קידוד מחדש, החתימה לא תתאים. חותמים על הבתים שנשלחים בדיוק.
  • לאפס את attempts בהפעלה חוזרת. הניסיון הבא מתנגש במספר ניסיון קיים, וההכנסה לטבלת הניסיונות נכשלת.
  • לנסות שוב 400. המקבל לא ישנה את התשובה, וה־worker מבזבז את הניסיונות ואת התור על מסירה שלא תצליח.
  • חכירה קצרה מהזמן הקצוב. ‏worker שני תופס את המסירה בזמן שהראשון עוד מחכה לתשובה, ושניהם שולחים. ההגדרות דוחות חכירה שאינה ארוכה מהזמן הקצוב.
  • להקשיב ל־ctx של הכיבוי באמצע בקשה. הבקשה נקטעת, התוצאה לא נרשמת, והמסירה נשלחת שוב אחרי שהחכירה פגה. הבקשה רצה עם context מנותק, מוגבל בחכירה.

יום 54: הגנות לכל endpoint. העתיקי את שתי החבילות, breaker ו־bulkhead, מהתרגיל של פרק 15, והחליפי את שם המודול. הבדיקות שלהן עוברות מיד, כי הן לא תלויות בשום דבר בפרויקט.

השאלה המעניינת היא איפה הן יושבות. כל worker מחזיק מפסק ומחיצה לכל endpoint, בזיכרון של התהליך. זו ההחלטה מטבלת ההחלטות בפרק 37, סעיף 37.5: מצב מקומי פשוט יותר ונכשל בבטחה. המחיר הוא שכל תהליך לומד לבד שה־endpoint מת. זה הקוד מהקובץ internal/delivery/worker.go:

    g := p.Guards.get(j.EndpointID)
    if g.bulkhead != nil {
        if err := g.bulkhead.Acquire(ctx); err != nil {
            p.postpone(ctx, j, busyWait(), "bulkhead", err)
            return Result{}, false
        }
        defer g.bulkhead.Release()
    }
    done, err := g.breaker.Allow()
    if err != nil {
        p.postpone(ctx, j, p.Guards.openWait(), "breaker", err)
        return Result{}, false
    }
    res = attempt()
    done(breakerError(res))
    return res, true

שלוש החלטות בקוד:

  • מחיצה בלי המתנה. כשה־endpoint כבר מחזיק את כל המקומות שלו, ה־worker לא מחכה. הוא מחזיר את המסירה לתור ותופס אחרת. אחרת, ה־worker עצמו היה נתקע, וזה בדיוק מה שהמחיצה נועדה למנוע.
  • דחייה בלי ניסיון. ‏Postpone מחזירה את attempts לערך שלפני התפיסה, ולא רושמת כלום בהיסטוריה. אף בקשה לא נשלחה, ולכן אסור שזה יקצר את הניסיונות של המסירה.
  • רק כשל זמני פוגע במפסק. תשובת 400 היא תשובה של מקבל שעובד. ‏breakerError מחזירה שגיאה רק למה שמנוסה שוב: זמן קצוב, חיבור, 408, 429 ו־5xx.

יום 77: מעקב אחד לכל אירוע. הקושי של Hookline הוא שהאירוע עובר בין תהליכים לא באותו זמן. ה־API מחזיר 202 ומסיים, וה־relay מפרסם רק אחר כך, בטרנזקציה אחרת. ההקשר של המעקב לא יכול לעבור בזיכרון, ולכן הוא נשמר עם האירוע: עמודה חדשה, events.trace_context, מחזיקה את הכותרת traceparent של בקשת הקליטה. זו הפונקציה מהקובץ internal/api/ingest.go:

func traceparent(ctx context.Context) string {
    carrier := propagation.MapCarrier{}
    otel.GetTextMapPropagator().Inject(ctx, carrier)
    return carrier.Get("traceparent")
}

מכאן כל קפיצה ממשיכה את אותו מעקב:

קפיצה איך ההקשר עובר ה־span
‏API ‏otelhttp, ו־RoutePattern לפניו כדי שהנתיב יופיע POST /v1/events
‏relay ‏traceparent מהשורה, ואז kotel כותב אותו לכותרות של הרשומה hookline.events publish
‏dispatcher ‏kotel קורא את הכותרות; ‏WithProcessSpan hookline.events receive, ‏process
‏worker ‏traceparent מהשורה של האירוע, ו־otelhttp בלקוח שולח אותו הלאה hookline.deliver, ‏HTTP POST
‏sink ה־instrumentation של FastAPI מפרק 24 POST /hooks/{name}

ה־span של ה־worker הוא ילד של ה־span של הקליטה, ולא של ה־dispatcher. הסיבה: ה־worker קורא את ההקשר מהאירוע. זו פשרה: ניסיון חוזר אחרי עשר דקות עדיין שייך לאותו מעקב, ונראה בו בדיוק מתי ניסו. זה הקוד מהקובץ internal/delivery/worker.go:

    ctx, span := otel.Tracer(metrics.Scope).Start(withTraceparent(ctx, j.TraceContext), "hookline.deliver",
        trace.WithAttributes(attribute.String("hookline.delivery.id", j.DeliveryID),
            attribute.String("hookline.event.id", j.EventID), attribute.String("hookline.endpoint.id", j.EndpointID),
            attribute.Int("hookline.attempt", j.Attempt)))
    defer span.End()

בלי collector, telemetry.Start לא עושה כלום, וכל המכשירים הם no-op. כך הבדיקות, ה־compose של אבני הדרך הקודמות והניסויים רצים כמו קודם, בלי שגיאות ייצוא בלוג.

DATABASE_URL= go test -race -run 'Trace|Health' ./internal/api/ ./internal/telemetry/

יום 78: מדדים, כללים ולוחות. המדדים של HTTP אומרים אם ה־API עונה. הם לא אומרים אם webhooks מגיעים. אלה המכשירים שהחבילה internal/metrics מוסיפה:

מדד ב־Prometheus סוג מה הוא אומר

שתי החלטות בטבלה. ‏30 הוא גבול של דלי בהיסטוגרמה של הפיגור, כי ה־SLI סופר מסירות בתוך 30 שניות, ואת זה אפשר לחשב בדיוק רק על גבול (פרק 25). ואין endpoint כ־label במעברי המפסק, כי סדרה לכל endpoint גדלה בלי גבול. המזהה נמצא בשורת הלוג.

38.9.8 טעויות נפוצות

  • לבדוק את הכתובת רק ביצירה. השם יכול להתפענח לכתובת אחרת בזמן השליחה. רק הבדיקה ב־dialer רואה את הכתובת שמתחברים אליה.

הבדיקה לא סומכת על טבלת המסירות. היא בונה את הסט הצפוי בעצמה, מהאירועים ומהמנויים שהיו קיימים כשכל אירוע נקלט. כך גם אירוע שה־dispatcher איבד, ולא יצר לו שורת מסירה, יופיע כחסר. זו השאילתה, מהקובץ scripts/verify-delivery.sh:

    SELECT DISTINCT e.id, ep.id, ep.url, extract(epoch FROM e.created_at), coalesce(d.status, 'none')
    FROM events e
    JOIN subscriptions s ON s.tenant_id = e.tenant_id AND s.event_type IN (e.type, '*')
                        AND s.created_at <= e.created_at
    JOIN endpoints ep ON ep.id = s.endpoint_id AND ep.enabled
    LEFT JOIN deliveries d ON d.event_id = e.id AND d.endpoint_id = ep.id

הצד השני הוא /receipts של כל sink, שסופר זוגות ייחודיים של נקודת קבלה ואירוע. זוג שחסר נכשל, וכפילות רק נספרת. לכל endpoint הבדיקה מדפיסה גם את הפיגור מהקליטה ועד הקבלה הראשונה, וזה המספר של N2 ושל N3.

הסקריפט מריץ שני מופעים של כל אחד משלושת התהליכים של הצינור, ושולח 50 אירועים בשנייה במשך שתי דקות. כל כמה שניות הוא הורג אחד מהם ב־SIGKILL, ומעלה אותו שוב. זה הלב שלו, מהקובץ scripts/chaos.sh:

  v=${VICTIMS[RANDOM % ${#VICTIMS[@]}]}
  kill -9 "${PIDS[$v]}" 2> /dev/null
  wait "${PIDS[$v]}" 2> /dev/null
  log "KILL  $v"
  kills=$((kills + 1))
  sleep $((RANDOM % 4 + 1))
  spawn "$v"
  log "START $v"

‏SIGKILL ולא SIGTERM, כי כיבוי מסודר הוא לא המקרה הקשה. במקביל, ה־sink השני נכשל בחצי מהבקשות, אחר כך נתקע, ואחר כך נכשל בחמישית מהן. אחרי העומס הסקריפט מחכה שהתור יתרוקן, ומריץ את הבדיקה. ‏SEED קובע את סדר ההריגות, ולכן ריצה שמצאה בעיה ניתנת לחזרה.

  • לבדוק את הצינור רק ברכיבים בודדים. כל רכיב יכול לעבור לבד, והחיבור ביניהם עדיין שבור. הבדיקה מקצה לקצה של אבן הדרך החמישית היא שמוכיחה את ההבטחה.
  • לסמוך על Kafka לסינון כפילויות. ה־offset של פרסום כפול שונה. הכפילות נעצרת באילוץ במסד, ובמקבל לפי מזהה האירוע.
  • לנסות שוב כל כישלון. תשובת 4xx סופית; ניסיון חוזר שלה רק מאריך את התור של כולם.
  • ‏SLO שבנוי רק מהצלחות. כשאף דבר לא מצליח אין לו נתונים, והוא שותק בדיוק בזמן התקלה.
  • סוד ב־values של chart. הוא נשמר בהיסטוריה של ה־release; ה־chart מקבל שם של Secret, לא את הערך.
  • הגנה שעולה יותר ממה שהיא חוסכת. מחיצה שמחכה, או השלת עומס אחרי קריאה למסד, מחזירות את העומס מהדלת האחורית.
  • הגנה בלי בדיקה שמוכיחה אותה. שורה במודל האיומים בלי שם של בדיקה היא תקווה, ולא הגנה.
  • „אפס חסרות” בלי לקרוא את הפיגור. הניסוי של אבן הדרך העשירית מצא באג אמיתי בדיוק שם, כשלא אבדה אף מסירה.

שאלות ראיון

  1. למה המאגר יושב מאחורי ממשק כבר באבן הדרך הראשונה, כשהוא עוד בזיכרון? כי ההחלפה ל־PostgreSQL באבן הדרך השנייה נעשית בלי לגעת ב־handler, ואותן בדיקות API רצות על שני המאגרים. הממשק גם מכריח להחליט מוקדם מה החוזה: מי מסנן לפי דיירת, מה השגיאות. המחיר הוא שכבה אחת נוספת, וזה זול לעומת שכתוב של כל ה־handlers.

  2. איך מבטיחים שקריסה של ה־relay לא תיצור מסירה כפולה? לא מבטיחים שהיא לא תפרסם פעמיים; היא כן תפרסם, כי קריסה בין הפרסום לסימון משאירה את השורה לא מסומנת. מבטיחים שהפרסום הכפול לא משנה כלום: ה־dispatcher מכניס עם ON CONFLICT DO NOTHING על הזוג אירוע ו־endpoint. ומול המקבל, שבו אין אילוץ משותף, החוזה הוא „לפחות פעם אחת” וסינון לפי Hookline-Event-Id. המשך: ולמה לא לסמן לפני הפרסום? כי אז קריסה בין הסימון לפרסום מאבדת את האירוע לגמרי; עדיף כפילות שמסננים על פני אובדן שאי אפשר לגלות.

  3. מה קורה כש־worker נתקע באמצע מסירה? החכירה שלו פגה, ו־worker אחר תופס את המסירה עם מספר ניסיון גבוה יותר. הניסיון התקוע נרשם כ„חכירה פגה”. אם הראשון מתעורר ומנסה לרשום תוצאה, הרישום בודק את מספר הניסיון ונדחה. המחיר האפשרי הוא שהמקבל קיבל שתי בקשות, וזה בסדר בחוזה „לפחות פעם אחת”. לכן החכירה חייבת להיות ארוכה מהזמן הקצוב של ניסיון.

  4. מקבל אחד של דיירת אחת תקוע. איך שאר המקבלים לא מרגישים? שתי הגנות בכל worker. מחיצה אטומה מגבילה כמה workers endpoint אחד יכול להחזיק, וכשהיא מלאה המסירה נדחית בלי לחכות. מפסק זרם מפסיק לשלוח אחרי כמה כשלים רצופים, ובודק שוב אחרי זמן. בשני המקרים הדחייה לא סופרת ניסיון. ההגנות מקומיות לכל תהליך: פשוט יותר ונכשל בבטחה, במחיר שכל worker לומד לבד. את המחיר הזה מודדים בניסוי N3, עם ההגנות ובלעדיהן. המשך: למה לא מפסק משותף ב־Redis? כי אז Redis נעשה תלות של כל שליחה, ותקלה בו משפיעה על כל המקבלים; הייתי עוברת אליו רק אם המדידה מראה שהרבה workers מכים endpoint מת לפני שהמפסקים המקומיים נפתחים.

  5. איך את מריצה מיגרציות בפריסה ל־Kubernetes, ומה יכול להשתבש? ‏Job של Helm ב־pre-install ו־pre-upgrade, כך שהסכמה מוכנה לפני שאף pod חדש עולה, עם פקודה אידמפוטנטית. שני דברים לשים לב אליהם: ה־Job לא רואה משאבים שה־chart עוד לא התקין, והמיגרציה חייבת להתאים גם לגרסה הישנה שעוד רצה, כי בעדכון מתגלגל שתיהן חיות יחד (פרק 30). לכן מיגרציה שמוחקת עמודה נכנסת רק אחרי שאף גרסה לא קוראת אותה.

  6. השירות שלך שולח בקשות לכתובות שהלקוחות בוחרים. איך את מגינה עליו? בודקת פעמיים. ביצירה, את ה־URL ואת כל הכתובות שהשם מתפענח אליהן, עם תשובה כללית ללקוח. ובכל חיבור, ב־Control של ה־dialer, את הכתובת שמתחברים אליה בפועל. השנייה היא שעומדת מול DNS rebinding, כי בין הרישום לשליחה השם יכול להצביע למקום אחר. בנוסף, אין proxy מהסביבה, אין הפניות, ומצב הפיתוח מתיר רק טווחים מוגדרים. ורשימה של כתובות מותרות לא אפשרית כאן, כי היעדים הם של הלקוחות: לכן חוסמים את מה שמסוכן, ובודקים בחיבור עצמו.
