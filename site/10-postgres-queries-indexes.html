פרק 10: PostgreSQL: שאילתות ואינדקסים

רוב הבעיות בשירותי backend שנראות כמו „השרת איטי” מתבררות כשאילתה אחת שקוראת מיליון שורות כדי להחזיר עשרים. מהנדסת בכירה לא מנחשת: היא מריצה את השאילתה עם EXPLAIN, קוראת את התוכנית, ובוחרת אינדקס אחד שמתאים בדיוק לשאילתה. בפרק הזה תבני מאגר הזמנות של מיליון שורות, תמדדי חמש שאילתות איטיות, תתקני אותן, ותכתבי מעליהן מאגר נתונים ב־Go שלא נופל לבור הקלאסי של N+1.

מה נלמד בפרק

  • להריץ PostgreSQL בקונטיינר ולעבוד מולו עם psql, בלי להתקין שום דבר על המחשב.
  • לייצר נתונים מציאותיים ומוטים עם generate_series, ולמה בלעדיהם כל ניסוי ביצועים משקר.
  • לקרוא תוכנית ביצוע: עלות, הערכה מול מציאות, דפים שנקראו, וסוגי הצמתים העיקריים.
  • איך אינדקס B-tree בנוי, מה הוא יודע לעשות ומה הוא עולה בכתיבה.
  • לבחור אינדקס מרוכב בסדר העמודות הנכון, אינדקס חלקי ואינדקס מכסה.
  • לזהות בעיית N+1 בקוד Go ולתקן אותה, ולעמד לפי מפתח (keyset) במקום לדלג על שורות.
  • לכתוב שכבת גישה לנתונים (repository) עם pgx, ולבדוק אותה מול מסד אמיתי.

ידע מקדים

  • פרק 2, סעיפים 2.4 ו־2.7: הקונטיינרים והקומפיילר של Go צריכים לעבוד.
  • פרק 3, סעיף 3.3 (מודולים וחבילות) וסעיף 3.8 (בדיקות טבלאיות).
  • פרק 4, סעיף 4.5 (עטיפת שגיאות) וסעיף 4.7 (generics): ה־API של pgx משתמש בשניהם.
  • פרק 5, סעיף 5.4 (context): כל קריאה למסד מקבלת context.
  • פרק 9, סעיף 9.4 (עימוד: offset מול cursor): כאן רואים למה cursor מהיר יותר, מתוך התוכנית עצמה.
  • לא צריך psql מותקן: הוא רץ בתוך הקונטיינר.

10.1 PostgreSQL בקונטיינר ו־psql

המסד רץ בקונטיינר אחד, מקובץ compose שנמצא בתיקיית הנתונים של התרגיל, data/compose.yaml. גרסת ה־image מקובעת בקובץ (נכון לאוקטובר 2026, ראי נספח ג), כך שכל מי שמריצה את התרגיל מקבלת אותו שרת בדיוק. כדאי להבין חמש החלטות בקובץ:

שורה למה
name: ch10 שם פרויקט ייחודי, כדי שהקונטיינר והנפח של הפרק לא יתנגשו בפרקים אחרים
127.0.0.1:5410:5432 הפורט נפתח רק למחשב שלך, ולא ברירת המחדל 5432, שאולי כבר תפוסה
shm_size שאילתות מקביליות משתמשות בזיכרון משותף; 64MB של Docker לא תמיד מספיקים
../:/work:ro תיקיית התרגיל שלך נראית בתוך הקונטיינר בנתיב /work, לקריאה בלבד
pgdata נפח בשם: הנתונים שורדים הפעלה מחדש, ונמחקים רק עם down -v

מפעילים מתוך תיקיית התרגיל. הדגל --wait מחכה עד שבדיקת הבריאות עוברת, כך שהפקודה הבאה לא נתקלת בשרת שעוד עולה:

docker compose -p ch10 -f data/compose.yaml up -d --wait
docker compose -p ch10 -f data/compose.yaml exec db psql -U course -d orders

הפקודה השנייה פותחת psql בתוך הקונטיינר, וה־prompt הוא orders=#. ל־psql יש פקודות משלו, שמתחילות בלוכסן הפוך ולא נשלחות לשרת:

פקודה מה היא עושה
\dt רשימת הטבלאות
\d orders העמודות, האילוצים והאינדקסים של טבלה
\di+ רשימת האינדקסים עם הגודל של כל אחד
\timing on מדפיס אחרי כל פקודה כמה זמן היא לקחה
\x auto שורות רחבות מוצגות אנכית
\i /work/schema.sql מריץ קובץ SQL מתוך תיקיית התרגיל
\q יציאה

קוד Go מתחבר לאותו שרת מבחוץ, דרך הפורט שנפתח. כתובת החיבור נשמרת במשתנה סביבה, כמו כל תצורה בספר (פרק 6, סעיף 6.3):

export DATABASE_URL=postgres://course:change-me@localhost:5410/orders

שימי לב: הסיסמה change-me היא סיסמת תרגול למסד שפתוח רק למחשב שלך. בשירות אמיתי הסיסמה מגיעה ממנהל סודות, וזה הנושא של פרק 28.

10.2 סכמה ונתונים מציאותיים

על טבלה של מאה שורות כל שאילתה מהירה, והמתכנן (planner) של PostgreSQL בוחר כמעט תמיד לקרוא את כל הטבלה, כי זה באמת הכי זול. לכן ניסוי אינדקסים על נתוני צעצוע לא מלמד כלום. צריך מספיק שורות כדי שקריאה מלאה תעלה משהו, וצריך התפלגות מוטה כמו בחיים: יש לקוחות שקונים פי אלף מאחרים, ורוב ההזמנות כבר נמסרו.

10.2.1 הסכמה

ארבע טבלאות: לקוחות, מוצרים, הזמנות ושורות הזמנה. זה קטע מהקובץ exercises/ch10-orders-db/starter/schema.sql:

CREATE TABLE orders (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (id),
    status      text NOT NULL CHECK (status IN ('pending', 'paid', 'shipped', 'delivered', 'cancelled')),
    total_cents bigint NOT NULL,
    created_at  timestamptz NOT NULL
);

CREATE TABLE order_items (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id    bigint NOT NULL REFERENCES orders (id),
    product_id  bigint NOT NULL REFERENCES products (id),
    quantity    int NOT NULL CHECK (quantity > 0),
    price_cents bigint NOT NULL
);

שימי לב למה שאין כאן: אין אינדקסים מלבד המפתחות הראשיים (ואינדקס הייחודיות על האימייל של הלקוח). זה מכוון, כי הוספתם היא התרגיל. ושימי לב לעוד דבר: המילה REFERENCES יוצרת מפתח זר (foreign key), אבל המסד לא יוצר אינדקס על העמודה המפנה. העמודה order_id אינה מאונדקסת עד שתוסיפי לה אינדקס בעצמך, וזו הסיבה הראשונה לשאילתה איטית שתמצאי בסעיף 10.4.

10.2.2 הזרע: generate_series

הפונקציה generate_series(1, 1000000) מחזירה טבלה של מיליון מספרים, ו־INSERT ... SELECT מעליה בונה מיליון שורות בפקודה אחת, בתוך השרת, בלי לולאה בצד הלקוח. כך נראית יצירת ההזמנות בקובץ exercises/ch10-orders-db/data/seed.sql:

INSERT INTO orders (id, customer_id, status, total_cents, created_at)
SELECT s.i,
       1 + floor(50000 * power(random(), 3))::bigint,
       CASE WHEN s.r < 0.01 THEN 'pending'
            WHEN s.r < 0.03 THEN 'cancelled'
            WHEN s.r < 0.06 THEN 'paid'
            WHEN s.r < 0.12 THEN 'shipped'
            ELSE 'delivered' END,
       t.total,
       TIMESTAMPTZ '2026-10-01 00:00+00' - power(random(), 2) * INTERVAL '730 days'
FROM (SELECT i, random() AS r FROM generate_series(1, 1000000) AS i) AS s
JOIN (SELECT order_id, sum(quantity * price_cents) AS total FROM staged_items GROUP BY order_id) AS t
  ON t.order_id = s.i;

שלוש ההטיות בשאילתה הזאת הן העיקר:

עמודה נוסחה מה יוצא
הלקוח מספר אקראי בחזקת 3, כפול 50,000 לקוח 1 מקבל עשרות אלפי הזמנות; לקוח טיפוסי כעשר
הסטטוס ספים על מספר אקראי אחד כאחוז אחד ממתינות, הרוב המוחלט נמסרו
הזמן מספר אקראי בריבוע, אחורה מ־1 באוקטובר 2026 הזמנות צפופות ליד ההווה, דלילות לפני שנתיים

העלאה בחזקה של מספר אקראי בין 0 ל־1 דוחפת את רוב התוצאות לכיוון 0, וזו דרך פשוטה לקבל התפלגות עם „זנב ארוך”. הזרע מתחיל ב־setseed(0.42), ולכן אותו קובץ מייצר את אותם נתונים בכל הרצה: השאילתות בתרגיל מתייחסות להזמנה 777777 וללקוח 4242, והן יחזירו אצלך את אותן שורות.

שורות ההזמנה נוצרות קודם, לטבלה זמנית, כדי שהסכום של כל הזמנה יהיה מדויק. בסוף הקובץ יש שתי פעולות שקל לשכוח:

  • הפונקציה setval מקדמת את מוני המזהים מעבר למזהים שהכנסנו בעצמנו. בלעדיה ההכנסה הבאה מהקוד נכשלת על מפתח כפול.
  • הפקודה VACUUM (ANALYZE) אוספת סטטיסטיקות לתכנון ומעדכנת את מפת הנראות (visibility map). המפה הזאת נחוצה לסריקת אינדקס בלבד, בסעיף 10.5.

כמה זמן לוקח הזרע? תמדדי ותרשמי. התוצאה תלויה במחשב ובמשאבים שהקצית ל־Docker; הכוונה היא שזה ייקח פחות מדקות ספורות. רשמי את זמן הזרע אצלך ( שניות) ואת גודל המסד אחריו (), שמוצג בפקודה \l+ של psql.

10.3 EXPLAIN ו־EXPLAIN ANALYZE

הפקודה EXPLAIN מחזירה את התוכנית שהמתכנן בחר, בלי להריץ את השאילתה. הגרסה EXPLAIN ANALYZE מריצה אותה באמת, ומוסיפה לכל צומת את מה שקרה בפועל. ההבדל הזה הוא כל הסיפור: הראשון מראה מה המתכנן מעריך, השני מראה מה היה. כשהשאילתה איטית, הפער בין השניים הוא בדרך כלל הרמז.

10.3.1 תוכנית ראשונה

זו שאילתה Q1 מהתרגיל, „שורות ההזמנה עם שמות המוצרים”, מהקובץ exercises/ch10-orders-db/data/queries/q1-order-items.sql:

-- Q1: the lines of one order, with product names (an order page).
EXPLAIN (ANALYZE, BUFFERS)
SELECT i.product_id, p.name, i.quantity, i.price_cents
FROM order_items i
JOIN products p ON p.id = i.product_id
WHERE i.order_id = 777777;

זו צורת הפלט לפני שיש אינדקס. הזמנים הוחלפו בשלוש נקודות, כי הם ייראו אחרת אצלך; את הזמנים שלך תרשמי בטבלה של התרגיל:

 Gather  (cost=1000.28..28090.37 rows=2 width=32) (actual time=… rows=2.00 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Nested Loop  (cost=0.28..27090.17 rows=1 width=32) (actual time=… rows=0.67 loops=3)
         ->  Parallel Seq Scan on order_items i  (cost=0.00..27081.87 rows=1 width=20) (actual time=… rows=0.67 loops=3)
               Filter: (order_id = 777777)
               Rows Removed by Filter: 666615
               Buffers: shared read=16666
         ->  Index Scan using products_pkey on products p  (cost=0.28..8.29 rows=1 width=20) (actual time=… rows=1.00 loops=2)
               Index Cond: (id = i.product_id)
               Index Searches: 2
 Planning Time: … ms
 Execution Time: … ms

קוראים תוכנית מבפנים החוצה: הצמתים המוזחים ביותר רצים ראשונים, ומעבירים שורות לצומת שמעליהם. כך מפרשים את המספרים:

שדה משמעות
cost=A..B הערכה ביחידות שרירותיות: A עד השורה הראשונה, B עד האחרונה. משווים עלויות, לא ממירים לשניות
rows= בסוגריים הראשונים כמה שורות המתכנן העריך
actual time=A..B אלפיות שנייה, לכל לולאה: עד השורה הראשונה ועד האחרונה
rows= ב־actual כמה שורות יצאו בפועל, בממוצע ללולאה (ב־PostgreSQL 18 עם שתי ספרות אחרי הנקודה)
loops= כמה פעמים הצומת רץ; הזמן והשורות הם ממוצע ללולאה, אז כופלים
Rows Removed by Filter שורות שנקראו ונזרקו: המדד הישיר לבזבוז
Buffers: shared hit דפים של 8KB שנמצאו בזיכרון של PostgreSQL
Buffers: shared read דפים שנקראו מהדיסק או ממטמון מערכת ההפעלה

התוכנית הזאת אומרת: שלושה תהליכים (שני workers ועוד המוביל) סרקו יחד את כל order_items, זרקו כשני מיליון שורות, וקראו כ־16 אלף דפים, כדי למצוא שתי שורות. זה סימן ההיכר של אינדקס חסר: סריקה מלאה עם סינון סלקטיבי מאוד, ומספר עצום בשורה Rows Removed by Filter.

שימי לב: בגרסה 18, ‏EXPLAIN ANALYZE מדפיס את שורות ה־BUFFERS גם בלי לבקש. בתרגיל שתי המילים כתובות במפורש, כדי שהשאילתות יעבדו כך גם בגרסאות קודמות שתפגשי בעבודה.

10.3.2 למה EXPLAIN לבד מטעה

הפקודה EXPLAIN בלי ANALYZE מראה רק את עמודת ההערכה. כשהסטטיסטיקות ישנות, או כשהנתונים מוטים, ההערכה רחוקה מהמציאות, והתוכנית שנראית סבירה על הנייר איטית בפועל. בנתונים שלנו, השאילתה „ההזמנות האחרונות של לקוח” מוערכת בכ־30 שורות ללקוח 4242 ובעשרות אלפים ללקוח 1, והמתכנן בוחר אסטרטגיה אחרת לכל אחד מהם. אי אפשר לדעת שהוא צדק בלי להריץ.

ומהצד השני, האפשרות ANALYZE מריצה את השאילתה. בקריאה זה רק זמן, אבל בפקודת כתיבה, כמו UPDATE, השינוי קורה באמת. בודקים פקודת כתיבה בתוך טרנזקציה שמבטלים, כמו בקובץ exercises/ch10-orders-db/data/queries/explain-write.sql:

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE orders SET status = 'paid' WHERE id = 42;
ROLLBACK;

10.3.3 הצמתים שתפגשי

צומת מה הוא עושה מתי הוא טוב
Seq Scan קורא את כל הטבלה, דף אחר דף כשצריך חלק גדול מהשורות, או כשהטבלה קטנה
Index Scan הולך באינדקס, ולכל התאמה קופץ לשורה בטבלה מעט שורות, או כשצריך את הסדר של האינדקס
Index Only Scan עונה מהאינדקס בלבד, בלי לגעת בטבלה כשכל העמודות הדרושות נמצאות באינדקס
Bitmap Index Scan ו־Bitmap Heap Scan אוסף מהאינדקס את כל הדפים המתאימים, ואז קורא אותם בסדר הפיזי כמות בינונית של שורות, מפוזרות
Nested Loop לכל שורה מהצד החיצוני, מחפש התאמות בצד הפנימי צד חיצוני קטן ואינדקס על הצד הפנימי
Hash Join בונה טבלת גיבוב מצד אחד ובודק מולה את הצד השני שני צדדים גדולים, בלי סדר מועיל
Merge Join ממזג שני קלטים שכבר ממוינים לפי מפתח החיבור כששני הצדדים מגיעים ממוינים, למשל מאינדקסים
Sort ממיין; top-N heapsort כשיש LIMIT כשאין אינדקס שנותן את הסדר
Limit עוצר אחרי N שורות שילוב עם צומת שמחזיר שורות בסדר הנכון חוסך הכול
Gather ו־Gather Merge אוספים תוצאות מ־workers מקביליים סריקות גדולות; אצלנו בדרך כלל סימן לסריקה מלאה

בקובץ exercises/ch10-orders-db/data/queries/joins.sql יש שתי שאילתות חיבור. הראשונה מבקשת את ההזמנות של לקוח 4242 עם השורות שלהן, כלומר מעט שורות בצד החיצוני. אחרי האינדקסים של התרגיל, התוכנית שלה היא Nested Loop: סריקה של 41 ההזמנות של הלקוח, ולכל אחת חיפוש באינדקס של שורות ההזמנה. בפלט יופיע loops=41. השאילתה השנייה באותו קובץ מסכמת את כל ההזמנות של חודש, מאות אלפי שורות בכל צד, ושם המתכנן בוחר Hash Join: הוא בונה טבלת גיבוב מההזמנות של החודש וסורק מולה את כל שורות ההזמנה. ארבע מאות אלף בדיקות באינדקס היו יקרות יותר מסריקה אחת.

10.4 אינדקסי B-tree

10.4.1 מה זה

אינדקס B-tree הוא עץ מאוזן של דפים, שבו המפתחות ממוינים. בעלים יש זוגות של מפתח ומצביע לשורה בטבלה (TID: מספר דף ומיקום בתוכו), והעלים מקושרים זה לזה, כך שאפשר ללכת קדימה או אחורה בסדר המפתחות. העץ רחב מאוד, מאות מפתחות בדף, ולכן גם על מיליון שורות הוא בעומק של שלוש או ארבע רמות: חיפוש הוא כמה קריאות דף במקום אלפים.

מהמבנה הזה נובע מה שהוא יודע לעשות:

  • שוויון: customer_id = 4242.
  • טווח: תנאי „גדול מ” או „קטן מ” על העמודה, וגם BETWEEN.
  • סדר: ORDER BY created_at, בשני הכיוונים, כי העלים מקושרים לשני הכיוונים.
  • קידומת: LIKE 'abc%', בתנאים מסוימים של סדר המיון במסד; לא נעסוק בזה כאן.
  • בדיקת IS NULL, ומציאת הערך הקטן או הגדול ביותר.

ומה הוא לא יודע: תנאי על פונקציה של העמודה (lower(email) = ...) לא משתמש באינדקס על email, אלא באינדקס ביטוי על lower(email). גם LIKE '%abc' לא נעזר בו, כי אין קידומת.

10.4.2 מה הוא עולה

כל הכנסה מוסיפה מפתח לכל אינדקס של הטבלה, ועדכון של עמודה מאונדקסת נוגע באינדקס. אינדקסים תופסים מקום בדיסק ובזיכרון ומתחרים עם הטבלה על המטמון. לכן כל אינדקס צריך שאילתה אמיתית שמצדיקה אותו.

10.4.3 שתי השאילתות הראשונות

השאילתה Q1 מחפשת לפי order_id, שהוא מפתח זר בלי אינדקס. התיקון הוא שורה אחת, מהקובץ exercises/ch10-orders-db/solution/indexes.sql:

-- Q1: foreign keys are not indexed automatically. Every "items of this order" lookup,
-- and every join from orders to order_items, needs this one.
CREATE INDEX order_items_order_id_idx ON order_items (order_id);

אחרי היצירה, הסריקה המלאה והמקבילית נעלמת, ובמקומה Nested Loop שמתחיל ב־Index Scan על האינדקס החדש. השורה Filter הפכה ל־Index Cond: התנאי מוחל בתוך האינדקס, לא אחרי הקריאה. השורה Index Searches, חדשה בגרסה 18, סופרת כמה פעמים ירדנו בעץ. את הזמן לפני ואחרי תרשמי בטבלה של התרגיל.

השאילתה Q2 סופרת את ההזמנות של יום אחד. אינדקס על created_at הופך אותה לסריקת bitmap בשני שלבים: כאלף שורות מפוזרות על כאלף דפים, ולכן המתכנן אוסף קודם את רשימת הדפים מהאינדקס וקורא אותם בסדר הפיזי, במקום לקפוץ הלוך ושוב. זה מצב הביניים בין סריקת אינדקס לסריקה מלאה.

10.4.4 למה המתכנן לפעמים „מתעלם” מאינדקס

המתכנן מעריך כמה שורות יעברו כל תנאי, לפי סטטיסטיקות שאוסף ANALYZE (ושמוצגות בתצוגה pg_stats). מזה הוא מחשב עלות לכל תוכנית אפשרית ובוחר את הזולה. כשתנאי מחזיר חלק גדול מהטבלה, קריאה רציפה של הכול זולה יותר מאלפי קפיצות אקראיות, ואז Seq Scan הוא הבחירה הנכונה, לא באג. הפרמטר random_page_cost (ברירת מחדל 4) אומר למתכנן כמה קריאה אקראית יקרה מקריאה רציפה; על SSD מקטינים אותו לפעמים.

בנתונים המוטים שלנו רואים את זה בבירור. עם אינדקס על customer_id בלבד, הלקוח הטיפוסי מקבל סריקת bitmap ואחריה מיון של 41 שורות. ללקוח 1, שיש לו כ־27 אלף הזמנות, המתכנן בוחר משהו אחר: הוא הולך אחורה באינדקס של created_at ומסנן לפי לקוח, כי ההזמנות של לקוח 1 כל כך צפופות שעשרים מהן יימצאו מהר. אותה שאילתה, שני ערכים, שתי תוכניות. זו הסיבה שבודקים עם הערכים הקשים, לא רק עם הממוצעים.

10.5 אינדקסים מרוכבים, חלקיים ומכסים

10.5.1 אינדקס מרוכב וסדר העמודות

אינדקס מרוכב (composite index) ממוין לפי העמודה הראשונה, בתוכה לפי השנייה, וכן הלאה, בדיוק כמו ספר טלפונים שממוין לפי שם משפחה ובתוכו לפי שם פרטי. מכאן הכלל: עמודות השוויון קודם, ואחריהן עמודת הטווח או המיון. השאילתה Q3, „עשרים ההזמנות האחרונות של לקוח”, היא הדוגמה הקלאסית:

-- Q3: equality column first, then the sort column. One index answers "this customer,
-- newest first, stop after 20" without sorting. id is the tie-breaker the keyset
-- pagination in orders.go relies on. A B-tree can be read backwards, so ASC works for DESC.
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at, id);

באינדקס הזה, כל ההזמנות של לקוח 4242 יושבות ברצף אחד, ממוינות לפי זמן. התוכנית יורדת בעץ אל סוף הרצף, הולכת אחורה עשרים צעדים ועוצרת. בתוכנית תראי Index Scan Backward, ואין בה מיון. זה עובד בדיוק אותו דבר ללקוח 1 ולשלושים שורות או לשלושים אלף, וזה הכוח של אינדקס שמתאים לשאילתה.

מה קורה בסדר ההפוך, (created_at, customer_id)? כדאי לנסות פעם אחת, בתוך טרנזקציה שמבטלים בסוף. התוכנית עדיין כתובה Index Cond: (customer_id = 4242), וזה מטעה: השוויון על העמודה השנייה לא מצמצם את הטווח בעץ, כי ההזמנות של הלקוח מפוזרות לאורך כל האינדקס. בפועל נקרא כמעט כל האינדקס. ההבדל מופיע בשורת ה־Buffers: השווי אותה בין שתי הגרסאות ותרשמי את שני המספרים.

10.5.2 אינדקס חלקי

השאילתה Q4 מבקשת את חמישים ההזמנות הממתינות הוותיקות ביותר, מה ש־worker של מחלקת משלוחים יבקש שוב ושוב. רק כאחוז אחד מההזמנות ממתינות, ואף אחד לא שואל את השאלה הזאת על הזמנות שנמסרו. אינדקס חלקי (partial index) מכיל רק את השורות שעונות על תנאי:

-- Q4: only about 1% of the rows are pending, and only those are ever queried this way.
-- A partial index holds just those rows: small, cheap to maintain, sorted by created_at.
CREATE INDEX orders_pending_created_idx ON orders (created_at) WHERE status = 'pending';

התוכנית לאחר מכן היא Index Scan אחד בלי Filter בכלל: התנאי „ממתינה” מובטח על ידי האינדקס עצמו. השווי עם \di+ את הגודל שלו לגודל של אינדקס מלא על created_at, ותרשמי. ויש בונוס בכתיבה: הזמנה שנמסרה לא נמצאת באינדקס, ולכן עדכונים שלה לא נוגעים בו.

המתכנן ישתמש באינדקס חלקי רק אם הוא יכול להוכיח מתוך השאילתה שהתנאי שלה גורר את תנאי האינדקס. התנאי status = 'pending' כתוב מילולית בשאילתה, ולכן זה עובד. פרמטר (status = $1) בתוכנית גנרית לא מספיק להוכחה הזאת.

10.5.3 אינדקס מכסה ו־Index Only Scan

השאילתה Q5 מסכמת לפי חודש את ההזמנות של לקוח 1 בשנת 2026. היא צריכה שלוש עמודות: הלקוח, הזמן והסכום (total_cents). האינדקס של Q3 כבר מוצא את השורות, אבל בשביל הסכום PostgreSQL קופץ לטבלה לכל אחת מאלפי השורות. אינדקס מכסה (covering index) מוסיף את העמודה החסרה כמטען, בלי להפוך אותה לחלק מהמפתח:

-- Q5: the Q3 index already finds the rows; adding total_cents as a payload column lets
-- PostgreSQL answer from the index alone (Index Only Scan). Replace, do not add a second
-- index with the same key columns.
DROP INDEX orders_customer_created_idx;
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at, id) INCLUDE (total_cents);

עמודה ב־INCLUDE לא משפיעה על המיון ולא משמשת לחיפוש; היא רק יושבת בעלה ליד המפתח. עכשיו התוכנית היא Index Only Scan, ובה השורה Heap Fetches: 0: אף שורה לא נקראה מהטבלה.

שתי הערות שהופכות את זה לנכון באמת:

  • סריקת אינדקס בלבד תלויה במפת הנראות. המסד צריך לדעת שהדף בטבלה „נקי”, כלומר כל השורות בו גלויות לכולם, ורק אז מותר לו לסמוך על האינדקס בלי לבדוק את הטבלה. הפקודה VACUUM מעדכנת את המפה. אם תראי Heap Fetches גבוה, הטבלה עברה הרבה שינויים מאז ה־VACUUM האחרון.
  • מחליפים, לא מוסיפים. היה אפשר להשאיר את האינדקס של Q3 ולהוסיף לידו עוד אחד עם אותן עמודות מפתח, אבל אז כל הכנסה משלמת פעמיים. האינדקס המכסה עונה גם על Q3 וגם על Q5, וגם על העימוד בסעיף הבא.

10.6 N+1 ועימוד מהיר

10.6.1 בעיית ה־N+1

בעיית N+1 היא קוד שמביא רשימה בשאילתה אחת, ואז שולח שאילתה נוספת לכל פריט ברשימה. כל שאילתה בנפרד מהירה ומאונדקסת היטב, ולכן שום EXPLAIN לא יחשוף את הבעיה; היא נמצאת בקוד, במספר הנסיעות לשרת. זו הגרסה האיטית מהקובץ exercises/ch10-orders-db/starter/orders.go:

// OrdersWithItemsNPlusOne is the slow version, kept for comparison: one query for
// the orders, then one more query per order for its items (1 + N round trips).
func (r *Repo) OrdersWithItemsNPlusOne(ctx context.Context, customerID int64, limit int) ([]Order, error) {
    orders, err := r.RecentOrders(ctx, customerID, limit)
    if err != nil {
        return nil, err
    }
    for i := range orders {
        rows, err := r.pool.Query(ctx, `
            SELECT product_id, quantity, price_cents
            FROM order_items
            WHERE order_id = $1
            ORDER BY id`, orders[i].ID)
        if err != nil {
            return nil, fmt.Errorf("items of order %d: %w", orders[i].ID, err)
        }
        items, err := pgx.CollectRows(rows, pgx.RowToStructByPos[Item])
        if err != nil {
            return nil, fmt.Errorf("items of order %d: %w", orders[i].ID, err)
        }
        orders[i].Items = items
    }
    return orders, nil
}

למאתיים הזמנות זה 201 שאילתות. כל אחת עולה נסיעה הלוך ושוב ברשת, ניתוח, תכנון והרצה. מול מסד על אותו מחשב זה מורגש; מול מסד בענן, במרחק של אלפית שנייה או יותר לכל נסיעה, זה מה שהופך דף לאיטי. ספריות ORM נופלות בזה בקלות, כי הגישה ל־order.Items נראית כמו גישה לשדה.

התיקון: שתי שאילתות, בלי קשר לכמה הזמנות יש. השנייה מביאה את כל השורות בבת אחת, עם מערך של מזהים כפרמטר. כך נראה הפתרון ב־exercises/ch10-orders-db/solution/orders.go:

    rows, err := r.pool.Query(ctx, `
        SELECT order_id, product_id, quantity, price_cents
        FROM order_items
        WHERE order_id = ANY($1)
        ORDER BY order_id, id`, ids)
    if err != nil {
        return nil, fmt.Errorf("items of %d orders: %w", len(ids), err)
    }
    var orderID int64
    var it Item
    _, err = pgx.ForEachRow(rows, []any{&orderID, &it.ProductID, &it.Quantity, &it.PriceCents}, func() error {
        o := byID[orderID]
        o.Items = append(o.Items, it)
        return nil
    })

הספרייה ממירה slice של int64 למערך במסד בלי עזרה. התנאי = ANY($1) משתמש באינדקס על העמודה. המפה byID מצביעה לתוך ה־slice של ההזמנות, ולכן ההוספה מעדכנת את ההזמנה עצמה.

יש עוד שתי דרכים מוכרות. חיבור JOIN אחד חוסך נסיעה, אבל מחזיר את עמודות ההזמנה שוב בכל שורת פריט ומחייב קיבוץ בצד של Go. הטיפוס pgx.Batch שולח כמה שאילתות בנסיעה אחת, אבל השרת עדיין מריץ N שאילתות.

איך תופסים N+1 לפני שהוא מגיע לייצור? סופרים שאילתות. ב־pgx אפשר לחבר רכיב מעקב (tracer) לחיבור. בתרגיל יש רכיב כזה, QueryCounter, שהבדיקה משתמשת בו כדי לדרוש „בדיוק שתי שאילתות”. בייצור, אותו מנגנון מחובר למעקב (פרק 24), ושם N+1 נראה כמגדל של spans זהים.

10.6.2 עימוד: OFFSET מול keyset

ב־OFFSET 19980 LIMIT 20, PostgreSQL לא „קופץ” לשורה 19,981. הוא מייצר את כל 20 אלף השורות בסדר הנכון וזורק את רובן. העמוד הראשון מהיר והעמוד האלף איטי, ובנוסף, אם נוספה הזמנה בזמן שהמשתמשת דפדפה, כל העמודים זזים בשורה והיא רואה שורה פעמיים. בקובץ exercises/ch10-orders-db/data/queries/pagination.sql יש את שתי הגרסאות, ובתוכנית של הראשונה תראי צומת Limit מעל אלפי שורות שנקראו.

עימוד keyset, שנקרא גם עימוד לפי cursor (פרק 9, סעיף 9.4), שומר את המפתח של השורה האחרונה בעמוד ומבקש „מה שבא אחריה”. כאן המפתח הוא הזוג (created_at, id): הזמן לבדו לא ייחודי, ו־id שובר שוויון. כך נראה העמוד הבא בקובץ exercises/ch10-orders-db/solution/orders.go:

        rows, err = r.pool.Query(ctx, `
            SELECT `+orderColumns+`
            FROM orders
            WHERE customer_id = $1 AND (created_at, id) < ($2, $3)
            ORDER BY created_at DESC, id DESC
            LIMIT $4`, customerID, after.CreatedAt, after.ID, limit+1)

שלושה פרטים קטנים עושים את העבודה:

  • השוואת שורות (a, b) < (x, y) היא השוואה לקסיקוגרפית, בדיוק הסדר של האינדקס (customer_id, created_at, id). לכן האינדקס מתחיל לקרוא מיד אחרי ה־cursor, ועמוד עמוק עולה כמו העמוד הראשון.
  • סדר ה־ORDER BY זהה לסדר העמודות באינדקס, כולל המזהה בסוף. אחרת חוזר צומת Sort.
  • מבקשים limit+1 שורות. אם הגיעה שורה נוספת, יש עמוד הבא, וה־cursor הוא השורה האחרונה שמוחזרת; אם לא, זה העמוד האחרון ומחזירים nil.

המחיר של keyset: אי אפשר לקפוץ ישר לעמוד 1000, ואי אפשר להציג „עמוד 7 מתוך 40” בלי ספירה נפרדת. לרשימות ארוכות ב־API זה כמעט תמיד מחיר שכדאי לשלם. בפרק 9 ראית איך ה־cursor נארז למחרוזת אטומה ללקוח; כאן עוסקים במה שקורה בתוך המסד.

10.7 pgx מ־Go

10.7.1 pool, לא חיבור

הספרייה pgx היא דרייבר ל־PostgreSQL. החבילה pgxpool שלה מנהלת מאגר חיבורים (connection pool). שירות HTTP מחזיק pool אחד לכל התהליך: כל בקשה לוקחת חיבור לזמן השאילתה ומחזירה אותו. חיבור בודד אחד לכל השירות היה מסדר את כל הבקשות בתור, וחיבור חדש לכל בקשה היה עולה פתיחת תהליך בשרת בכל פעם. פרק 11, סעיף 11.7, עוסק בגודל ה־pool. בתרגיל, הפונקציה Config בקובץ db.go קובעת גבול מפורש ומחזירה תצורה ולא מאגר מוכן. כך הבדיקות יכולות להוסיף לה מונה שאילתות ונתיב חיפוש (search_path) לפני הפתיחה.

10.7.2 שאילתות, פרמטרים ושורות

שלוש המתודות שתשתמשי בהן כל הזמן:

מתודה מחזירה מתי
Query pgx.Rows הרבה שורות
QueryRow שורה אחת, ל־Scan שורה אחת בדיוק; אין שורות זו השגיאה pgx.ErrNoRows
Exec pgconn.CommandTag כתיבה; RowsAffected אומר כמה שורות השתנו

הפרמטרים נכתבים $1 וכן הלאה, ונשלחים בנפרד מהטקסט של השאילתה. לכן אין הזרקת SQL גם כשהערך מגיע ממשתמשת. לעולם לא בונים שאילתה עם fmt.Sprintf מערך של משתמשת. בתרגיל יש חיבור מחרוזות אחד, orderColumns, והוא קבוע שנכתב בקוד, לא קלט.

את השורות קוראים עם pgx.CollectRows ופונקציה שממירה שורה לערך. זו הקריאה של Q3 בקובץ exercises/ch10-orders-db/starter/orders.go:

func scanOrder(row pgx.CollectableRow) (Order, error) {
    var o Order
    err := row.Scan(&o.ID, &o.CustomerID, &o.Status, &o.TotalCents, &o.CreatedAt)
    return o, err
}

// RecentOrders returns the customer's newest orders, newest first (query Q3).
func (r *Repo) RecentOrders(ctx context.Context, customerID int64, limit int) ([]Order, error) {
    rows, err := r.pool.Query(ctx, `
        SELECT `+orderColumns+`
        FROM orders
        WHERE customer_id = $1
        ORDER BY created_at DESC, id DESC
        LIMIT $2`, customerID, limit)
    if err != nil {
        return nil, fmt.Errorf("recent orders: %w", err)
    }
    return pgx.CollectRows(rows, scanOrder)
}

הפונקציה CollectRows סוגרת את rows בעצמה, גם בשגיאה. אם את עוברת על שורות ידנית בלולאה, את חייבת לסגור אותן ב־defer rows.Close() ולבדוק את rows.Err() אחרי הלולאה. שורות שלא נסגרו מחזיקות חיבור, ובסוף המאגר נגמר. הגנריקה pgx.RowToStructByPos[Item] ממלאת struct לפי סדר העמודות, נוח כשהשאילתה והטיפוס צמודים.

איך Rust עושה את זה: המאקרו query_as! של sqlx בודק את השאילתה מול מסד אמיתי בזמן הקומפילציה, כולל הטיפוסים של העמודות. ל־pgx אין שלב כזה: שם עמודה שגוי או סוג לא מתאים יתגלו רק בזמן ריצה. לכן ב־Go הבדיקות מול מסד אמיתי הן מה שמחליף את הבדיקה של הקומפיילר.

10.7.3 בדיקות מול מסד אמיתי

בדיקה מול חיקוי (mock) של המסד בודקת בעיקר את החיקוי. הבדיקות בתרגיל רצות מול השרת שבקונטיינר, ובכל זאת לא נוגעות במיליון השורות: כל בדיקה יוצרת סכמה פרטית, מכוונת אליה את נתיב החיפוש של המאגר, מריצה עליה את schema.sql ומכניסה 25 הזמנות ידועות. בסוף הסכמה נמחקת. כשהמשתנה DATABASE_URL לא מוגדר, הבדיקות מדלגות עם הודעה. כך go test ./... ירוק גם בלי Docker, אבל „ירוק עם דילוגים” הוא לא „עבר”.

הבדיקה של N+1 מראה איך הופכים ביצועים לטענה שאפשר לבדוק בלי שעון: היא דורשת שהגרסה המהירה תשלח בדיוק שתי שאילתות, לפי QueryCounter, ושתחזיר בדיוק את מה שהגרסה האיטית מחזירה. השני חשוב לא פחות מהראשון. אופטימיזציה שמשנה תוצאה היא באג. ועל הנתונים המלאים יש בתרגיל פקודה קטנה, cmd/nplus1, שמריצה את שתי הגרסאות ומדפיסה מספר שאילתות וחציון זמנים, כדי שתמדדי את ההבדל בעצמך.

סיכום

  • נתונים מציאותיים ומוטים הם תנאי לכל ניסוי ביצועים; generate_series עם setseed מייצר אותם בתוך השרת, ושוב ושוב אותו דבר.
  • הפקודה EXPLAIN מראה הערכה; EXPLAIN (ANALYZE, BUFFERS) מראה מה קרה. מחפשים פער בין שורות מוערכות לאמיתיות, מספר גבוה של שורות שסוננו, ו־Sort שאפשר היה לחסוך.
  • אינדקס B-tree עונה על שוויון, טווח וסדר. מפתח זר לא מאונדקס אוטומטית. כל אינדקס עולה בכתיבה ובמקום.
  • אינדקס מרוכב: שוויון קודם, טווח או מיון אחר כך. חלקי: כשהשאילתה תמיד מסננת לאותה תת־קבוצה קטנה. מכסה: עמודות ב־INCLUDE לסריקת אינדקס בלבד, בתנאי שמפת הנראות עדכנית.
  • בעיית N+1 מתגלה בספירת שאילתות ולא בתוכנית. מתקנים בשאילתה אחת עם = ANY($1), או בחיבור.
  • עימוד לפי מפתח, עם (created_at, id) ואינדקס באותו סדר, נותן עמוד עמוק במחיר של עמוד ראשון. דילוג על שורות קורא אותן ומשליך.
  • בספרייה pgx: מאגר חיבורים אחד לתהליך, פרמטרים ולא חיבור מחרוזות, CollectRows, ובדיקות מול מסד אמיתי בסכמה פרטית.

טעויות נפוצות

  • להאמין ל־EXPLAIN בלי ANALYZE. ההערכה יכולה לטעות בסדרי גודל, במיוחד בנתונים מוטים. מריצים ובודקים את השורות בפועל.
  • להריץ EXPLAIN ANALYZE על DELETE בלי טרנזקציה. השורות נמחקות באמת. עוטפים ב־BEGIN ו־ROLLBACK.
  • לשכוח אינדקס על מפתח זר. כל חיבור וכל „הפריטים של ההזמנה” הופכים לסריקה מלאה, וגם מחיקה בטבלת האב סורקת את טבלת הבן.
  • להפוך את סדר העמודות באינדקס מרוכב. התוכנית אפילו כותבת Index Cond, אבל קוראת כמעט את כל האינדקס. שוויון קודם.
  • להוסיף אינדקס כמעט זהה לקיים. שני אינדקסים עם אותה קידומת מכפילים את עלות הכתיבה; מרחיבים את הקיים.
  • לשכוח rows.Close() בלולאה ידנית. החיבור לא חוזר ל־pool, ואחרי כמה בקשות הכול נתקע. הפונקציה CollectRows סוגרת בעצמה.

שאלות ראיון

  1. שאילתה מהירה בפיתוח ואיטית בייצור. איך את חוקרת? קודם מריצה EXPLAIN (ANALYZE, BUFFERS) בייצור, או על עותק בגודל ייצור, כי התוכנית תלויה בכמות ובהתפלגות. מחפשת פער בין שורות מוערכות לשורות בפועל (סטטיסטיקות ישנות או ערך מוטה), סריקה מלאה עם סינון סלקטיבי (אינדקס חסר), ומיון שאפשר היה לחסוך. בודקת גם אם הבעיה בכלל בשאילתה ולא ב־N+1 או בהמתנה לנעילה. התיקון נבחר לפי השאילתה, ונמדד שוב באותו אופן.

המשך: ואם התוכנית טובה והשאילתה עדיין איטית? אז מסתכלים על Buffers (נקרא מהדיסק ולא מהזיכרון), על המתנה לנעילות ב־pg_stat_activity, ועל מספר השאילתות לבקשה.

  1. באיזה סדר תשימי עמודות באינדקס מרוכב? עמודות השוויון קודם, ואחריהן עמודת הטווח או המיון, כי האינדקס ממוין לפי הראשונה ורק בתוכה לפי השנייה. כך כל השורות של שוויון אחד נמצאות ברצף, ממוינות כפי שהשאילתה רוצה. השיקול השני הוא אילו שאילתות נוספות האינדקס ישרת: אינדקס על (customer_id, created_at) עונה גם על „כל ההזמנות של לקוח”, אבל לא על „כל ההזמנות של אתמול”. לפעמים עדיף אינדקס אחד רחב יותר משניים צרים.

  2. מתי סריקה מלאה היא הבחירה הנכונה? כשהשאילתה צריכה חלק ניכר מהטבלה, או כשהטבלה קטנה. קריאה רציפה של דפים זולה הרבה יותר מקפיצות אקראיות לכל שורה, והמתכנן יודע את זה דרך random_page_cost והסטטיסטיקות. לכן „הוא לא משתמש באינדקס” היא לא תמיד בעיה. כשהמתכנן טועה, הסיבה הנפוצה היא סטטיסטיקות לא עדכניות.

  3. למה keyset ולא OFFSET? דילוג על N שורות מייצר את כולן וזורק אותן, ולכן העלות גדלה עם עומק העמוד, ושינויים בין עמודים מזיזים שורות. עימוד keyset מתחיל מהמפתח האחרון, עם אינדקס באותו סדר, ולכן כל עמוד עולה אותו דבר ואין כפילויות. המחיר הוא שאין קפיצה לעמוד שרירותי ואין „עמוד 7 מתוך 40” בחינם. ל־API ולגלילה אינסופית זה מתאים; לטבלת ניהול קטנה עם מספרי עמודים, OFFSET מספיק טוב.

  4. מה המחיר של אינדקס, ואיך תחליטי אם להוסיף אחד? כל אינדקס מאט הכנסות ועדכונים, תופס מקום, ומתחרה על המטמון. מוסיפים אינדקס כשיש שאילתה אמיתית ותכופה שהוא מתקן, ובודקים שהיא באמת משתמשת בו. מעדיפים להרחיב אינדקס קיים (עוד עמודה, INCLUDE) על פני הוספת אחד כמעט זהה, ושוקלים אינדקס חלקי כשהשאילתה תמיד מסננת לתת־קבוצה קטנה. ובייצור יוצרים אותו עם CONCURRENTLY, כדי לא לחסום כתיבות לטבלה.

המשך: איך תמצאי אינדקסים מיותרים? בתצוגה pg_stat_user_indexes, אינדקס ש־idx_scan שלו נשאר אפס לאורך זמן הוא מועמד להסרה, אחרי שבודקים שהוא לא אוכף ייחודיות.

הפתק המוכן נמצא גם כקובץ: obsidian/10-postgres-queries-indexes.md. זה תוכנו:

  • קודם מודדים: ‏EXPLAIN (ANALYZE, BUFFERS) על נתונים בגודל ובצורה אמיתיים; EXPLAIN לבד הוא רק הערכה.
  • קוראים מבפנים החוצה: שורות מוערכות מול בפועל, מספר הלולאות, שורות שסוננו ודפים שנקראו.

  • מרוכב: שוויון קודם, טווח או מיון אחר כך. הסדר ההפוך כותב Index Cond וקורא הכול.

  • מחליפים אינדקס, לא מוסיפים כמעט זהה.
  • ‏N+1: סופרים שאילתות; מתקנים עם = ANY($1).
  • עימוד keyset: ‏(created_at, id) < ($2, $3) עם אינדקס באותו סדר; מבקשים limit+1.

תרגיל

מטרה: לטעון מאגר הזמנות של מיליון שורות, לתקן חמש שאילתות איטיות באינדקסים תוך רישום הזמנים שלך לפני ואחרי, ולכתוב repository ב־pgx עם תיקון ל־N+1 ועימוד keyset, עם בדיקות מול המסד. זמן: שני ימי לימוד, ימים 24 ו־25, כ־40 דקות בנייה ביום הראשון וכ־70 בשני. ידע מקדים: הפרק, Docker פועל (פרק 2, סעיף 2.4), Go (פרק 2, סעיף 2.7), ועימוד מפרק 9, סעיף 9.4.

הצעדים, קוד ההתחלה, הרמזים והפתרון נמצאים ב־ exercises/ch10-orders-db/README.md.

קריטריון סיום:

  • המסד טעון, וזמן הזרע שלך רשום בפתק.
  • לכל אחת מחמש השאילתות יש תוכנית לפני ואחרי, והזמנים שלך רשומים בטבלה שב־README של התרגיל.
  • הקובץ indexes.sql שלך מכיל אינדקס אחד לכל שאילתה, והאינדקס המכסה מחליף את המרוכב.
  • הבדיקות עוברות מול הקונטיינר עם -race, כולל הבדיקה שדורשת שתי שאילתות בלבד.
  • הפלט של cmd/nplus1 על לקוח 1 רשום בפתק.

העשרה אופציונלית

  • בתיעוד של PostgreSQL 18, הפרק „Using EXPLAIN” (בחלק Performance Tips) עובר על כל צומת עם דוגמאות, והפרק „Indexes” מסביר אינדקסים חלקיים, מכסים ו־skip scan.
  • האתר use-the-index-luke.com של Markus Winand מלמד אינדקסים דרך תוכניות ביצוע, כולל פרק שלם על עימוד keyset.
  • נסי אינדקס ביטוי: חיפוש לקוח לפי lower(email), לפני ואחרי CREATE INDEX ... ON customers (lower(email)).
  • הריצי את Q3 עם SET enable_indexscan = off כדי לראות את התוכנית השנייה הכי טובה, ולהבין כמה המתכנן היה משלם בלעדיה.
