פרק 3: צעדים ראשונים ב־Go

את כותבת Rust כל יום, ולכן הפרק הזה לא מלמד אותך לתכנת. הוא מלמד אותך איפה Go מוותרת על ביטחון שהקומפיילר של Rust נותן לך, מה היא מקבלת בתמורה, ואיפה הוויתור נושך. בראיון ל־backend בכיר יצפו ממך לכתוב Go נקייה ובדוקה, ולהסביר מה קורה מתחת לפני השטח של slice או map. בסוף הפרק תהיה לך תוכנית אמיתית, logstat, עם בדיקות ובלי אזהרות.

מה נלמד בפרק

  • מה Go מנסה להיות, ומה היא בכוונה לא.
  • שרשרת הכלים, ומה מקביל לכל כלי ב־Cargo.
  • מודולים וחבילות, ונראות לפי אות גדולה.

  • בדיקות טבלאיות, ו־staticcheck ו־gofmt כהרגל.

ידע מקדים

  • היכרות יומיומית עם Rust. אין צורך בידע קודם ב־Go.

3.1 למה Go, ומה היא לא

Go נולדה כדי לכתוב שירותי רשת בצוותים גדולים, כך שקוד של אדם אחד יהיה קריא לאחר בלי מאמץ. מכאן ההחלטות שלה: שפה קטנה, קומפילציה מהירה, בינארי סטטי אחד, ספרייה סטנדרטית רחבה לרשת, ומקביליות מובנית. רוב הכלים שתפגשי בהמשך הספר כתובים בה, ובהם Kubernetes ו־Terraform.

בסקר המודעות של הספר Go הופיעה ב־13 מתוך 30 מודעות בכירות, בדרך כלל כאחת מכמה שפות אפשריות, והיא חזקה במיוחד במסלולי platform ו־DevOps. המקור: סעיף 4 בקובץ 00-stage1/01-market-research.md.

מה Go בכוונה לא נותנת לך, ביחס ל־Rust:

נושא Rust Go
זיכרון בעלות ושאילה, נבדקות בקומפילציה אוסף זבל (GC) בזמן ריצה
שגיאות Result<T, E> והאופרטור ? ערך error רגיל ובדיקה מפורשת
ערך חסר Option<T> ערך אפס, או nil
פולימורפיזם traits מוצהרים ממשקים מרומזים
מרוצי נתונים (data races) נמנעים בקומפילציה נתפסים בזמן ריצה עם -race

התמורה: פחות טקסים, קומפילציה מהירה, וסגנון אחיד לכולם. המחיר: חלק מהבאגים ש־Rust עוצרת בקומפילציה יגיעו אצלך לזמן ריצה, והפרק מראה איפה.

3.2 שרשרת הכלים: run, build, fmt, vet

הכלי go הוא המהדר, מנהל החבילות ומריץ הבדיקות גם יחד:

פקודת Go מה היא עושה המקבילה ב־Rust
go run . מהדרת לתיקייה זמנית ומריצה cargo run
go build ./... מהדרת הכול; תוכנית יחידה נכתבת כבינארי cargo build
go test ./... מריצה את כל הבדיקות cargo test
gofmt -l . מדפיסה קבצים שאינם מעוצבים cargo fmt --check
go vet ./... ניתוח סטטי (static analysis) מובנה לבאגים נפוצים חלק קטן מ־clippy
staticcheck ./... ניתוח סטטי רחב, כלי חיצוני cargo clippy

הביטוי ./... פירושו „החבילה בתיקייה הזאת וכל מה שמתחתיה”.

לכלי העיצוב gofmt אין הגדרות כלל: אין קובץ תצורה ואין ויכוח על סגנון, ולכן כל קוד Go נראה אותו דבר. ועוד דבר: go test מריץ בעצמו חלק מבדיקות vet ונכשל אם הן מוצאות משהו. תראי את זה בפרק 4.

שימי לב: הספר כתוב ל־Go 1.27, נכון לאוקטובר 2026. הגרסה המדויקת שאומתה רשומה בנספח ג.

3.3 מודולים וחבילות

מודול (module) הוא יחידת הגרסה וההפצה, המקבילה של crate. חבילה (package) היא תיקייה אחת של קבצי .go עם אותו שם package. חבילה בשם main עם פונקציה main היא תוכנית; כל חבילה אחרת היא ספרייה. יוצרים מודול מתוך תיקייה ריקה:

go mod init example.com/ch03-logstat
go mod edit -go=1.27
cat go.mod

module example.com/ch03-logstat

go 1.27

השורה הראשונה היא נתיב המודול, השם שבו מייבאים אותו; הוא לא חייב להתקיים ככתובת. השנייה אומרת על איזו גרסה של השפה הקוד נשען, והספר מקבע אותה במפורש.

תלות חיצונית מוסיפים עם go get, והיא נרשמת בגרסה מדויקת ב־go.mod. לצידו נוצר go.sum, ובו גיבוב קריפטוגרפי של כל תלות. הוא לא קובץ נעילה: את הגרסאות קובע go.mod, והוא רק מוודא שהתוכן שירד נכון. שני הקבצים נכנסים ל־Git. לתרגיל של הפרק אין תלויות בכלל.

איך Rust עושה את זה: Cargo פותר טווח גרסאות לגרסה החדשה ביותר שמתאימה, ונועל אותה בקובץ הנעילה. ב־Go כל מודול מצהיר על הגרסה המינימלית שהוא צריך, והכלי בוחר את הגבוהה מבין המינימליות (minimal version selection). התוצאה דטרמיניסטית בלי קובץ נעילה, ושדרוג קורה רק כשמבקשים אותו.

נראות נקבעת לפי האות הראשונה. שם שמתחיל באות גדולה (ParseLine) מיוצא; שם באות קטנה (report) פרטי לחבילה. אין pub, ואין פרטיות ברמת קובץ: כל הקבצים בחבילה רואים זה את זה.

3.4 התחביר למתכנתת Rust

הדרך המהירה ללמוד תחביר היא לקרוא קוד אמיתי. זו תחילת הקובץ parse.go מהתרגיל:

// Entry is one parsed access-log line in Common Log Format:
//
//  host ident user [time] "METHOD path PROTO" status bytes
type Entry struct {
    Host   string
    Time   time.Time
    Method string
    Path   string
    Status int
    Bytes  int64
}

// clfTime is Go's reference time (Mon Jan 2 15:04:05 MST 2006) written in the log's layout.
const clfTime = "02/Jan/2006:15:04:05 -0700"

הטיפוס בא אחרי השם, בלי נקודתיים. הערה מעל שם מיוצא היא התיעוד שלו. הקבוע מגלה הפתעה: תבנית זמן ב־Go אינה %d/%m/%Y. כותבים תאריך ייחוס קבוע, 2 בינואר 2006 בשעה 15:04:05, בצורה שבה הזמן מופיע בקלט. וזה תחילת גוף הפונקציה, מאותו קובץ:

func ParseLine(line string) (Entry, error) {
    var e Entry
    host, rest, ok := strings.Cut(line, " ")
    if !ok || host == "" {
        return Entry{}, fmt.Errorf("no host field")
    }
    e.Host = host

מה לשים לב אליו:

  • החזרה מרובה. הפונקציה מחזירה כמה ערכים, והשגיאה תמיד אחרונה. בפרק 4 נעמיק.
  • הצהרה קצרה. האופרטור := מצהיר ומאתחל עם טיפוס מוסק.
  • ערך אפס. הביטוי var e Entry יוצר struct שכל שדותיו באפס. אין משתנה לא מאותחל.
  • פירוק מחרוזות. הפונקציה strings.Cut מחזירה את מה שלפני המפריד, את מה שאחריו, והאם נמצא.

לולאה יש אחת, for, בכמה צורות:

צורה שימוש
for i := 0; i < n; i++ לולאה קלאסית
for cond המקבילה של while
for i, v := range items מעבר על slice, מחרוזת או map
for i := range 10 המספרים 0 עד 9

החל מ־Go 1.22 משתנה הלולאה חדש בכל איטרציה, ולכן השורה v := v שתמצאי בקוד ישן מיותרת היום.

טעות נפוצה: משתנה או ייבוא שלא משתמשים בהם הם שגיאת קומפילציה, לא אזהרה. באמצע עבודה, כתבי _ = x.

3.5 ערכים, מצביעים, ו־GC מול בעלות

ב־Go הכול מועבר לפי ערך. העברת struct לפונקציה מעתיקה אותו, כאילו לכל טיפוס יש Copy. מצביע הוא ערך בפני עצמו, כתובת, ולכן מועתקת רק הכתובת. אין שאילה, אין הבחנה בין קריאה לכתיבה, ואין משך חיים (lifetime). מותר להחזיר מצביע למשתנה מקומי, כמו בקובץ stats.go:

// NewStats returns a Stats with its map allocated.
func NewStats() *Stats {
    return &Stats{Paths: make(map[string]int)}
}

ב־C++ זה מצביע תלוי, וב־Rust זה לא מתקמפל. ב־Go זה תקין: המהדר מבצע ניתוח בריחה (escape analysis), מזהה שהערך חי אחרי שהפונקציה חוזרת, ומקצה אותו על הערימה (heap). אוסף הזבל ישחרר אותו כשאיש כבר לא מצביע עליו. אפשר לבקש מהמהדר להראות את ההחלטות שלו:

go build -o /dev/null -gcflags=-m . 2>&1 | grep -E 'NewStats|stats.go:27'

./stats.go:26:6: can inline NewStats
./stats.go:48:15: inlining call to NewStats
./stats.go:27:9: &Stats{...} escapes to heap
./stats.go:27:27: make(map[string]int) escapes to heap

בלי ה־grep תראי שגם ארגומנטים לפונקציות של fmt בורחים, כי הן מקבלות אותם כממשק. בקוד רגיל לא חושבים על זה; בפרק 6 תמדדי הקצאות עם בנצ'מרק (benchmark).

הכלל המעשי: מצביע כשהפונקציה צריכה לשנות את הערך של הקוראת; ערך לכל struct קטן ובלתי משתנה.

איך Rust עושה את זה: הקומפיילר יודע בדיוק מתי כל ערך נהרס, ולכן אין עלות בזמן ריצה, אבל משלמים בזמן כתיבה: משכי חיים, Rc, Arc ובודק השאילות. Go מעבירה את המחיר לזמן ריצה, לאוסף זבל שרץ במקביל לתוכנית. מה שהולך לאיבוד: אין ערבות לכותב יחיד, ולכן מרוצי נתונים אפשריים (פרק 5). וגם Drop אין: קבצים נסגרים ידנית עם defer.

3.6 slices מבפנים

slice נראה כמו Vec<T>, אבל מתנהג כמו משהו בין וקטור לבין חלק שאול ממנו, ושם מתחילות ההפתעות. בפנים הוא שלושה שדות, „כותרת” (slice header):

שדה משמעות
מצביע לאיבר הראשון במערך הבסיס (backing array)
len כמה איברים ה־slice רואה
cap כמה מקום יש במערך מהמצביע ועד סופו

השמה או העברה לפונקציה מעתיקות את הכותרת, לא את האיברים, ולכן שני slices יכולים לחלוק מערך. הביטוי paths[:2] יוצר כותרת עם אורך 2, אבל עם אותו מצביע, והקיבולת שלה נמשכת עד סוף המערך המקורי.

הפונקציה append כותבת במערך הקיים כשיש מקום, ומקצה מערך חדש כשאין. כלומר היא לפעמים משנה זיכרון משותף ולפעמים לא, ומהקוד לבד אי אפשר לדעת. כך זה נראה, בקובץ example_test.go של התרגיל:

// The aliasing bug: head shares its backing array with paths, so append writes into paths.
func Example_appendAliasing() {
    paths := []string{"/a", "/b", "/c", "/d"}
    head := paths[:2]           // len 2, cap 4: same backing array
    head = append(head, "/new") // fits in cap, so it overwrites paths[2]
    fmt.Println(paths, len(head), cap(head))

    paths = []string{"/a", "/b", "/c", "/d"}
    safe := slices.Clone(paths[:2]) // own backing array
    safe = append(safe, "/new")
    limited := paths[:2:2] // full slice expression: cap 2, so append must copy
    limited = append(limited, "/new")
    fmt.Println(paths, safe, limited)
    // Output:
    // [/a /b /new /d] 3 4
    // [/a /b /c /d] [/a /b /new] [/a /b /new]
}

השורה הראשונה בפלט היא הבאג: הוספנו ל־head, והאיבר השלישי של paths השתנה. בקוד אמיתי זה קורה כשפונקציה מחזירה חלק מ־slice פנימי, והקוראת מוסיפה לו. שתי דרכים מונעות זאת:

  • העתקה עם slices.Clone: הקצאה אחת, ואין שום שיתוף.
  • ביטוי slice מלא כמו paths[:2:2]: האינדקס השלישי מגביל את הקיבולת, והוספה חייבת להעתיק.

פונקציה ששמה מתחיל ב־Example ומסתיימת בהערת // Output: היא בדיקה: go test מריץ אותה ומשווה את הפלט להערה. כך הדוגמאות בפרק מאומתות ולא רק מתוארות.

איך Rust עושה את זה: המצב הזה לא מתקמפל. חלק שאול של וקטור אי אפשר להגדיל, ובזמן שהשאילה פעילה אסור לשנות את המקור. Go נותנת לך כותרת זולה להעתקה, ומשאירה לך לדעת מי עוד רואה את המערך.

כשנגמר המקום, append מקצה מערך גדול יותר; היחס המדויק הוא פרט מימוש, ואל תסמכי עליו. כשידוע מראש כמה איברים יהיו, הקצי מראש עם make([]T, 0, n), כמו Vec::with_capacity. ועוד: slice שערכו nil הוא slice תקין באורך אפס, ואפשר לעבור עליו ולהוסיף לו.

3.7 maps, מחרוזות ו־runes

3.7.1 maps

map הוא טבלת גיבוב, כמו HashMap. ערך האפס שלו הוא nil: מותר לקרוא ממנו, אבל כתיבה אליו היא panic, ולכן NewStats יוצרת אותו עם make. מפתח חסר מחזיר ערך אפס, ולכן s.Paths[path]++ עובד גם בפעם הראשונה. כדי להבחין בין „חסר” ל„אפס” כותבים v, ok := m[k]. ועוד שתי תכונות:

  • סדר המעבר לא מוגדר. המפרט אומר זאת במפורש, והמימוש מערבב בכוונה. כל פלט שנבנה ממעבר על map צריך מיון.
  • אין בטיחות לכתיבה מקבילה. שתי goroutines (פונקציות שרצות במקביל, פרק 5) שכותבות לאותו map בלי נעילה מפילות את התהליך עם fatal error: concurrent map writes. אי אפשר לתפוס את זה.

כך TopPaths הופכת map לטבלה ממוינת ודטרמיניסטית, בקובץ stats.go:

func TopPaths(paths map[string]int, n int) []PathCount {
    rows := make([]PathCount, 0, len(paths))
    for p, c := range paths {
        rows = append(rows, PathCount{Path: p, Count: c})
    }
    slices.SortFunc(rows, func(a, b PathCount) int {
        if c := cmp.Compare(b.Count, a.Count); c != 0 {
            return c
        }
        return cmp.Compare(a.Path, b.Path)
    })
    return rows[:max(0, min(n, len(rows)))] // clamp n into 0..len(rows)
}

ההשוואה הראשונה הפוכה כדי למיין בסדר יורד. השנייה שוברת שוויון לפי הנתיב, כדי שהפלט יהיה זהה בכל הרצה.

3.7.2 מחרוזות: בתים, לא תווים

מחרוזת ב־Go היא רצף בתים בלתי ניתן לשינוי. בדרך כלל אלה בתים של UTF-8, אבל השפה לא אוכפת זאת. האורך len(s) נמדד בבתים. rune הוא נקודת קוד אחת של Unicode, המקבילה של char. בעברית ההבדל מיידי, כי כל אות היא שני בתים. מהקובץ example_test.go:

// A string is bytes. Hebrew letters are two bytes each in UTF-8.
func Example_hebrewBytesAndRunes() {
    word := "שלום"
    fmt.Println(len(word), utf8.RuneCountInString(word))
    fmt.Println(utf8.ValidString(word[:3])) // a byte slice cut through a letter
    for i, r := range "אב!" {
        fmt.Println(i, string(r)) // i is the byte offset, r is the rune
    }
    fmt.Println(Truncate("/מוצרים/נעליים", 8))
    // Output:
    // 8 4
    // false
    // 0 א
    // 2 ב
    // 4 !
    // /מוצרים…
}

מה רואים בפלט:

  • אורך. המילה „שלום” היא 8 בתים ו־4 runes.
  • חיתוך. חיתוך באמצע אות מצליח בשקט ומייצר מחרוזת פגומה. ב־Rust אותו חיתוך היה panic.
  • מעבר. לולאת range על מחרוזת מחזירה runes, אבל האינדקס הוא היסט בבתים: 0, 2, 4.

לכן logstat חותכת נתיבים ארוכים לפי runes. מהקובץ stats.go:

// Truncate shortens s to at most limit runes (not bytes), marking the cut with "…".
func Truncate(s string, limit int) string {
    if limit < 1 {
        return ""
    }
    if utf8.RuneCountInString(s) <= limit {
        return s
    }
    runes := []rune(s)
    return string(runes[:limit-1]) + "…"
}

ההמרה []rune(s) מפענחת ומקצה זיכרון חדש. וגם rune אינו בהכרח תו שהעין רואה: אות עם ניקוד היא כמה runes. לספירת תווים נראים צריך ספרייה חיצונית, והתרגיל לא נזקק לה.

שימי לב: בלוג גישה נתיב בעברית מגיע מקודד באחוזים, כמו %D7%A2%D7%92%D7%9C%D7%94. הפונקציה DisplayPath מפענחת אותו רק לתצוגה; הספירה נעשית על הנתיב המקורי.

3.8 בדיקות טבלאיות

בדיקה ב־Go היא פונקציה ששמה מתחיל ב־Test, בקובץ שמסתיים ב־_test.go. אין מאקרו ואין ספריית assertions: בודקים עם if, ומדווחים עם t.Errorf, שממשיכה, או t.Fatalf, שעוצרת. קובץ הבדיקה יושב באותה חבילה ורואה גם שמות פרטיים, כמו מודול בדיקות פנימי ב־Rust.

ההרגל המרכזי הוא בדיקה טבלאית (table-driven test): slice של מקרים ולולאה אחת. מהקובץ parse_test.go, ההתחלה:

func TestParseLine(t *testing.T) {
    tests := []struct {
        name    string
        line    string
        want    Entry
        wantErr bool
    }{

ואחרי המקרים, הלולאה:

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseLine(tt.line)
            if tt.wantErr {
                if err == nil {
                    t.Fatalf("ParseLine(%q) = %+v, want an error", tt.line, got)
                }
                return
            }

למה זו ברירת המחדל:

  • מקרה חדש הוא שורה אחת. את השורה המשובשת שמצאת בייצור מוסיפים בשנייה.
  • לכל מקרה יש שם. הפונקציה t.Run יוצרת תת־בדיקה שאפשר להריץ לבד.
  • הודעה אחידה. הנוסח got X, want Y חוסך לפתוח את הקוד כדי להבין את הכשל.

כך מריצים תת־בדיקה אחת; רווח בשם הופך לקו תחתון:

go test -run 'TestParseLine/bad_time' -v .

PASS

הזמן אצלך יהיה אחר. ועוד שתי מוסכמות שהתרגיל משתמש בהן:

  • תיקיית testdata. הכלי מתעלם ממנה בבנייה, ושם שמים קבצי קלט לבדיקות.
  • פונקציית run. הפונקציה main רק קוראת לה; הבדיקות קוראות לה עם זרמים מזויפים ובודקות קוד יציאה.

3.9 תוכנית קטנה: logstat

הכלי קורא לוג גישה בפורמט הנפוץ של שרתי web, מקובץ או מהקלט הסטנדרטי, וסופר:

  • כמה שורות היו, כמה מהן משובשות, ומספרי השורות של המשובשות הראשונות.
  • כמה תשובות היו בכל מחלקת סטטוס.
  • אילו נתיבים התבקשו הכי הרבה, בלי מחרוזת השאילתה ועם עברית קריאה.

שורה משובשת נספרת ואינה עוצרת את הכלי: לוג אמיתי תמיד מכיל זבל, וכלי שקורס בשורה ה־40,000 חסר תועלת. הלב הוא המתודה Add, בקובץ stats.go:

// Add counts one line. A malformed line is counted, never fatal.
func (s *Stats) Add(line string) {
    s.Lines++
    e, err := ParseLine(line)
    if err != nil {
        s.Malformed++
        if len(s.BadLines) < maxBadLines {
            s.BadLines = append(s.BadLines, s.Lines)
        }
        return
    }
    s.Classes[e.Status/100]++
    path, _, _ := strings.Cut(e.Path, "?") // count /a?x=1 and /a?x=2 as /a
    s.Paths[path]++
}

הטיפוס של Classes הוא [6]int, מערך באורך קבוע ולא slice. מערך הוא ערך: השמה מעתיקה את כל ששת המספרים, ומשווים שני מערכים עם ==. ה־map, לעומתו, משותף; הדוגמה Example_valuesAndReferences מראה את ההבדל. הקריאה עצמה, באותו קובץ:

func Collect(r io.Reader) (*Stats, error) {
    s := NewStats()
    sc := bufio.NewScanner(r)
    sc.Buffer(make([]byte, 0, 64*1024), 1024*1024) // allow lines up to 1 MiB
    for sc.Scan() {
        s.Add(sc.Text())
    }
    return s, sc.Err()
}

3.10 staticcheck ו־gofmt כהרגל

שלושה כלים רצים לפני כל commit. כשהכול תקין, אף אחד מהם לא מדפיס דבר:

gofmt -l .
go vet ./...
staticcheck ./...
כלי מה הוא תופס
gofmt -l קבצים לא מעוצבים; הדגל -w מתקן במקום
go vet באגים שהמהדר מאשר, כמו מחרוזת פורמט שלא מתאימה לארגומנטים
staticcheck באגים, קוד מת, ערכים שמחושבים ולא נקראים, ו־API שהוצא משימוש

העורך מעצב בדרך כלל בכל שמירה. זה מה ש־staticcheck מוצא בקוד ההתחלה של התרגיל, לפני שמילאת אותו:

parse.go:21:7: const clfTime is unused (U1000)
stats.go:10:7: const maxBadLines is unused (U1000)

לכל ממצא יש קוד שאפשר לחפש בתיעוד; U1000 פירושו קוד שלא בשימוש. כאן הממצאים צפויים, והם ייעלמו כשתסיימי. בפרק 27 נוסיף את golangci-lint, שמריץ עשרות כלים כאלה יחד. ההרגל מתחיל כאן: הכלים שקטים לפני שמבקשים סקירת קוד.

סיכום

  • Go מחליפה בדיקות קומפילציה של Rust בפשטות ובזמן ריצה: אוסף זבל, ערכי אפס, ושגיאות כערכים.
  • מודול מוגדר בקובץ go.mod עם גרסה מינימלית לכל תלות; לכלי העיצוב אין הגדרות.
  • הכול מועבר לפי ערך. ערך שחי אחרי הפונקציה בורח לערימה, והדגל -gcflags=-m מראה זאת.
  • slice הוא מצביע, אורך וקיבולת; הוספה עשויה לכתוב למערך משותף. העתקה או ביטוי slice מלא מונעים זאת.
  • סדר המעבר על map אקראי, וכתיבה מקבילה אליו מפילה את התהליך.
  • מחרוזת היא בתים, ו־runes הם נקודות קוד. בעברית כל אות היא שני בתים.
  • בדיקות טבלאיות הן ברירת המחדל, ופונקציית Example היא בדיקה שגם מתעדת.

טעויות נפוצות

  • להחזיר חלק מ־slice פנימי. הקוראת מוסיפה לו ומשנה את הנתונים שלך. החזירי עותק או הגבילי קיבולת.
  • להניח שהוספה משנה את ה־slice המקורי. המהדר מחייב להשתמש בתוצאה, אבל השמה למשתנה אחר עוברת ומשאירה שני slices שאולי חולקים מערך. כותבים s = append(s, x).
  • לכתוב ל־map שלא אותחל. זה panic. אתחלי עם make או עם ליטרל.
  • להסתמך על סדר המעבר ב־map. זה „עובד אצלי” ונכשל לפעמים ב־CI. מייני.
  • לחתוך מחרוזת לפי בתים. עברית תיחתך באמצע אות. ספרי runes.
  • לשכוח את sc.Err(). סורק שנכשל נראה בדיוק כמו סוף קובץ.

שאלות ראיון

  1. מה זה slice header, ולמה append יכולה להפתיע? זה מצביע למערך בסיס, אורך וקיבולת. העתקה שלו מעתיקה רק את שלושתם, ולכן שני slices יכולים לחלוק מערך. הוספה כותבת במקום כשיש קיבולת ומקצה מערך חדש כשאין, כך שהתוצאה תלויה בקיבולת, שלא רואים בקוד. ההגנה היא לדעת מי הבעלים של המערך: מי שמחזירה slice פנימי מחזירה עותק או מגבילה קיבולת.

המשך: למה לא להעתיק תמיד? כי העתקה עולה הקצאה, ורוב ה־slices לא משותפים. Go משאירה את ההחלטה לך, ובקוד חם ההבדל נמדד.

  1. מה Go מרוויחה ומה היא מפסידה בכך שיש לה אוסף זבל במקום בעלות? היא מרוויחה פשטות: אין משכי חיים, מותר להחזיר מצביע לערך מקומי, ומבנים עם מעגלים לא דורשים מונה הפניות. היא מפסידה דטרמיניזם: עבודת GC בזמן ריצה, ואין ערבות קומפילציה נגד מרוצי נתונים. בשירותי רשת, שבהם זמן התגובה נשלט בעיקר על ידי הרשת ומסד הנתונים, זה בדרך כלל שווה; במערכות זמן אמת קשיחות, פחות.

  2. למה סדר המעבר על map אקראי, ומה עושים כשצריך סדר? המפרט לא מגדיר סדר, והמימוש מערבב בכוונה כדי שאף קוד לא יסתמך על סדר מקרי שיישבר בשדרוג. כשצריך סדר, אוספים ל־slice וממיינים, כולל שבירת שוויון, כדי שהפלט יהיה דטרמיניסטי.

המשך: ומה אם שתי goroutines כותבות לאותו map? התהליך קורס בשגיאה פטאלית שאי אפשר לתפוס. פותרים בנעילה סביב ה־map, נושא של פרק 5.

  1. מה מחזיר len על המחרוזת „שלום”, ואיך חותכים עברית בבטחה? 8, כי האורך נמדד בבתים ובעברית כל אות היא שני בתים. כדי לחתוך לפי תווים סופרים runes וממירים ל־slice של runes לפני החיתוך. גם זה לא מושלם: אות עם ניקוד היא כמה runes לתו אחד שהעין רואה.
