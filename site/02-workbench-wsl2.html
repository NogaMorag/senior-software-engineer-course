פרק 2: סביבת העבודה: WSL2, Docker, Go ו־uv

בסוף הפרק הזה יהיה לך מחשב שמריץ כל דבר בספר: מערכת הפעלה של שרתים בתוך Windows, מנוע קונטיינרים, שתי שפות התכנות של הספר וניהול גרסאות, ובהמשך גם את הכלים של חלק ה. כל כלי מותקן באותה תבנית קבועה, כך שתמיד תדעי מה הוא, איפה הוא יושב, איך מוודאים שהוא עובד, ואיך מסירים אותו בלי להשאיר לכלוך. בעבודה אמיתית, סביבה שאפשר להקים מחדש בשעה אחת היא מה שמבדיל בין מפתחת שתלויה במזל לבין מפתחת שאפשר לסמוך עליה.

הפרק מחולק לשלושה ימי לימוד, בכוונה, כי יום התקנה ויום שימוש ראשון לא נפגשים:

יום 3 2.9, 2.11 ו־2.12 מאגר הקורס, בדיקת העשן, ההתחייבות הראשונה, ועצירה וניקוי.
יום 57 2.10 הכלים של חלק ה, יום לפני שמשתמשים בהם.

על Mac עושים את אותם ימים עם סעיף 2.13 במקום ההוראות של Windows.

מה הורץ בפועל בזמן כתיבת הפרק, ומה לא:

מה איך נבדק

ההתקנות בתוך Ubuntu, doctor.sh ובדיקות העשן הורצו בקונטיינר של Ubuntu 26.04; הפלטים הועתקו משם

אם משהו ב־Windows נראה אצלך אחרת, התיעוד הרשמי הוא המקור, ונספח ב מרכז את התקלות הידועות.

מה נלמד בפרק

  • לערוך ב־VS Code את הקבצים שבתוך המערכת.
  • להתקין את Go ואת uv בתיקיית הבית, ולבדוק כל הורדה מול טביעת הקובץ שלה.
  • להתקין בגרסה מוצמדת את כלי ה־Go שהספר משתמש בהם.

ידע מקדים

2.1 מה מתקינים ולמה

כלי מה הוא עושה בקורס איפה הוא יושב מתי
WSL2 ו־Ubuntu מערכת Linux אמיתית שבה רץ הכול דיסק וירטואלי בתיקיית המשתמשת של Windows יום 0
Windows Terminal ו־bash הטרמינל והמעטפת שבהם מקלידים כל פקודה מובנה ב־Windows 11; bash בתוך Ubuntu יום 0
Docker Desktop מריץ PostgreSQL, Redis, Redpanda ו־kind בקונטיינרים אפליקציה ב־Windows ומכונת Linux קטנה משלה יום 0
Git ומפתח SSH ניהול גרסאות, והזדהות מול GitHub בלי סיסמה חבילת Ubuntu; המפתח בתיקייה ~/.ssh יום 0
VS Code והרחבת WSL העורך, שעובד ישירות על קבצי Linux אפליקציה ב־Windows ושרת קטן בתוך Ubuntu יום 0
Go השפה הראשית של הספר ושל פרויקט הגמר התיקייה ~/.local/go יום 0
כלי Go ניתוח סטטי ובודקי קוד, מיגרציות, protobuf, סריקת חולשות, בדיקת workflows התיקייה ~/.local/bin יום 0
uv ו־Python 3.14 פרויקטי Python, גרסאות וקבצי נעילה התיקייה ~/.local/bin ומטמון של uv יום 0
kind, kubectl, Helm, Terraform, k6 הכלים של חלק ה התיקייה ~/.local/bin יום 57

מה לא מתקינים, ולמה:

  • לא מנוע Docker נוסף מתוך apt. הוא מתנגש ב־Docker Desktop, ושני מנועים זה מקור קבוע לבלבול.
  • לא Go מתוך apt. הגרסה בחבילות של ההפצה מפגרת אחרי הגרסה שהספר מצמיד.
  • לא pip ולא Python מהאתר הרשמי. uv מנהל את Python ואת התלויות, עם קובץ נעילה.
  • לא sudo לכלים של הקורס. כל הכלים חוץ מחבילות הבסיס נכנסים לתיקיית הבית שלך: קל לשדרג, קל להסיר, ושום דבר לא נוגע במערכת.

לכל כלי בפרק יש אותו מבנה, כדי שתדעי מה לחפש: מה ולמה, איפה, גרסה (עם הפניה לנספח ג), פקודות התקנה, פלט צפוי, בדיקה, הפעלה מחדש, הסרה, וטבלת תקלות קצרה. התקלות שחוצות כלים מרוכזות בסעיף 2.11, וכל הטבלאות מרוכזות שוב בנספח ב.

מונח: משתנה הסביבה PATH הוא רשימת תיקיות, מופרדות בנקודתיים, שבהן המעטפת מחפשת פקודה כשאת מקלידה את שמה. „התקנה” של כלי שורת פקודה היא בדרך כלל רק העתקת קובץ הרצה לתיקייה שנמצאת ב־PATH. זו הסיבה שאחרי התקנה צריך לפעמים לפתוח טרמינל חדש: המעטפת קוראת את הגדרות ה־PATH רק כשהיא עולה.

2.2 WSL2 ו־Ubuntu

שאלה תשובה
מה שכבה שמריצה ליבת Linux אמיתית במכונה וירטואלית קלה, ומעליה הפצת Ubuntu
למה הכלים בספר נבנו קודם ל־Linux, ושרתי הייצור שתעבדי מולם רצים על Linux
איפה קובץ דיסק וירטואלי (ext4.vhdx) בתיקיית המשתמשת של Windows; הבית שלך ב־Linux הוא /home/<שם>
גרסה נכון לאוקטובר 2026: WSL 3.0.1, והפצת ברירת המחדל היא Ubuntu 26.04 LTS (נספח ג)

לפני ההתקנה. צריך שני דברים:

  • מערכת הפעלה: Windows 11, או Windows 10 בגרסה 22H2.
  • וירטואליזציה מופעלת בהגדרות הקושחה. כדי לבדוק, פתחי את מנהל המשימות ועברי ללשונית הביצועים. בחרי את המעבד, ומצאי את השורה Virtualization: צריך להופיע בה Enabled. אם כתוב Disabled, מפעילים אותה בהגדרות הקושחה של המחשב (השם משתנה בין יצרנים).

התקנה. זו אחת הפקודות הבודדות בספר שרצות ב־Windows עצמו, ב־PowerShell עם הרשאות מנהלת. פותחים אותו מהתפריט של לחיצה ימנית על סמל הטרמינל:

wsl --install

הפקודה מפעילה את רכיבי Windows הנדרשים ומורידה את Ubuntu. בסיומה צריך להפעיל מחדש את Windows. אחרי ההפעלה מחדש נפתח חלון של Ubuntu ומבקש שם משתמשת וסיסמה. אלה של Linux, לא של Windows:

  • שם משתמשת: קצר, באותיות קטנות באנגלית, בלי רווחים. הוא יופיע בכל נתיב.
  • סיסמה: תשמש את sudo, הפקודה שמריצה פעולה כמנהלת. בזמן ההקלדה לא מופיע דבר על המסך; זה תקין.

אם החלון לא נפתח מעצמו, או שאת רוצה לראות אילו הפצות קיימות, אלה הפקודות, שוב ב־PowerShell:

wsl --list --online
wsl --install -d Ubuntu

בדיקה מצד Windows. ב־PowerShell רגיל:

wsl --version
wsl --list --verbose

WSL version: 3.0.1.0
Kernel version: ...
...
  NAME      STATE           VERSION
* Ubuntu    Running         2

העמודה החשובה היא VERSION: היא חייבת להיות 2. המספרים בשורות הראשונות יכולים להיות גבוהים יותר אצלך.

בדיקה מצד Ubuntu. מכאן והלאה, כל הפקודות רצות בתוך Ubuntu. פתחי את Ubuntu והריצי:

head -2 /etc/os-release
uname -r
sudo apt update && sudo apt upgrade -y

PRETTY_NAME="Ubuntu 26.04.1 LTS"
NAME="Ubuntu"
...-microsoft-standard-WSL2

השורה השלישית מעדכנת את רשימת החבילות ואת החבילות המותקנות. היא שואלת את סיסמת ה־Linux שבחרת, ובפעם הראשונה עשויה לקחת כמה דקות.

הכלל החשוב ביותר בפרק: עובדים בתוך מערכת הקבצים של Linux. הכוננים של Windows מופיעים תחת /mnt/c, וזה מפתה לעבוד שם. אל תעשי זאת. גישה מ־Linux לקבצים של Windows עוברת דרך שכבת תרגום, והיא איטית בהרבה; גם הרשאות הקבצים וסופי השורות מתנהגים אחרת. התיעוד של Microsoft ממליץ לשמור את קבצי הפרויקט במערכת הקבצים של Linux, כשעובדים עם הכלים שלה. כל מה שבספר חי תחת ~, תיקיית הבית שלך ב־Linux.

כדי לראות את הקבצים האלה בסייר הקבצים של Windows, הריצי את הפקודה הבאה מתוך Ubuntu. היא פותחת את התיקייה הנוכחית בסייר:

explorer.exe .

הפעלה מחדש. הפקודה הראשונה למטה עוצרת את כל ההפצות ואת המכונה הווירטואלית; הטרמינל הבא שתפתחי יעלה אותן מחדש. השנייה עוצרת רק את Ubuntu. שתיהן ב־PowerShell:

wsl --shutdown
wsl --terminate Ubuntu

גיבוי והסרה. הפקודה --unregister מוחקת את ההפצה וכל מה שבתוכה, בלי דרך חזרה. לכן מגבים קודם לקובץ אחד, שאפשר לשחזר ממנו בפקודת הייבוא (--import). ב־PowerShell:

wsl --export Ubuntu D:\backup\ubuntu.tar
wsl --unregister Ubuntu
מה רואים הסיבה הסבירה מה עושים
שגיאה 0x80370102 וירטואליזציה כבויה בקושחה להפעיל אותה בהגדרות ה־UEFI ולהפעיל מחדש
שגיאה 0x8007019e רכיב ה־WSL של Windows לא הופעל להריץ שוב את פקודת ההתקנה כמנהלת, ולהפעיל מחדש
ההפצה לא מופיעה ברשימה ההורדה לא הושלמה להתקין במפורש עם -d Ubuntu
שכחת את סיסמת ה־Linux ב־PowerShell: wsl -u root, ואז בתוך Ubuntu passwd <שם>

2.3 הטרמינל ו־bash

הטרמינל של Windows מותקן מראש. בהגדרות שלו (החץ הקטן ליד הלשוניות) עשי שני שינויים:

איפה בהגדרות מה לשנות
Startup, השדה Default profile לבחור Ubuntu
הפרופיל של Ubuntu, השדה Command line השורה שמתחת

השינוי השני חשוב: בלעדיו הטרמינל נוטה להיפתח בתיקייה של Windows, תחת /mnt/c, בדיוק המקום שבו לא עובדים.

wsl.exe -d Ubuntu --cd ~

פתחי לשונית חדשה. הפקודה pwd מדפיסה את התיקייה הנוכחית, וצריכה להדפיס /home/<שם>. בספר הפקודות מופיעות בלי התחילית שאת רואה במסך (שם, מחשב ונתיב), כדי שתוכלי להעתיק אותן כמו שהן.

המעטפת (shell) היא התוכנית שקוראת את מה שאת מקלידה ומריצה אותו. ב־Ubuntu זו bash. הפקודות שיחזרו בכל הספר:

פקודה מה היא עושה
pwd מדפיסה את התיקייה הנוכחית; הבדיקה הראשונה כשמשהו „לא נמצא”
ls -la רשימת הקבצים, כולל קבצים נסתרים שמתחילים בנקודה
cd ~ חזרה לתיקיית הבית; cd - חוזרת לתיקייה הקודמת
mkdir -p a/b יצירת תיקייה, כולל תיקיות הביניים
cat file ו־less file הדפסת קובץ, או דפדוף בו (יציאה עם q)
command -v go מאיזה קובץ תרוץ הפקודה; ריק אם היא לא נמצאת
echo "$PATH" התיקיות שבהן המעטפת מחפשת פקודות
source ~/.bashrc קריאה מחדש של קובץ ההגדרות של bash, בלי לפתוח טרמינל
Ctrl+C ו־Ctrl+R עצירת תוכנית שרצה; חיפוש בהיסטוריית הפקודות

חבילות בסיס. אלה החבילות היחידות שמותקנות עם sudo, פעם אחת:

sudo apt install -y build-essential ca-certificates curl jq unzip
חבילה למה צריך אותה
build-essential מהדר C; גלאי המרוצים של Go (פרק 5) צריך אותו
ca-certificates התעודות שמאפשרות הורדות מאובטחות
curl הורדת קבצים מהטרמינל
jq קריאת JSON מהטרמינל; נשתמש בו לבדיקת ההורדה של Go
unzip פתיחת קבצי zip; Terraform מגיע כך (סעיף 2.10)

התיקייה של הכלים, ב־PATH. כל הכלים של הקורס נכנסים לשתי תיקיות בבית שלך:

  • ל־Go עצמה: ~/.local/go/bin
  • לכל השאר: ~/.local/bin

הפקודות האלה יוצרות את השנייה ומוסיפות את שתיהן לתחילת ה־PATH, בקובץ ההגדרות של bash:

mkdir -p ~/.local/bin
cat >> ~/.bashrc <<'EOF'

# senior-course (chapter 2): user-space tools first
export PATH="$HOME/.local/go/bin:$HOME/.local/bin:$PATH"
EOF
source ~/.bashrc
echo "$PATH" | tr ':' '\n' | head -2

/home/noga/.local/go/bin
/home/noga/.local/bin

הסימן >> מוסיף לסוף הקובץ ולא דורס אותו, וזה חשוב: בקובץ הזה יש הגדרות של Ubuntu. תיקייה שמופיעה מוקדם ב־PATH מנצחת, ולכן גרסה שהתקנת בבית תנצח גרסה ישנה של המערכת. הריצי את בלוק הפקודות פעם אחת בלבד; הרצה שנייה תוסיף שורה כפולה (לא מזיק, אבל מבלבל).

עברית בטרמינל. הטרמינל מציג אותיות עבריות, אבל ייתכן שמשפט שלם יופיע בסדר הפוך. זו בעיית תצוגה בלבד: הקובץ עצמו תקין, ו־VS Code יציג אותו נכון. הקידוד צריך להיות UTF-8. כדי לבדוק, הריצי locale: השורה הראשונה בפלט צריכה להסתיים ב־UTF-8.

הפעלה מחדש והסרה. הפקודה exec bash מחליפה את המעטפת הנוכחית במעטפת טרייה, כמו לשונית חדשה. אין מה להסיר: הטרמינל מובנה. כדי לבטל את שינוי ה־PATH, מוחקים את שלוש השורות שהוספת בסוף ~/.bashrc.

מה רואים הסיבה הסבירה מה עושים
הטרמינל נפתח ב־/mnt/c/Users/... תיקיית ההתחלה של הפרופיל שדה Command line כמו למעלה
command not found מיד אחרי התקנה המעטפת לא קראה מחדש את ה־PATH source ~/.bashrc, או לשונית חדשה
Could not get lock /var/lib/dpkg/lock-frontend עדכון אוטומטי רץ ברקע לחכות דקה ולנסות שוב; לא למחוק את קובץ הנעילה

2.4 Docker Desktop עם WSL2

מה אפליקציה של Windows שמריצה מנוע Docker במכונה וירטואלית משלה, ומחברת אליו את הפקודה docker

מפתח SSH. זוג מפתחות הוא שני קבצים: מפתח פרטי שלא יוצא מהמחשב לעולם, ומפתח ציבורי (הסיומת .pub) שנותנים ל־GitHub. כש־GitHub רואה חיבור, הוא בודק שלצד השני יש את המפתח הפרטי שמתאים.

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub

לשאלה על מיקום הקובץ לוחצים Enter (ברירת המחדל). לשאלה על סיסמת מפתח (passphrase) מומלץ לבחור אחת: היא מגינה על המפתח אם הקובץ דולף. הפקודה השנייה מדפיסה שורה אחת שמתחילה ב־ssh-ed25519. העתיקי אותה, ואז:

  1. ב־GitHub, פתחי את ההגדרות של החשבון.
  2. בעמוד SSH and GPG keys, לחצי על New SSH key.
  3. הדביקי את השורה, תני למפתח שם (למשל שם המחשב), ושמרי.

כדי לא להקליד את סיסמת המפתח בכל פעם, נשתמש בכלי keychain, שמחזיק את המפתח פתוח בזיכרון בין לשוניות:

sudo apt install -y keychain
echo 'eval "$(keychain --eval --quiet id_ed25519)"' >> ~/.bashrc
source ~/.bashrc
ssh -T git@github.com

בחיבור הראשון מוצגת טביעת אצבע של השרת, עם שאלה אם להמשיך. השווי אותה לטביעות שבתיעוד של GitHub, בעמוד שכתובתו מתחת, ורק אז הקלידי yes:

https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints

התשובה הצפויה:

החלפה והסרה. אם מפתח דלף או שאת מחליפה מחשב: מוחקים אותו בעמוד המפתחות ב־GitHub (זה מה שמבטל אותו באמת), מוחקים את שני הקבצים, ויוצרים זוג חדש. את Git עצמו מסירה הפקודה הראשונה:

2.7 Go

שאלה תשובה
מה המהדר, הכלים (go build, go test, gofmt, go vet) והספרייה הסטנדרטית

ההתקנה היא קובץ דחוס רשמי שנפתח לתוך תיקיית הבית, בלי sudo. לפני הפתיחה בודקים שהקובץ שהורד הוא בדיוק הקובץ שפורסם. האתר של Go מפרסם טביעת SHA-256 לכל קובץ. הטביעה (checksum) היא מחרוזת שמחושבת מכל בית בקובץ. הפקודה sha256sum מחשבת אותה מחדש ומשווה.

ARCH=$(dpkg --print-architecture)
GO_TGZ="go1.27.1.linux-${ARCH}.tar.gz"
cd /tmp
curl -fsSLO "https://go.dev/dl/${GO_TGZ}"
curl -fsSL "https://go.dev/dl/?mode=json&include=all" \
  | jq -r --arg f "$GO_TGZ" '.[].files[] | select(.filename == $f) | "\(.sha256)  \(.filename)"' \
  | sha256sum -c -
rm -rf "$HOME/.local/go"
tar -C "$HOME/.local" -xzf "$GO_TGZ"
go env -w GOBIN="$HOME/.local/bin"
go version
go env GOROOT GOPATH GOBIN

2.11 פתרון תקלות

רוב התקלות בהתקנה הן אחת משלוש: הפקודה לא נמצאת, נמצאת גרסה אחרת ממה שהתקנת, או שאת בתיקייה הלא נכונה. סדר הבדיקה שפותר את רובן, לפני שמחפשים ברשת:

  1. קראי את השורה האחרונה של השגיאה, עד הסוף. ברוב המקרים היא אומרת בדיוק מה חסר.
  2. איפה את? הפקודה pwd. אם התשובה מתחילה ב־/mnt/c, עברי ל־~.
  3. מי ירוץ? הפקודה command -v <כלי> מראה את הנתיב. נתיב תחת /usr/bin כשציפית ל־~/.local/bin אומר שעותק של המערכת מנצח.
  4. ה־PATH עדכני? פתחי לשונית חדשה, או הריצי source ~/.bashrc, ונסי שוב.

  6. נספח ב מרכז את התקלות הידועות לפי הודעת השגיאה, כולל תקלות שאופייניות ל־Mac.

2.12 עצירה, הפעלה מחדש וניקוי

ביום רגיל. אין צורך לעצור כלום בין ימי לימוד, אבל שלושה הרגלים חוסכים זיכרון ודיסק:

מתי מה עושים
בסוף תרגיל עם compose docker compose -p chNN down בתיקיית התרגיל, ו־down -v אם רוצים גם למחוק את הנתונים
בסוף יום שבו לא צריך קונטיינרים לצאת מ־Docker Desktop
כשהמחשב איטי או WSL מתנהג מוזר wsl --shutdown ב־PowerShell, ולפתוח טרמינל מחדש

מקום בדיסק של Docker. אימג'ים, קונטיינרים שעצרו, ונפחים (volumes) מצטברים. קודם מסתכלים, אחר כך מוחקים:

docker system df
docker container prune
docker image prune
docker system prune

פקודה מה היא מוחקת
docker system df כלום; מציגה כמה מקום תופס כל סוג
docker container prune קונטיינרים שעצרו
docker image prune אימג'ים שאין להם תגית (שכבות ישנות של בניות)

כל הפקודות שמוחקות שואלות לפני כן. נפחים לא נמחקים באף אחת מהן, בכוונה: שם נמצאים הנתונים שלך. מחיקה של נפח היא פעולה מפורשת, בדגל -v של down בתרגיל, או בפקודה שמתחת:

docker volume rm <name>

הדיסק הווירטואלי לא קטן מעצמו. כל הפצה של WSL שמורה בקובץ ext4.vhdx שגדל לפי הצורך. לפי התיעוד של Microsoft, קובץ כזה גדל כשמוסיפים קבצים, אבל לא קטן כשמוחקים אותם. אחרי ניקוי גדול בתוך Ubuntu, הנה הדרך להחזיר את המקום ל־Windows. הצעדים לא הורצו בהרצה שבה נכתב הספר (אין שם Windows); הם מבוססים על שני עמודי התיעוד שבסוף הסעיף.

  1. עצירה. צאי מ־Docker Desktop, ואז ב־PowerShell עצרי את WSL. הקובץ חייב להיות מנותק בזמן הכיווץ.
  2. הנתיב לקובץ. ב־PowerShell רגיל, הפקודה השנייה למטה מדפיסה את הנתיב המלא של הדיסק של Ubuntu. העתיקי אותו.
  3. כיווץ. פתחי PowerShell עם הרשאות מנהלת והריצי diskpart. בשורה DISKPART> הקלידי את שלוש השורות של הבלוק השני, עם הנתיב שהעתקת. הכיווץ עשוי לקחת כמה דקות.
wsl --shutdown
(Get-ChildItem -Path HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss | Where-Object { $_.GetValue("DistributionName") -eq 'Ubuntu' }).GetValue("BasePath") + "\ext4.vhdx"

select vdisk file="<path-to-ext4.vhdx>"
compact vdisk
exit

שימי לב לשני דברים. ראשית, Microsoft ממליצה לא לגעת בקבצים של WSL בכלים של Windows, חוץ מהפעולות המתועדות האלה; לא מזיזים את הקובץ ולא פותחים אותו. שנית, האימג'ים של Docker לא יושבים בדיסק של Ubuntu אלא בדיסק נפרד של Docker Desktop. הצעדים כאן לא מטפלים בו, ולכן ייתכן שהמקום ש־docker system prune פינה לא יחזור ל־Windows. לדיסק הזה יש הגדרות משלו ב־Docker Desktop, ותיעוד משלו באתר של Docker.

https://learn.microsoft.com/en-us/windows/wsl/disk-space
https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/compact-vdisk

הגבלת הזיכרון של WSL. לפי התיעוד של Microsoft, ברירת המחדל היא חצי מהזיכרון של המחשב. אם המחשב נעשה איטי כשאשכול kind וכמה קונטיינרים רצים, אפשר להגביל:

  • הקובץ: קובץ טקסט בשם .wslconfig, ב־Windows, בתיקייה שהמשתנה %UserProfile% מצביע עליה.
  • התוכן: הבלוק שמתחת. המספרים הם נקודת פתיחה; התאימי למחשב שלך.
  • הפעלה: אחרי השמירה, עצירה של WSL ב־PowerShell (כמו בצעד הראשון למעלה), כדי שההגדרה תיקלט.
[wsl2]
memory=8GB
processors=4

ניקוי מלא. אם תרצי להתחיל מאפס: כל סעיף בפרק כולל את פקודות ההסרה של הכלי שלו, בסדר הפוך להתקנה. המאגר שלך ב־~/senior-course שווה יותר מכל כלי. לפני --unregister (סעיף 2.2), ודאי שהוא נשמר ב־GitHub, או בקובץ הגיבוי של wsl --export.

ב־Mac: הפקודה sed שונה במקום אחד. בגרסה של macOS הדגל -i דורש ארגומנט, גם אם הוא ריק. זה ההבדל היחיד בפקודות הספר שגורם לשגיאה מבלבלת (invalid command code) במקום לעבוד:

sed -i 's/a/b/' file      # Ubuntu
sed -i '' 's/a/b/' file   # macOS

פקודות ההורדה ובדיקת הטביעות של סעיפים 2.7, 2.7.1 ו־2.10 עובדות ב־Mac כמו שהן, אחרי החלפת השמות לפי הטבלה. הן נבדקו בפועל על Mac עם מעבד של Apple. שתי הפקודות sha256sum ו־unzip קיימות במערכת. גם הפקודה shasum -a 256 -c עובדת. לבדיקת הטביעה של Go צריך גם את jq:

brew install jq

שתי הערות על המעטפת. ראשית, הסקריפטים של הספר נכתבו ל־bash, ומריצים אותם במפורש דרכה; לכן המעטפת השונה של Mac לא מפריעה. הגרסה של bash שמגיעה עם macOS היא 3.2 הישנה, והרופא נבדק גם בה. שנית, קבצים שהורדו בדפדפן מסומנים ב־macOS כ„הגיעו מהאינטרנט”, והמערכת עלולה לחסום את הרצתם; קבצים שהורדו ב־curl לא מסומנים כך. אם הורדת בדפדפן ונחסמת, הפקודה שמתחת מסירה את הסימון:

xattr -d com.apple.quarantine <file>

את Docker Desktop מורידים מעמוד ההתקנה הרשמי, בגרסה שמתאימה למעבד; הדרישות המעודכנות מופיעות שם. כל השאר בפרק, מסעיף 2.9 והלאה, זהה: אותן תיקיות, אותו doctor.sh, אותן בדיקות.

סיכום

  • מערכת ההפעלה: Ubuntu בתוך WSL2.
  • קונטיינרים: Docker Desktop, על אותו מנוע וירטואלי.
  • ניהול גרסאות: Git, עם מפתח SSH להזדהות. העורך: VS Code, שעובד על הקבצים שבתוך המערכת.
  • שפות: Go ו־uv בתיקיית הבית; ביום 57 נוספים חמשת הכלים של חלק ה.
  • עובדים רק בתוך מערכת הקבצים של Linux, תחת ~; הכוננים של Windows תחת /mnt/c הם לייבוא חד־פעמי.
  • הכלים של הקורס נכנסים לתיקיית הבית, בלי sudo. תיקייה מוקדמת ב־PATH מנצחת, ואחרי שינוי פותחים לשונית חדשה.
  • כל הורדה נבדקת מול הטביעה שפורסמה לצידה, לפני ההתקנה. כל אימג' שחייב להיות זהה מוצמד לפי טביעה.
  • doctor.sh מסכם את המצב, וקוד היציאה שלו הוא מספר הכשלים; הוא נשען על השוואת גרסאות כמספרים.
  • בדיקות העשן מוכיחות שהשרשרת כולה עובדת: בדיקה טבלאית ב־Go, pytest בסביבה הווירטואלית, וקונטיינר ראשון.
  • לכל כלי יש דרך לעצור, לנקות ולהסיר; נפחים של Docker נמחקים רק במפורש.

טעויות נפוצות

  • לעבוד תחת /mnt/c „כי שם הקבצים”. הכול איטי, והרשאות וסופי שורות משתבשים. מעתיקים פעם אחת לתוך ~.
  • להתקין Docker גם מ־apt. שני מנועים, ושתי פקודות docker שמתחלפות לפי ה־PATH.
  • לדלג על בדיקת הטביעה כי „זה אתר רשמי”. הבדיקה לא חושדת באתר; היא תופסת הורדה חלקית או קובץ אחר ממה שחשבת.
  • לפתוח גרסת Go חדשה מעל הישנה. קבצים ישנים נשארים ושוברים את ההתקנה. מוחקים את התיקייה ואז פותחים.
  • להסיק מ„הפקודה עובדת” שהגרסה נכונה. עותק ישן מוקדם ב־PATH עונה ראשון. command -v ו־doctor.sh אומרים את האמת.
  • להריץ docker system prune בלי לקרוא מה הוא מוחק. הוא בטוח לנפחים, אבל docker volume prune לא.

שאלות ראיון

  1. למה להריץ את התלויות של שירות (מסד נתונים, תור) בקונטיינרים גם בפיתוח מקומי? כדי שהגרסה והתצורה יהיו זהות לאלה של הסביבות האחרות, ויוגדרו בקובץ שנכנס ל־Git ולא בזיכרון של מישהי. מתקינים פעם אחת את Docker ולא כל מסד בנפרד, ומוחקים ומקימים מחדש בשניות. המחיר: עוד שכבה להבין, צריכת זיכרון, והבדלים קטנים שנשארים (מערכת קבצים, רשת) בין מחשב מקומי לייצור.

  2. איך את מוודאת שקובץ הרצה שהורדת הוא מה שחשבת? משווים את טביעת ה־SHA-256 שלו לטביעה שפורסמה. זה מוכיח שלמות, לא מקור: אם תוקף שולט בשרת, הוא מחליף את שניהם. למקור צריך חתימה, למשל חתימות GPG או Sigstore, ובארגון גם מאגר פנימי של קבצים שנבדקו. ההחלטה כמה רחוק ללכת תלויה במה שהכלי מקבל: כלי שרץ ב־CI עם סודות מצדיק יותר.

המשך: ולמה להצמיד אימג' לפי digest ולא לפי תגית? כי תגית היא מצביע שאפשר להזיז, וה־digest מחושב מהתוכן. הצמדה לפי digest נותנת בנייה שחוזרת על עצמה, והמחיר הוא שעדכוני אבטחה לא מגיעים מעצמם: צריך תהליך שמעדכן את ההצמדות.

  1. פקודה שהתקנת „לא נמצאת”, או מדווחת גרסה אחרת. איך את מאבחנת? קודם command -v לראות איזה קובץ רץ, ואחר כך ה־PATH עצמו, לפי הסדר. אחר כך: האם המעטפת נפתחה לפני ההתקנה, והאם קובץ ההגדרות באמת נטען. הנקודה בראיון היא השיטה: לבודד שכבה אחר שכבה במקום לנחש, ולהבין שה־PATH הוא רשימה מסודרת שבה הראשון מנצח.

  2. מה ההבדל בין טווח גרסאות בקובץ ההגדרות לבין קובץ נעילה? הטווח אומר מה מקובל; קובץ הנעילה אומר מה בדיוק הותקן, כולל תלויות עקיפות וטביעות. בלי נעילה, שתי התקנות של אותו פרויקט באותו יום יכולות לקבל גרסאות שונות, ובאג מופיע רק אצל אחת. המחיר: מישהו צריך לעדכן את הנעילה באופן יזום, ולבדוק את העדכון.

  3. למה סקריפט בדיקה מחזיר את מספר הכשלים כקוד יציאה? כי קוד יציאה הוא החוזה בין תוכניות: CI, Makefile או סקריפט אחר מחליטים לפיו בלי לפרש טקסט. אפס אומר הצלחה, וכל מספר אחר אומר כמה דברים לתקן. המגבלה: קודי יציאה מעל 125 שמורים למעטפת, אז סקריפט שעלול לספור יותר צריך תקרה, וקוד שמור לשגיאת שימוש (כאן 64) חייב להיות מתועד.

המשך: ואיך בודקים סקריפט כזה בלי להתקין ולהסיר כלים? מריצים אותו מול תיקייה של כלים מזויפים, עם PATH שמכיל רק אותה, כמו test_doctor.sh. כך כל מקרה (חסר, ישן, חדש) הוא שורה בבדיקה.
