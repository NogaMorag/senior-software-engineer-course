# פרק 9: עיצוב API ו־gRPC

ממשק API הוא הבטחה. ברגע שלקוח אחד כתב קוד מול צורת התשובה שלך, כל שינוי בה הוא משא ומתן, וכל שגיאה
שלא תיעדת היא באג אצל מישהו אחר. הפרק מלמד לתכנן את ההבטחה לפני הקוד: חוזה כתוב, צורת שגיאה אחת, עימוד
שלא מאבד פריטים, ניסיון חוזר שלא יוצר כפילויות, ושינויים שלא שוברים לקוחות. ואז הוא מראה מתי gRPC
מתאים יותר מממשק JSON רגיל, ומתי ממש לא.

## מה נלמד בפרק

- לחשוב על API כחוזה: משאבים, פעלים וקודי סטטוס שמשמעותם ידועה מראש.
- לכתוב קובץ OpenAPI 3.1 שהוא מקור האמת, ולבדוק אותו בכלי שרץ בקונטיינר.
- להחזיר כל שגיאה בצורה אחת: פרטי בעיה לפי RFC 9457.
- עימוד עם cursor שלא מכפיל ולא מדלג כשנוספים פריטים באמצע.
- מפתחות אידמפוטנטיות, כולל בקשות מקבילות עם אותו מפתח.
- גרסאות ותאימות לאחור: שינויים מוסיפים, קורא סובלני, כותרות הוצאה משימוש.
- שירות gRPC קטן שמחולל עם buf, בדיקות בלי רשת, ומתי לא לבחור בו.

## ידע מקדים

- פרק 6, סעיפים 6.1 עד 6.6: הנתב, שכבות ביניים (middleware), לוגים מובנים, תצורה ובדיקות. התרגיל כותב
  גרסאות קטנות משלו לאותם רכיבים, ולא מייבא את התרגיל של פרק 6.
- פרק 4: ממשקים ושגיאות עטופות. פרק 5: מנעולים, context והדגל `-race`.
- פרק 2: Docker פועל. את buf ושני התוספים שלו התרגיל בודק בתחילת יום 21, ומתקין אם הם חסרים.

## 9.1 REST כחוזה: משאבים ופעלים

ב־REST מתארים את המערכת כאוסף של משאבים (resources), שלכל אחד כתובת, ומפעילים עליהם קבוצה קטנה
וקבועה של פעלים, שיטות ה־HTTP. הכוח של הסגנון הוא האחידות: כל לקוח, פרוקסי ומטמון יודעים מה מותר לעשות
עם `GET` בלי לקרוא את התיעוד שלך. בתרגיל המשאב הוא פריט בקטלוג:

| פעולה | שיטה ונתיב | הצלחה | בטוחה | אידמפוטנטית |
| --- | --- | --- | --- | --- |
| רשימה | `GET /v1/items` | 200 | כן | כן |
| יצירה | `POST /v1/items` | 201 עם `Location` | לא | לא, אלא עם מפתח |
| קריאה | `GET /v1/items/{id}` | 200 | כן | כן |
| מחיקה | `DELETE /v1/items/{id}` | 204 | לא | כן |

שיטה **בטוחה** (safe) לא משנה מצב, ולכן מותר לשמור את התשובה במטמון. שיטה **אידמפוטנטית** (idempotent)
היא כזו שעשר בקשות זהות משאירות את אותו מצב כמו בקשה אחת. מחיקה פעמיים משאירה פריט מחוק; יצירה פעמיים
יוצרת שני פריטים. לכן לקוח שקיבל זמן קצוב ביצירה לא יודע אם מותר לו לנסות שוב, וסעיף 9.5 פותר את זה.

קוד הסטטוס (status code) הוא החלק היחיד בתשובה שכל רכיב בדרך מבין, ולכן הוא חייב להיות נכון:

| קוד | מתי |
| --- | --- |
| 400, 413, 415 | קלט שגוי; גוף גדול מדי; סוג תוכן שאינו JSON |
| 404, 405 | אין משאב או נתיב כזה; שיטה לא נתמכת (עם הכותרת `Allow`) |
| 409, 422 | התנגשות עם המצב; בקשה מובנת אבל אסורה |
| 429, 503 | עומס; הלקוח מנסה שוב אחרי המתנה (פרק 15) |
| 500 | באג אצלנו |

הכלל שכדאי לומר בראיון במשפט אחד: **4xx אומר „את טעית”, 5xx אומר „אנחנו טעינו”.** קוד 400 על באג בשרת
עוצר ניסיונות חוזרים בדיוק כשהיה צריך אותם, וקוד 500 על קלט שגוי מעיר את התורנית בלילה.

## 9.2 OpenAPI כמקור אמת

המונח OpenAPI הוא תקן לתיאור ממשק HTTP בקובץ טקסט: נתיבים, פרמטרים, גופי בקשה, תשובות לכל קוד וסכמות
של הנתונים. גרסה 3.1 מיישרת את הסכמות שלה עם התקן JSON Schema, ולכן כלים של התקן הזה מבינים גם אותן.

„מקור אמת” (source of truth) הוא סדר עבודה: שינוי ב־API מתחיל בקובץ ונסקר כקובץ, ורק אחר כך נכתב הקוד.
כשמפיקים את הקובץ מהקוד, החוזה הוא תוצאת לוואי: שדה שנוסף בטעות למבנה מופיע בו, ואף אחד לא החליט עליו. בקובץ `api/openapi.yaml` של התרגיל גם הגבולות כתובים:

<div dir="ltr" align="left">

```yaml
    NewItem:
      type: object
      additionalProperties: false
      required: [sku, name, price_cents]
      properties:
        sku:
          type: string
          pattern: "^[A-Z0-9-]{3,32}$"
          examples: [MUG-001]
```

</div>

קובץ חוזה שאף אחד לא בודק נרקב. כלי בדיקה (linter) תופס הפניה לסכמה שלא קיימת, פעולה בלי תשובת שגיאה
או מזהה פעולה כפול. התרגיל מריץ את Redocly מתוך קונטיינר, כך שאין מה להתקין מעבר ל־Docker. התג נעול
לגרסה שנבדקה ב־Docker Hub (נכון לאוקטובר 2026; ראי נספח ג):

<div dir="ltr" align="left">

```bash
docker run --rm -v "$PWD/api:/spec:ro" -w /spec redocly/cli:2.57.0 lint openapi.yaml
```

</div>

הפלט המצופה מסתיים בשורה `Your API description is valid`. ממצא אחד מוחרג במפורש, לפי מיקום: לנתיב
`/healthz` אין שגיאת לקוח לתעד.

> **שימי לב:** הכלי מוכיח שהקובץ תקין, לא שהשרת מקיים אותו. את הצד השני בודקות בדיקות הקוד: נתיבי השרת
> מול נתיבי החוזה, וקוד, סוג תוכן וצורת גוף של כל שגיאה. פרק 26 מרחיב לבדיקות חוזה (contract tests).

## 9.3 חוזה שגיאות: problem details

בלי החלטה מפורשת, כל נתיב ממציא צורת שגיאה משלו, והלקוח כותב קוד שונה לכל אחד. המסמך RFC 9457
(יולי 2023, מחליף את RFC 7807) מגדיר צורה אחת שנקראת פרטי בעיה (problem details). סוג התוכן שלה הוא
`application/problem+json`, ואלה החברים שלה:

| חבר | משמעות |
| --- | --- |
| `type` | כתובת שמזהה את סוג הבעיה; ברירת המחדל היא `about:blank` |
| `title` | תקציר קבוע לסוג, שלא משתנה בין מופעים |
| `status` | קוד הסטטוס, חוזר בגוף |
| `detail` | הסבר למופע הזה, לבני אדם; אסור לפענח אותו בקוד |
| `instance` | מזהה המופע; בתרגיל, הנתיב שבו קרתה הבעיה |

מותר להוסיף חברי הרחבה (extension members), וה־RFC מחייב לקוחות להתעלם ממה שהם לא מכירים. התרגיל
מוסיף חבר בשם `errors`: רשימת שדות לא תקינים, ולכל שדה הסבר ומצביע (JSON Pointer) למקומו בגוף. זו
הדוגמה שה־RFC עצמו מביא לשגיאת תקינות. הלקוח מחליט מה לעשות לפי `type`, ולא לפי הטקסט.

הקובץ `internal/problem/problem.go` מגדיר את המבנה ואת פונקציית הכתיבה היחידה:

<div dir="ltr" align="left">

```go
// Write sends p as the response. Instance defaults to the request path, so a log line and the body agree.
func Write(w http.ResponseWriter, r *http.Request, p *Problem) {
	if p.Instance == "" && r != nil {
		p.Instance = r.URL.Path
	}
	w.Header().Set("Content-Type", ContentType)
	w.Header().Set("X-Content-Type-Options", "nosniff")
	w.WriteHeader(p.Status)
	_ = json.NewEncoder(w).Encode(p) // the status line is already sent; nothing useful to do on error
}
```

</div>

כותרות נקבעות לפני `WriteHeader`, ואחרי ששורת הסטטוס נשלחה אי אפשר לשנות אותה, ולכן שגיאה בקידוד
נבלעת. כל סוג בעיה מוגדר פעם אחת, ומתועד בחוזה בסכמה `Problem`, שאותה את מוסיפה ביום 19.

חוזה שגיאות אחד חל גם על שגיאות שלא כתבת. הנתב של Go עונה על נתיב לא מוכר ועל שיטה לא נתמכת בטקסט
פשוט. הקובץ `internal/httpapi/server.go` סוגר את שני הפערים:

<div dir="ltr" align="left">

```go
	// A pattern without a method is less specific than the same pattern with one, so these catch
	// every other method and answer 405 in the problem format instead of the mux's plain text.
	mux.Handle("/v1/items", methodNotAllowed("GET, POST"))
	mux.Handle("/v1/items/{id}", methodNotAllowed("GET"))
	mux.Handle("/v1/products/{id}", methodNotAllowed("GET"))
	mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		problem.Write(w, r, problem.NotFound.New("no such route"))
	})
```

</div>

תבנית עם שיטה מדויקת יותר מאותה תבנית בלי שיטה (פרק 6), ולכן כל שיטה אחרת נופלת לתבנית הכללית. גם
שגיאת 500 עוברת דרך `Write`, והשגיאה האמיתית נרשמת רק בלוג: הודעה של מסד נתונים בתוך `detail` היא
דליפה של מבנה פנימי.

## 9.4 עימוד: offset מול cursor

רשימה בלי עימוד (pagination) היא תקרית שמחכה ליום שבו יש בטבלה מיליון שורות. הדרך הנאיבית היא היסט (offset): „תני לי 5 פריטים החל ממקום 5”. היא נשברת כשהרשימה מסודרת
מהחדש לישן ונוספים פריטים בזמן שהלקוח עובר בין עמודים:

| שלב | מה הלקוח רואה |
| --- | --- |
| עמוד 1, היסט 0 | פריטים 10, 9, 8, 7, 6 |
| בינתיים נוספים 11 ו־12 | הרשימה היא עכשיו 12, 11, 10, 9, 8, 7, 6, ... |
| עמוד 2, היסט 5 | פריטים 7, 6, 5, 4, 3: הפריטים 7 ו־6 חוזרים |

כשפריטים נמחקים קורה ההפך, ופריט מדלג ולא מוצג אף פעם. בדיקה אחת בתרגיל משחזרת את הטבלה כדי לתעד את
הפגם. ויש להיסט גם מחיר: מסד הנתונים עובר על כל השורות שלפני ההיסט וזורק אותן (פרק 10).

### 9.4.1 cursor: להמשיך מהפריט האחרון

הפתרון הוא לזכור את הפריט האחרון שראית, לא את המקום. השרת מחזיר עם העמוד סמן שנקרא cursor, ובו מפתח
המיון של הפריט האחרון; הבקשה הבאה מבקשת פריטים שממוינים אחריו, ופריטים חדשים לא משפיעים על ההמשך.

זה עובד רק אם מפתח המיון **יציב ושלם**: לכל שני פריטים סדר אחד וקבוע. זמן יצירה לבדו לא מספיק, כי שני
פריטים יכולים להיווצר באותו רגע. לכן המפתח הוא זוג, זמן ואחריו מזהה שמכריע תיקו. הקובץ
`internal/catalog/memory.go` מתעד את השאילתה המקבילה, שתחזור בפרק 10:

<div dir="ltr" align="left">

```go
// List returns up to limit items that sort strictly after the cursor (all items when after is nil),
// and whether more exist. In SQL the same query is:
//
//	SELECT ... FROM items WHERE (created_at, id) < ($1, $2)
//	ORDER BY created_at DESC, id DESC LIMIT $3 + 1
```

</div>

מבקשים פריט אחד יותר מגודל העמוד: אם הוא הגיע, יש עמוד הבא, בלי שאילתת ספירה. הסמן עצמו אטום
(opaque): בפנים יש JSON קטן עם שדה גרסה, מקודד ב־base64 בגרסה שבטוחה לכתובות. הקובץ `internal/page/page.go`:

<div dir="ltr" align="left">

```go
func Encode(c Cursor) string {
	b, _ := json.Marshal(wire{V: version, T: c.CreatedAt.UnixNano(), ID: c.ID}) // cannot fail for this struct
	return base64.RawURLEncoding.EncodeToString(b)
}
```

</div>

קידוד כזה אינו הצפנה. הוא אומר ללקוח שאין כאן מה לפרק, וכל עוד הלקוחות רק מחזירים את המחרוזת, מותר לך
לשנות את תוכנה. סמן שלא נוצר בשרת מקבל 400; סמן שאסור לזייף חותמים עליו (פרק 28).

בדיקת הליבה היא `TestCursorNoDuplicatesNoGapsUnderInserts`. היא עוברת על 25 פריטים בעמודים בגדלים 1, 3
ו־10, מוסיפה פריטים בין עמוד לעמוד, ובודקת שכל פריט מקורי הופיע בדיוק פעם אחת. היא רצה גם עם שעון
קפוא, שבו לכל הפריטים אותו זמן, וזו הריצה שמוכיחה שהמזהה באמת מכריע תיקו.

המחיר: אין קפיצה לעמוד 37, ומספר העמודים הכולל דורש ספירה נפרדת. לטבלה בממשק משתמש היסט סביר; לרשימות
שלקוחות סורקים, כמו ב־Hookline, cursor הוא ברירת המחדל.

## 9.5 מפתחות אידמפוטנטיות

לקוח שולח בקשת יצירה ומקבל זמן קצוב. אולי הבקשה לא הגיעה, ואולי הפריט נוצר והתשובה אבדה. מפתח אידמפוטנטיות (idempotency key) פותר את זה: הלקוח
מייצר ערך ייחודי לכל פעולה לוגית, ושולח אותו בכותרת `Idempotency-Key` בכל ניסיון של אותה פעולה.

הכותרת מתוארת בטיוטה של קבוצת העבודה httpapi ב־IETF. הגרסה האחרונה, 07, פורסמה באוקטובר 2025 ותוקפה
פג באפריל 2026 בלי שהפכה ל־RFC (נכון לאוקטובר 2026, לפי datatracker). כלומר זו מוסכמה מתועדת, לא תקן.
התרגיל מממש את הסמנטיקה שלה:

| מצב | תשובה |
| --- | --- |
| מפתח חסר או לא תקין | 400 מסוג `idempotency-key-missing` |
| מפתח חדש | מריצים את ה־handler ושומרים את התשובה |
| אותו מפתח ואותה בקשה, הראשונה הסתיימה | התשובה השמורה, בית בבית, עם `Idempotent-Replayed` |
| אותו מפתח ובקשה אחרת | 422 מסוג `idempotency-key-reused` |
| אותו מפתח, הראשונה עוד רצה | 409 מסוג `idempotency-in-progress`, עם `Retry-After` |
| הראשונה הסתיימה ב־5xx או קרסה | המפתח משתחרר, וניסיון חוזר ירוץ מחדש |

„אותה בקשה” נקבעת לפי טביעת אצבע (fingerprint): גיבוב SHA-256 של השיטה, הנתיב, סוג התוכן והגוף. הכותרת
`Idempotent-Replayed` היא מוסכמה של התרגיל, לא של הטיוטה. הלב של המנגנון, בקובץ `internal/idem/idem.go`:

<div dir="ltr" align="left">

```go
// Begin claims key for a request with fingerprint fp, atomically.
func (s *Store) Begin(key string, fp [32]byte) (Outcome, Response) {
	s.mu.Lock()
	defer s.mu.Unlock()
	now := s.now()
	s.sweep(now)
	e, ok := s.entries[key]
	if ok && now.After(e.expires) {
		delete(s.entries, key)
		ok = false
	}
	switch {
	case !ok:
		s.entries[key] = &entry{fingerprint: fp, expires: now.Add(s.ttl)}
		return Started, Response{}
	case e.fingerprint != fp:
		return Mismatch, Response{}
	case !e.done:
		return InProgress, Response{}
	default:
		return Replay, e.resp
	}
}
```

</div>

הבדיקה והשמירה קורות תחת נעילה אחת, וזה העיקר. בשתי קריאות נפרדות, שתי בקשות מקבילות היו עוברות את
הבדיקה יחד ויוצרות שני פריטים: מרוץ (race condition) קלאסי של בדיקה ואז פעולה. במסד נתונים, אילוץ
ייחודיות עושה את אותה עבודה (פרק 11). אחת הבדיקות עוצרת בקשה בתוך ה־handler ושולחת שנייה, שמקבלת 409.

שכבת הביניים סביב `Begin` קוראת את הגוף, מחשבת טביעת אצבע ומריצה את ה־handler לתוך מקליט (recorder),
כדי שאפשר יהיה לשמור את התשובה לפני שהיא נשלחת. שלוש החלטות תכנון מסתתרות בה, וכדאי שתדעי להגן עליהן:

- **תשובת 4xx נשמרת.** לפי הטיוטה, מפתח שייך לגוף בקשה אחד; אחרי 400 מתקנים ושולחים מפתח חדש.
- **תשובת 5xx לא נשמרת**, וגם לא בקשה שקרסה ב־panic. כשל שלנו לא אמור לנעול את הלקוח בחוץ. המחיר: אם
  חלק מהעבודה בוצע לפני הכשל, הוא יבוצע שוב. מעל מסד נתונים הטרנזקציה מבטלת את החלק הזה, ולכן ב־Hookline
  המפתח נשמר באותה טרנזקציה כמו האירוע (פרק 38, סעיף 38.2).
- **המפתח תחום לשיטה ולנתיב**, וב־Hookline גם לדיירת (tenant), כדי שדיירת אחת לא תראה תשובה של דיירת אחרת.

המפתחות נשמרים לזמן חיים (TTL) של 24 שעות, והחוזה מצהיר על כך כפי שהטיוטה דורשת. המגבלה הגדולה: החנות
בזיכרון של תהליך אחד, וניסיון חוזר שמגיע לעותק אחר של השירות לא יכיר את המפתח.

> **איך Rust עושה את זה:** ב־Rust הטבלה הייתה יושבת בתוך `Mutex<HashMap<..>>`, והמהדר היה מכריח אותך
> לגשת אליה רק דרך המנעול. ב־Go אין אכיפה כזאת: אפשר לגשת לשדה `entries` גם בלי לנעול. את המשמעת
> מחזירים מתודות קטנות שכל אחת נועלת בעצמה, והרצת הבדיקות עם `-race` (פרק 5).

## 9.6 גרסאות ותאימות לאחור

תאימות לאחור (backward compatibility) אומרת שלקוח שנכתב מול הגרסה של אתמול עובד גם היום. שומרים עליה
כשיודעים מראש אילו שינויים בטוחים:

| שינוי | בטוח ללקוחות קיימים? |
| --- | --- |
| להוסיף שדה לתשובה, נתיב, או פרמטר אופציונלי | כן, אם הלקוחות סובלניים |
| להוסיף ערך לרשימת ערכים סגורה (enum) בתשובה | מסוכן: לקוח שמטפל בכל הערכים יישבר |
| להפוך שדה אופציונלי בבקשה לחובה | לא |
| לשנות שם, טיפוס או משמעות של שדה | לא |
| להסיר שדה או נתיב | רק אחרי תהליך הוצאה משימוש |

הכלל שמאפשר להוסיף שדות נקרא קורא סובלני (tolerant reader): לקוח קורא את מה שהוא צריך ומתעלם מהשאר.
ובכל זאת, השרת **דוחה** שדות לא מוכרים בבקשה (סעיף 9.9). שדה כזה הוא כמעט תמיד שגיאת כתיב, ובלי
דחייה הלקוח מקבל 201 ופריט בלי המחיר ששלח. השרת יודע מה הוא מבין, ולכן קפדנות זולה לו; הלקוח לא יודע
מה יתווסף מחר, ולכן הוא זה שסובלני.

> **איך Rust עושה את זה:** ב־serde ברירת המחדל סובלנית, ושדות לא מוכרים נזרקים בשקט. קפדנות מבקשים
> במפורש, עם `#[serde(deny_unknown_fields)]`. ב־Go המצב זהה, והקריאה `DisallowUnknownFields` היא הבקשה
> המפורשת להפך.

הגרסה הראשית יושבת בנתיב (`/v1/`), וגרסה חדשה מגיעה רק עם שינוי שובר שאי אפשר להימנע ממנו. כדי להעביר
לקוחות מודיעים להם בתוך הפרוטוקול. הנתיב הישן `/v1/products/{id}` בתרגיל עדיין עובד, ומסמן כל תשובה בשלוש כותרות:

| כותרת | מקור | משמעות |
| --- | --- | --- |
| `Deprecation` | RFC 9745 (מרץ 2025) | מאז מתי הנתיב הוצא משימוש, כ־`@` ואחריו שניות יוניקס |
| `Sunset` | RFC 8594 | מתי הוא יפסיק לעבוד, בתאריך HTTP |
| `Link` | `rel="successor-version"` | לאן לעבור |

כותרות לבדן לא מספיקות. לפני תאריך הסיום מודדים מי עדיין קורא לנתיב הישן (פרק 24) ופונים אליו. נתיב
שנמחק כשעדיין יש לו תעבורה הוא תקרית שהכנת בעצמך.

## 9.7 gRPC ו־protobuf

המסגרת gRPC משמשת לקריאות מרוחקות (RPC) בין שירותים. במקום משאבים ופעלים מגדירים שירות ומתודות, כמו
ממשק בשפת תכנות. ההודעות מקודדות ב־protobuf, פורמט בינארי עם סכמה, והתעבורה רצה מעל HTTP/2. מקובץ הגדרה
אחד מחוללים קוד ללקוח ולשרת. בתרגיל השירות `CatalogService` מגדיר שתי מתודות:

- המתודה `Ping`, לבדיקה שהשירות עונה.
- המתודה `GetItem`, לקריאת פריט לפי מזהה.

אלה ההודעות של פריט, בקובץ `proto/catalog/v1/catalog.proto`:

<div dir="ltr" align="left">

```proto
message Item {
  string id = 1;
  string sku = 2;
  string name = 3;
  int64 price_cents = 4;
  // Field 5 was "double price" in an early draft. Removed fields are reserved, never reused.
  reserved 5;
  reserved "price";
  // Unix time in milliseconds.
  int64 created_at_unix_ms = 6;
}
```

</div>

המספרים שליד השדות הם החוזה: על החוט נשלח מספר השדה, ושינוי מספר או טיפוס שובר כל לקוח קיים. שדה
שהוסר מסומן `reserved`, כדי שלקוח ישן לא יפענח אף פעם בתים חדשים כמחיר.

### 9.7.1 buf: בדיקה וחילול

הכלי buf מחליף את ההפעלה הידנית של `protoc`. הקובץ `buf.yaml` מגדיר את המודול ואת כללי הבדיקה. הקובץ
`buf.gen.yaml` מפעיל את שני התוספים שמחוללים קוד לתיקיית הפלט, `gen`:

<div dir="ltr" align="left">

```bash
buf lint
buf generate
git status --short gen
```

</div>

| פקודה | מה היא עשתה |
| --- | --- |
| `buf lint` | בדקה שמות, חבילות ומבנה לפי כללי `STANDARD`; שקט פירושו תקין |
| `buf generate` | מחקה את `gen/` וחוללה מחדש את ההודעות, השרת והלקוח |
| `git status --short gen` | פלט ריק: הקוד השמור זהה בדיוק למה שחולל עכשיו |

**את הקוד המחולל שומרים במאגר**, משלוש סיבות:

- מי שבונה את הפרויקט לא צריך את buf ואת התוספים, בגרסאות המדויקות.
- סקירת קוד רואה מה השתנה בפועל בממשק המחולל.
- הפקודה `go get` של המודול עובדת בלי שלב חילול.

המחיר הוא סכנה שקובץ ההגדרה והקוד יתרחקו, ולכן בודקים ב־CI שחילול מחדש לא משנה כלום (פרק 23). הפקודה
`buf breaking` משווה את קובץ ההגדרה לענף הראשי ועוצרת שינוי שובר, למשל שינוי שם של שדה, לפני שהוא נכנס;
ה־README של התרגיל מראה את הפלט.

### 9.7.2 שרת, קודי סטטוס ובדיקה עם bufconn

הקובץ `internal/grpcapi/server.go` מממש את הממשק המחולל מעל אותה חנות שמשרתת את ה־HTTP. המבנה מטמיע את
`UnimplementedCatalogServiceServer`, ולכן כשתתווסף מתודה, הקוד ימשיך להתקמפל ויחזיר `Unimplemented`. ב־gRPC
אין פרטי בעיה: שגיאה היא קוד סטטוס של gRPC והודעה. המיפוי שווה שינון:

| מצב | HTTP | gRPC |
| --- | --- | --- |
| קלט לא תקין | 400 | `InvalidArgument` |
| לא נמצא | 404 | `NotFound` |
| כבר קיים | 409 | `AlreadyExists` |
| עבר גבול הזמן הכולל | 504 | `DeadlineExceeded` |
| באג אצלנו | 500 | `Internal` |

החבילה `bufconn` מספקת מאזין בזיכרון. השרת והלקוח מדברים את הפרוטוקול המלא, כולל מסגרות HTTP/2 וקודי
סטטוס, בלי פורט ובלי רשת. השרת מאזין ל־`lis`, והלקוח מתחבר אליו כך, בקובץ
`internal/grpcapi/server_test.go`:

<div dir="ltr" align="left">

```go
	conn, err := grpc.NewClient("passthrough:///bufnet",
		grpc.WithContextDialer(func(ctx context.Context, _ string) (net.Conn, error) { return lis.DialContext(ctx) }),
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
```

</div>

בלי הקידומת `passthrough:///` הלקוח מנסה לפענח את השם `bufnet` בשרת שמות. בדיקה נוספת שולחת קריאה עם גבול
זמן כולל (deadline) שכבר עבר, ומקבלת `DeadlineExceeded`: ב־gRPC גבול הזמן עובר עם הבקשה לשרת.

> **איך Rust עושה את זה:** ב־Rust המקבילה הנפוצה היא הספרייה tonic. הקוד מחולל בכל בנייה, מתוך הקובץ
> `build.rs`. ב־Go המוסכמה הפוכה: מחוללים פעם אחת ושומרים במאגר, והבנייה לא מריצה שום מחולל.

## 9.8 מתי לא gRPC

המסגרת gRPC טובה במקום שבו שני הצדדים בשליטתך: שירותים פנימיים, חוזה קפדני, קידוד קומפקטי, זרימה בשני
הכיוונים וגבולות זמן שעוברים בשרשרת. מחוץ למקום הזה המחיר עולה מהר:

- **דפדפנים.** קוד בדפדפן לא מקבל שליטה מלאה ב־HTTP/2, ובעיקר לא את ה־trailers שבהם נשלח הסטטוס. צריך
  פרוטוקול מתווך כמו gRPC-Web ופרוקסי שמתרגם, כלומר עוד רכיב לתפעל.
- **API ציבורי.** הלקוחות מצפים ל־JSON ולשורת `curl` שעובדת. לבקש מהם לחולל לקוח מקובץ הגדרה זה חסם
  כניסה, ולכן גם Hookline חושף לדיירות ממשק JSON רגיל.
- **ניפוי באגים.** התעבורה בינארית. כדי לקרוא אותה צריך את קובץ ההגדרה, או שירות השתקפות (reflection)
  וכלי ייעודי כמו grpcurl.
- **מאזני עומסים.** לקוח gRPC מחזיק חיבור HTTP/2 ארוך אחד ומרבב עליו בקשות רבות. מאזן שמחלק חיבורים, ולא
  בקשות, שולח את כל התעבורה של לקוח לעותק אחד. ה־Service הרגיל של Kubernetes עובד ברמת החיבור (פרק 20).

לכן בתרגיל ה־HTTP הוא הפנים הציבוריות וה־gRPC הוא הצינור הפנימי, ושניהם קוראים לאותה חנות.

## 9.9 אימות קלט וגבולות

אימות קלט (input validation, לא לבלבל עם אימות זהות) הוא הקו הראשון של שירות: כל בית שנכנס מגיע ממישהו
שלא כתבת. הסדר הולך מהזול ליקר: גודל, אחר כך פורמט, אחר כך תוכן.

הפונקציה `http.MaxBytesReader` עוטפת את גוף הבקשה ונכשלת אחרי מספר בתים נתון. היא חייבת לבוא **לפני** כל
קורא: מפענח JSON שמקבל גוף של גיגה־בייט ישמח לקרוא את כולו לזיכרון. בתרגיל, שכבה בשם `limitBody` מחילה
אותה על נתיב היצירה, 16 KiB כברירת מחדל, ושגיאת חריגה הופכת ל־413. גם לשרת עצמו יש זמנים קצובים
לכותרות, לבקשה ולתשובה; בלעדיהם, לקוח ששולח בית אחד בדקה מחזיק חיבור לנצח.

אחרי הגודל, פענוח קפדני של אובייקט JSON אחד בדיוק, בקובץ `internal/httpapi/decode.go`:

<div dir="ltr" align="left">

```go
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	err = dec.Decode(dst)
	if err == nil && dec.Decode(&struct{}{}) != io.EOF {
		err = errors.New("unexpected data after the JSON object")
	}
```

</div>

הפענוח השני הוא בדיקה שרבים שוכחים: `Decode` קורא ערך אחד ועוצר, כך ששני אובייקטים רצופים עוברים בשקט
והשני נזרק. לפני כל זה נבדק סוג התוכן (415), ושדה בטיפוס שגוי הופך לבעיית תקינות עם מצביע לשדה.

אחר כך כללי השדות, כפי שהם כתובים בחוזה. כל הבעיות מדווחות יחד, כדי שהלקוח יתקן הכול בסבב אחד:

| שדה | כלל |
| --- | --- |
| `sku` | חובה; 3 עד 32 תווים מתוך אותיות גדולות, ספרות ומקף |
| `name` | חובה; לא ריק אחרי הסרת רווחים; UTF-8 תקין; עד 200 תווים |
| `price_cents` | חובה; מספר שלם מ־0 עד 100,000,000 |

המבנה שמקבל את הגוף משתמש במצביעים, כדי להבדיל בין שדה חסר לבין שדה ששווה אפס: מחיר 0 חוקי, מחיר חסר
לא. מחירים נשמרים כמספר שלם של אגורות, כי חשבון בשברים בינאריים מאבד אגורות.

> **שימי לב:** הגבולות כתובים פעמיים, בחוזה ובקוד, ולכן הם יכולים להתרחק. הבדיקות בודקות את הקוד; את
> ההתאמה לחוזה בודקת סקירת קוד, או כלי שבודק בקשות מול הסכמה (ראי העשרה אופציונלית).

## סיכום

- API הוא חוזה: משאבים, פעלים אחידים וקודי סטטוס ידועים. 4xx טעות של הלקוח, 5xx שלנו.
- הקובץ `openapi.yaml` הוא מקור האמת: שינוי מתחיל בו, כלי בודק אותו, ובדיקות בודקות שהשרת מקיים אותו.
- כל שגיאה היא פרטי בעיה לפי RFC 9457, והלקוח מחליט לפי `type`; גם 404 ו־405 של הנתב.
- עימוד עם cursor על זמן ומזהה לא מכפיל ולא מדלג; מפתח אידמפוטנטיות הופך ניסיון חוזר לבטוח.
- תאימות לאחור: מוסיפים ולא משנים; לקוח סובלני ושרת קפדן בבקשות; הוצאה משימוש עם כותרות ומדידה.
- בין שירותים פנימיים מתאים gRPC, והמספרים בקובץ ה־proto הם החוזה; כלפי חוץ, ממשק JSON.
- גבול גודל לפני פענוח, פענוח קפדני, וכללי שדות שכתובים גם בחוזה.

## מונחים לזכור

| מונח בעברית | באנגלית | במשפט אחד |
| --- | --- | --- |
| משאב | resource | דבר שיש לו כתובת ב־API, כמו פריט או אוסף פריטים |
| אידמפוטנטיות | idempotency | חזרה על פעולה משאירה את אותו מצב כמו פעם אחת |
| פרטי בעיה | problem details | צורת השגיאה של RFC 9457 |
| עימוד | pagination | חלוקה של רשימה ארוכה לעמודים |
| היסט | offset | עימוד לפי מקום ברשימה; נשבר כשהרשימה משתנה |
| cursor | cursor | סמן אטום עם מפתח המיון של הפריט האחרון שנראה |
| מפתח אידמפוטנטיות | idempotency key | ערך שהלקוח שולח כדי שניסיון חוזר לא יבצע פעמיים |
| טביעת אצבע | fingerprint | גיבוב של הבקשה, שקובע אם שתי בקשות הן אותה בקשה |
| תאימות לאחור | backward compatibility | לקוח ישן ממשיך לעבוד מול שרת חדש |
| קורא סובלני | tolerant reader | לקוח שמתעלם משדות שהוא לא מכיר |
| הוצאה משימוש | deprecation | הודעה שנתיב ייעלם, עם תאריך ותחליף |
| קוד מחולל | generated code | קוד שכלי כתב מקובץ הגדרה, ולא עורכים ביד |
| אימות קלט | input validation | בדיקה שהקלט בגודל, בפורמט ובטווח המותרים |

## טעויות נפוצות

- **להחזיר 200 עם הודעת שגיאה בגוף.** פרוקסי, מטמון ומדדים רואים הצלחה. הסטטוס חייב לומר את האמת.
- **לפענח את `detail` בקוד הלקוח.** זה טקסט לבני אדם, והוא ישתנה. מחליטים לפי `type`.
- **cursor על זמן יצירה בלבד.** שני פריטים באותו רגע, והסדר ביניהם שרירותי. מוסיפים מזהה שמכריע תיקו.
- **לבדוק מפתח אידמפוטנטיות ולשמור אותו בשתי פעולות.** בקשות מקבילות עוברות את הבדיקה יחד. ההחלטה
  חייבת להיות אטומית: מנעול אחד, או אילוץ ייחודיות במסד.
- **לשמור תשובת 5xx תחת המפתח.** הלקוח ננעל בחוץ בגלל כשל שלנו, עד שהמפתח יפוג.
- **להשתמש שוב במספר של שדה שנמחק ב־proto.** לקוחות ישנים יפענחו בתים חדשים לשדה הלא נכון.
- **לשים את `MaxBytesReader` אחרי הפענוח, או לא לשים בכלל.** הגבול שווה משהו רק לפני הקריאה הראשונה.

## שאלות ראיון

1. **איך תתכנני את חוזה השגיאות של API חדש?** צורה אחת לכל השגיאות, ועדיף תקן על המצאה: פרטי בעיה לפי
   RFC 9457, עם סוג תוכן משלו וכלל ברור להרחבות. הלקוח מחליט לפי `type`, מזהה יציב שמתועד בחוזה, ולא
   לפי הטקסט. גם שגיאות שלא כתבתי, של הנתב או מ־panic, יוצאות באותה צורה ובלי פרטי מימוש. התמורה: לקוח
   שכותב טיפול בשגיאות פעם אחת.

2. **למה עימוד לפי היסט נשבר, ומה מחליף אותו?** היסט הוא מקום ברשימה, והמקום משתנה כשנוספים או נמחקים
   פריטים לפניו, ולכן מופיעות כפילויות ודילוגים. cursor זוכר את מפתח המיון של הפריט האחרון, ובתנאי
   שהמפתח שלם (זמן ומזהה) ויש עליו אינדקס, הוספות לא משפיעות. מוותרים על קפיצה לעמוד שרירותי ועל ספירה
   זולה.

   **המשך:** ואם ממיינים לפי שדה שמשתנה, כמו מחיר? פריט שהמחיר שלו השתנה יכול לחצות את הסמן ולהופיע
   פעמיים או לא בכלל. מתעדים את זה, או מעמדים מעל תמונת מצב (snapshot) של התוצאה, במחיר של אחסון.

3. **מה מבטיח מפתח אידמפוטנטיות, ומה לא?** בתוך זמן החיים שלו, ניסיונות חוזרים של אותה בקשה מבצעים את
   הפעולה לכל היותר פעם אחת ומחזירים את אותה תשובה; בקשה אחרת עם אותו מפתח נדחית, ובקשה מקבילה מקבלת
   409. הוא לא מגן אחרי שפג, לא עוזר ללקוח ששולח מפתח חדש בכל ניסיון, ובזיכרון של תהליך אחד לא חוצה
   עותקים. במימוש אמיתי שומרים אותו באותה טרנזקציה כמו התוצאה, עם אילוץ ייחודיות לפי דיירת ומפתח.

   **המשך:** למה לא לשמור גם 5xx? כי אז כשל זמני שלנו נועל את הלקוח בחוץ. אם החשש הוא ביצוע חלקי,
   הפתרון הוא טרנזקציה שמבטלת הכול, לא שמירת הכשל.

4. **אילו שינויים ב־API בטוחים, ואיך מסירים נתיב?** הוספה בטוחה כשהלקוחות סובלניים; שינוי שם, טיפוס,
   משמעות או חובה אינו בטוח. להסרה מכריזים בכותרות הוצאה משימוש ותאריך סיום, מודדים מי עדיין
   קורא ופונים אליו, ומסירים רק כשהתעבורה נעלמה. בקובץ ה־proto, בדיקת תאימות אוטומטית רצה ב־CI.

5. **מתי תבחרי ב־gRPC, ומתי בממשק JSON רגיל?** בין שירותים פנימיים שבשליטתי, gRPC: חוזה קפדני עם קוד
   מחולל, קידוד קומפקטי וגבולות זמן שעוברים בשרשרת. לכל מה שפונה החוצה, ממשק JSON: דפדפנים, לקוחות
   ציבוריים, אינטגרציות, וכל מקום שבו ניפוי עם `curl` חשוב. ובתשתית, חיבור ארוך אחד דורש איזון ברמת הבקשה.

- **מקור אמת:** הקובץ `openapi.yaml` קודם לקוד; כלי בודק אותו, בדיקות בודקות שהשרת מקיים אותו.
