# נספח ה: רשימות בדיקה

תשע רשימות קצרות, לרגעים שבהם קל לשכוח צעד: לפני ראיון, בסבב תכנון מערכות, בסקירת קוד, לפני שמעלים שירות
לייצור, לפני שפותחים PR, באבטחה, לפני הגשה של מטלת בית, לפני פרסום הפרויקט, ובסוף כל שבוע. כל פריט נלקח מהפרק
שמפורט בכותרת, ושם יש ההסבר המלא.

כל פריט הוא כן או לא, עם ראיה: קובץ שקיים, בדיקה שרצה, או מספר שמדדת, עם התנאים. פריט שאין לו ראיה כזאת לא
מסומן. אפשר להעתיק כל רשימה לפתק בכספת, ולסמן שם.

## לפני ראיון (פרק 34)

**בשיחה הראשונה עם המגייסת** (סעיף 34.1.6), שואלים ורושמים:

- [ ] כמה שלבים יש, מה כל אחד, וכמה זמן לוקח התהליך כולו.
- [ ] מטלת בית או קוד חי, באיזו שפה, ובאיזה כלי.
- [ ] האם מותר להשתמש בכלי AI, ובאילו שלבים (סעיף 34.1.4).
- [ ] האם ראיון התכנון הוא על תחום המוצר של החברה.
- [ ] מי יהיו המראיינים.
- [ ] התהליך רשום בפתק משלו: באיזה שלב הוא, ומה נאמר בכל שיחה.

**הסיפורים** (סעיפים 34.2 ו־34.3):

- [ ] חמישה סיפורים כתובים, במבנה מצב, משימה, פעולה, תוצאה, ומה הייתי עושה אחרת.
- [ ] טבלת הכיסוי מלאה: כל סימן (היקף, עמימות, קונפליקט, כישלון, השפעה) מסומן לפחות פעמיים.
- [ ] אחד מהסיפורים על Hookline, עם מה שכתבת בעצמך ומה שקיבלת מהקורס.
- [ ] יש סיפור כישלון אמיתי, עם התיקון ומה שהשתנה אחריו.
- [ ] כל סיפור סופר בקול עם שעון עצר, בפחות משלוש דקות; „אני” בפעולה, „אנחנו” רק במצב.
- [ ] כל מספר בסיפור הוא מספר שאת יודעת איך נמדד.
- [ ] אין בסיפורים שמות לקוחות, נפחים חסויים או שמות של מערכות פנימיות.
- [ ] קראת את המודעה, ובחרת איזה סיפור עונה על כל שורה בסעיף האחריות שלה.

**קורות החיים** (סעיף 34.5):

- [ ] תקציר קצר בראש העמוד: תפקיד, שנים, מסלול.
- [ ] שמות הכלים כתובים כמו במודעות.
- [ ] כל סעיף ניסיון עונה על מה עשית, איך, ומה יצא, ואת יכולה להגן על כל שורה בו.
- [ ] Hookline מופיע כפרויקט לימוד שנבנה לפי מפרט, ו־Rust מופיעה כבידול.

**שכר והצעות** (סעיף 34.6):

- [ ] יש לך טווח, עם המקור והתאריך שלו, ולא מספר יחיד.
- [ ] הצעות מושוות בטבלה לפי שווי כולל: מניות, קרן השתלמות, פנסיה והודעה מוקדמת, לא רק הבסיס.

**כלל הכנות** (סעיף 34.7):

- [ ] אין בקורות החיים או בסיפורים טענה שלא עשית, כולל מספר שלא מדדת.
- [ ] תרגלת תשובה של „אני לא יודעת”: מה כן ידוע לך, ואיך היית מבררת.

## סבב תכנון מערכות (פרק 29, סעיף 29.1)

**הצעדים, לפי הסדר** (מותר לחזור אחורה כשמספר שובר דרישה):

- [ ] דרישות שאפשר לבדוק, ולא־מטרות שמנטרלות ציפיות סבירות. שאלת מי, מה, כמה ומה מחוץ לתחום.
- [ ] הערכת גודל: בקשות בשנייה, בתים, רוחב פס, וגם השיא, כל אחד עם ההנחה שלו כתובה.
- [ ] בתים לאחסון, ביטים לרשת.
- [ ] API: נתיבים או הודעות, עם דוגמה אחת של בקשה ותשובה.
- [ ] מודל נתונים שנגזר מהשאילתות: אינדקס לכל שאילתה חמה, אילוץ לכל כלל שאסור לשבור.
- [ ] תכנון כללי: תרשים אחד, ופסקה לכל רכיב: מה הוא מחזיק, ומה קורה כשהוא נופל.
- [ ] צלילה לעומק בשניים או שלושה חלקים קשים: מצבי כשל ופשרות.

**לכל פשרה שלושה חלקים:**

- [ ] החלופה הפשוטה.
- [ ] למה לא היא כאן.
- [ ] מה היה משנה את דעתך.

**בזמן הסבב:**

- [ ] חלוקת זמן גסה, לפי ההצעה בסעיף 29.1.3: כחמש דקות לדרישות, חמש להערכה, עשר ל־API ולנתונים, עשר
  לתכנון הכללי, וחמש־עשרה לצלילה.
- [ ] כשהמראיינת מכוונת לחלק אחר, הולכים איתה.
- [ ] במסמך כתוב: לפחות שתי חלופות, ואחת מהן „לא לעשות כלום” (פרק 29, טעויות נפוצות).

## סקירת קוד (פרק 27)

**לפני שקוראים שורה** (סעיף 27.1):

- [ ] קראת את התיאור של הבקשה: מה היא מנסה לעשות.
- [ ] דירגת כל חלק לפי שלוש שאלות: מה יכול להישבר, כמה רחוק זה מגיע, כמה קשה לחזור.
- [ ] סדר הקריאה הוא לפי הסיכון, לא לפי סדר הקבצים; שמות וסגנון בסוף.
- [ ] אם אי אפשר לסקור את הבקשה ברצינות בשעה, ההערה הראשונה היא בקשה לפצל.

**מה מחפשים** (סעיף 27.2):

- [ ] נכונות בגבולות: קלט ריק, ענק, שלילי, כפול; מקרי קצה של עימוד וזמן.
- [ ] טיפול בשגיאות: עטיפה, השוואה עם `errors.Is`, ומה יוצא ללקוח.
- [ ] מקביליות: מצב משותף, נעילות, goroutines שלא מסתיימות.
- [ ] דליפת משאבים: חיבורים, קבצים, גופי תשובה, `rows.Close()`.
- [ ] אבטחה: הרשאה לכל אובייקט, הזרקות, סודות, קלט שנבנה לתוך שאילתה.
- [ ] בדיקות שבודקות: האם כל בדיקה יכולה להיכשל, והאם היא מכסה את המקרה המסוכן.
- [ ] יכולת הפעלה: לוגים, מדדים, זמנים קצובים, ביטול, תצורה.
- [ ] מה חסר: בדיקת הרשאה, סגירת משאב, בדיקה למקרה המסוכן.

**הכלים** (סעיפים 27.5 ו־27.6):

- [ ] הכלים `go vet`, staticcheck ו־golangci-lint נקיים; כל השתקה עם נימוק.
- [ ] הכלי `govulncheck` רץ, ומה שנקרא בפועל מתוקן קודם.
- [ ] ב־Python, ruff ו־mypy נקיים.

**ההערות** (סעיף 27.3):

- [ ] כל הערה מתחילה באחת מחמש תוויות החומרה של סעיף 27.3, מ„חוסם” ועד „שבח”.
- [ ] כל הערה אומרת כמה זה חשוב, למה, ומה לעשות; על הקוד, לא על האדם.
- [ ] ההערות החוסמות נכתבו קודם.
- [ ] בסוף, פסקת סיכום אחת: מה חוסם ומה לא.

**כשמקבלים סקירה** (סעיף 27.4):

- [ ] כל הערה קיבלה תשובה: תיקון, הסבר, או משימה עם קישור.
- [ ] אי־הסכמה מנומקת בעובדה: מדידה, תיעוד או בדיקה.

## מוכנות של שירות לייצור (פרקים 6, 20 עד 25, 28)

**השירות עצמו** (פרק 6):

- [ ] לשרת יש זמנים קצובים, לפחות `ReadHeaderTimeout`.
- [ ] כיבוי מסודר: האות הופך ל־context, ו־`Shutdown` מקבל context חדש עם זמן חסד.
- [ ] גוף הבקשה מוגבל בגודל לפני הפענוח (`http.MaxBytesReader`).
- [ ] כל התצורה ממשתני סביבה נבדקת בעלייה, וכל הבעיות מדווחות יחד.
- [ ] כל שורת לוג נושאת את מזהה הבקשה.
- [ ] שגיאות פנימיות לא יוצאות ללקוח.
- [ ] ‏pprof מוגש רק על מאזין פרטי.

**ה־image** (פרק 19):

- [ ] בנייה רב־שלבית, ושלב ריצה מינימלי (distroless).
- [ ] משתמש מספרי שאינו root.
- [ ] אין סודות באף שכבה; `.dockerignore` קיים.
- [ ] תגית לפי גרסה ומזהה commit, לא `latest`.
- [ ] יש SBOM, והסריקה נקראה, וכל ממצא קיבל החלטה כתובה.

**על Kubernetes** (פרקים 20 ו־21):

- [ ] שלוש בדיקות מוגדרות; בדיקת החיות בודקת רק את התהליך, ובדיקת המוכנות את התלויות.
- [ ] requests ו־limits מוגדרים, ותקרת הזיכרון תואמת את מה שהשירות באמת צורך.
- [ ] ל־HPA יש request למעבד.
- [ ] השדה `replicas` לא כתוב ב־manifest כשיש HPA.
- [ ] פריסה מתגלגלת עם `maxUnavailable: 0`, ובדיקת מוכנות שעוצרת גרסה שבורה.
- [ ] סודות ב־Secret שנוצר מבחוץ, לא ב־Git.
- [ ] ה־selector של ה־Deployment ושל ה־Service תואם לתוויות, בלי תווית גרסה בתוכו.
- [ ] ה־chart עובר `helm lint` ו־kubeconform, ונבדק גם באשכול אמיתי.

**תשתית כקוד** (פרק 22):

- [ ] גרסאות ה־providers נעולות, וקובץ הנעילה ב־Git.
- [ ] ה־state מחוץ ל־Git, ובצוות ב־backend מרוחק עם נעילה.
- [ ] קראת את ה־plan לפני apply, ואין בו `-/+` על משהו שמחזיק נתונים.

**תצפיתיות** (פרק 24):

- [ ] מדדי RED לשירות, עם התבנית של הנתיב כ־label ולא הנתיב הגולמי.
- [ ] מעקב שעובר בין השירותים (propagator מותקן), וכיבוי שמרוקן את הטלמטריה.
- [ ] לוגים מובנים עם מזהה המעקב.
- [ ] הדשבורד שמור כקובץ במאגר.

**SLO והתראות** (פרק 25):

- [ ] יש SLI שמודד את מה שהמשתמשת חווה, ו־SLO שאינו 100%.
- [ ] התראות על קצב שריפה בכמה חלונות, עם בדיקות promtool.
- [ ] לכל התראה יש runbook, וכל קריאה דורשת פעולה.

**אבטחה** (פרק 28): הרשימה המלאה בהמשך הנספח.

## היגיינת PR ו־CI (פרק 23)

**ה־PR:**

- [ ] הבקשה קטנה, והתיאור אומר מה, למה, ואיך בדקת (פרק 27, סעיף 27.4).
- [ ] הבדיקות, הבודקים הסטטיים והפורמט עברו אצלך לפני ה־push.
- [ ] ‏actionlint נקי על כל קובצי ה־workflow (סעיף 23.8).

**ה־workflow:**

- [ ] ‏`permissions: contents: read` ברמה העליונה, ולכל job רק מה שהוא צריך.
- [ ] ‏`packages: write` רק ל־job שדוחף.
- [ ] קלט חיצוני (כותרת PR, שם ענף) עובר דרך `env`, לא ישירות בתוך `run`.
- [ ] אין `pull_request_target` שמריץ קוד מה־PR.
- [ ] ‏`shell: bash`, כדי ש־`pipefail` יתפוס כישלון בצינור.
- [ ] לכל job יש זמן קצוב, ויש קבוצת מקביליות שמבטלת הרצות מיושנות.
- [ ] ‏service container עם בדיקת בריאות ומיפוי פורטים.
- [ ] ב־job שבו המסד אמור להיות, דילוג של בדיקות הוא כישלון (`fail-on-skip`).
- [ ] בדיקה חובה לא מוגדרת על workflow שמסונן לפי נתיב.
- [ ] ‏actions בגרסה ראשית ב־workflows של בדיקות; ב־workflow שכותב או מפרסם, SHA מלא עם התגית כהערה.
- [ ] ה־image מתפרסם רק מ־`main`, ורק אחרי בדיקת עשן.

## אבטחה (פרק 28)

- [ ] עברת על הרשימה של OWASP, והתחלת בהרשאה לכל אובייקט (BOLA, סעיף 28.1).
- [ ] הדיירת היא חלק ממפתח החיפוש ומהחתימה של המאגר, בכל נתיב.
- [ ] אובייקט של דיירת אחרת מחזיר את אותו 404 כמו מזהה שלא קיים, ויש לזה בדיקה.
- [ ] באסימון JWT, האלגוריתם נלקח מהתצורה ולא מהאסימון עצמו.
- [ ] המפתח נבחר לפי `kid` מתוך ה־JWKS, עם סוג מפתח מתאים.
- [ ] המנפיק והקהל (`iss`, ‏`aud`) נבדקים במדויק, וזמן התפוגה חובה.
- [ ] נגד SSRF, הכתובת שנפתרה נבדקת ב־`Control` של ה־dialer (סעיף 28.5).
- [ ] הבדיקה מבטלת קודם את המיפוי של IPv4 בתוך IPv6.
- [ ] אין proxy בלקוח, וכל הפניה נבדקת מחדש.
- [ ] מפתחות API נשמרים כ־SHA-256, לא בטקסט גלוי ולא ב־bcrypt.
- [ ] סודות לא מופיעים בלוגים, ויש בדיקה שמוודאת את זה.
- [ ] ‏Secret של Kubernetes מוגן בהרשאות ובהצפנה במנוחה, כי base64 אינו הצפנה.
- [ ] יש SBOM, וסריקה של ה־image לצד govulncheck (פרק 28).
- [ ] יש מודל איומים בשיטת STRIDE, ולכל שורה בו בדיקה ובעלים (סעיף 28.8).

## הגשה של מטלת בית (פרק 34, סעיף 34.4)
